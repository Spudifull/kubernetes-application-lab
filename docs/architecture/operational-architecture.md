# Эксплуатационная архитектура

Документ описывает механизмы развёртывания и эксплуатации приложения, которые исследуются в Kubernetes Application Lab: запуск, обновление, завершение работы, обработку отказов, масштабирование и диагностику.

**Состояние:** сценарии уровня приложения и CI/CD/GitOps проверены в пределах соответствующих отчётов (`Current`). Для многонодового `kind` подготовлены отдельные сценарии этапа 10A (`Prepared`), результаты их запуска пока не опубликованы. Эксперименты на независимых виртуальных машинах с `kubeadm` остаются `Target`.

## Развёртывание приложения

Для базового сценария используется следующая последовательность:

```text
исходный код → контейнерный образ → выделенный кластер kind
→ подготовка Namespace → установка Helm release
→ готовность Pod → проверка HTTP через Service
```

`Taskfile.yml` содержит команды сборки, развёртывания и проверки. Helm chart описывает ресурсы приложения; его корректность проверяется отдельно от фактической работы в кластере. Команда `task smoke` создаёт временный клиентский `Pod`, обращается к `/version` через DNS-имя `Service` и проверяет конкретный сетевой путь.

Для GitOps используется отдельная схема:

```text
изменение в Git → проверка CI → публикация проверенного образа
→ изменение желаемого состояния → синхронизация Argo CD
→ проверка Pod imageID и ответа /version
```

Окружение development синхронизируется автоматически, stable — вручную. Для последнего проверенного выпуска обоим окружениям передан один digest образа API без повторной сборки. CI также анализирует образы publisher и worker, но кластерная проверка и продвижение между окружениями относятся к API, а не к полному стеку PostgreSQL/Kafka. См. [контракт поставки](../design/ci-cd-gitops.md), [проверку нового выпуска](../verification/security-release.md) и [историю первых GitOps-экспериментов](../verification/gitops-development.md).

## Готовность и завершение работы

Kubernetes и приложение выполняют разные части процедуры завершения:

1. При удалении `Pod` Kubernetes начинает процедуру завершения и обновляет состояние ресурса. Изменения маршрутизации через `EndpointSlice` распространяются независимо от действий приложения.
2. Если задан HTTP `preStop`, kubelet выполняет его до отправки сигнала `SIGTERM` основному процессу. В лабораторном профиле этот обработчик создаёт ограниченную задержку перед завершением.
3. Получив `SIGTERM`, приложение перестаёт принимать новую работу и завершает уже принятые запросы в пределах установленного срока.
4. Если процесс не завершился за отведённое Kubernetes время, он может быть принудительно остановлен.

`/readyz` показывает готовность принимать работу, `/livez` — работоспособность процесса.

### Почему важен `preStop`

При первоначальном обновлении с нагрузкой клиент получал HTTP `503` от завершающихся экземпляров. После введения короткого `preStop` повторный опыт завершился без ошибок в пределах измеренной нагрузки.

Состояния `Pod`, условия `EndpointSlice` (`ready`, `serving`, `terminating`) и клиентские ответы необходимо фиксировать раздельно. Изменение `EndpointSlice` не доказывает, что маршрутизация уже обновилась во всех точках сети. Прямой `SIGTERM` процессу не запускает Kubernetes `preStop`.

Подробности: [контракт времени выполнения](../design/application-runtime.md) и [обновление под нагрузкой](../verification/rolling-update-under-load.md).

## Обновление и откат

Успешное завершение `helm upgrade` или `kubectl rollout status` подтверждает состояние механизмов развёртывания, но не гарантирует отсутствие ошибок у клиентов.

При проверке обновления сопоставляются:

- ревизия Helm, образ и состояние `Deployment`;
- готовность новых экземпляров и завершение старых;
- состояния `EndpointSlice`;
- HTTP-ответы клиента во время нагрузки;
- журналы завершения приложения и события Kubernetes.

Неисправное обновление проверяется отдельно: новое состояние может не достичь готовности, после чего выполняется явный откат и повторная проверка доступности. История успешных и неуспешных запусков сохраняется в [отчётах](../verification/README.md).

В GitOps восстановление проверялось иначе: после временного изменения образа в работающем development-окружении система возвращалась к известной исправной конфигурации из Git. При этом старая реплика продолжала отвечать, поэтому эксперимент не доказывает полную недоступность приложения. Результаты приведены в [отчёте](../verification/gitops-development.md).

## Обработка заданий и отказ зависимостей

Основной путь фоновой обработки:

```text
HTTP API → PostgreSQL (задание + outbox)
→ сервис публикации → Kafka → обработчик → PostgreSQL
```

При отправке события возможен разрыв между подтверждением Kafka и отметкой о публикации в PostgreSQL. В этом случае сервис может опубликовать запись повторно. Обработчик должен учитывать повторную доставку и не создавать повторный SQL-эффект. После успешной SQL-транзакции он подтверждает смещение Kafka; нарушение этого порядка привело бы к риску потерять результат обработки.

В отдельных лабораторных сценариях проверялись остановка брокера, сбой обработчика до подтверждения смещения, повторные попытки и перенос сообщений в DLQ. Эти результаты относятся к конкретным настройкам и версиям, приведённым в [отчётах Kafka](../verification/README.md). Гарантии описаны в [контракте событийной обработки](../design/kafka-event-processing.md).

## Ресурсы и масштабирование

`requests` учитываются при планировании `Pod`, а `limits` ограничивают потребление ресурсов контейнером во время выполнения. Они не заменяют измерение фактической нагрузки.

При ограничении CPU приложение может испытывать throttling и увеличение задержки. Превышение лимита памяти может привести к `OOMKilled`. Для этих механизмов в проекте предусмотрены воспроизводимые опыты.

Масштабирование также разделено по назначению:

| Механизм | Что изменяет | Ограничение |
|---|---|---|
| HPA | Число реплик приложения по метрикам ресурсов. | Не увеличивает ёмкость PostgreSQL и других зависимостей. |
| KEDA | Число реплик обработчика по отставанию потребителей Kafka. | Не гарантирует рост пропускной способности при ограничениях брокера и базы данных. |

При увеличении числа реплик нужно учитывать суммарное число соединений с PostgreSQL, параллельную обработку и нагрузку на Kafka. Эксперимент KEDA выполнялся как отдельный профиль; базовое развёртывание использует фиксированное число обработчиков.

Результаты: [CPU throttling](../verification/cpu-throttling.md), [OOMKilled](../verification/oomkilled.md), [HPA](../verification/hpa-autoscaling.md), [KEDA](../verification/keda.md).

## Сеть и политики доступа

Диагностика сетевого пути проводится последовательно: сначала проверяются сам процесс и `Pod`, затем выбор конечных точек через `Service`, разрешение имени DNS, сетевые политики и входная маршрутизация.

```text
процесс и порт → Pod → Service и EndpointSlice → DNS
→ разрешение трафика политиками → Gateway / Ingress
```

Такая последовательность служит планом диагностики, а не то что запрос проходит через компоненты именно в таком физическом порядке.

Отдельный сетевой кластер с Cilium используется для проверки действия `NetworkPolicy`. Проверки DNS, `Service`, Gateway и правил доступа имеют собственные [отчёты](../verification/README.md).

## Наблюдаемость

Приложение, сервис публикации и обработчик предоставляют метрики и диагностические события. Система наблюдаемости объединяет:

- метрики Prometheus, панели Grafana и оповещения Alertmanager;
- журналы, собираемые Alloy и хранимые в Loki;
- трассировки, передаваемые через OpenTelemetry Collector в Tempo.

Готовность приложения не зависит от доступности этой системы. Если сборщик или хранилище недоступны, часть диагностических данных может быть утрачена. Поэтому успешная обработка задания и полнота его трассировки проверяются отдельно.

Результаты включают наблюдение за восстановлением после отказа Collector, сквозные трассировки и циклы оповещений см. [архитектуру наблюдаемости](../design/observability-architecture.md) и [результаты проверок](../verification/README.md).
