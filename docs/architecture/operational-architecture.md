# Эксплуатационная архитектура

**Состояние: Current для реализованных механизмов этапов 1–8 в границах профильных verification-отчётов. Уровень узлов и самостоятельно управляемого кластера остаётся Target.**

## Развёртывание

Текущий исполняемый путь:

```text
исходный код
→ контейнерный образ
→ загрузка образа в kind
→ Namespace с ограничениями безопасности
→ Helm release
→ Deployment и Service
→ проверка готовности
→ внутрикластерная минимальная проверка доступности
```

Helm chart является источником описания ресурсов приложения. Значения образа передаются при установке и обновлении release; `Namespace` готовится отдельно. Чистый прогон подтвердил установку и готовность новых реплик, но выявил ошибки HTTP-клиента во время завершения старых Pod.

После появления GitOps:

```text
изменение конфигурации в Git
→ reconciliation
→ новая желаемая версия
→ проверка развёртывания
```

`reconciliation` оставляется как термин GitOps, потому что обозначает конкретный непрерывный процесс сведения фактического и желаемого состояния.

## Путь обработки заданий

```text
API → PostgreSQL Outbox → Kafka → Worker → PostgreSQL
```

API сохраняет задание и outbox в одной SQL-транзакции. Publisher публикует событие, после broker ack отмечает outbox; worker сохраняет SQL-эффект до Kafka offset commit и распознаёт повторную доставку. Контракты — [Kafka и обработка заданий](../design/kafka-event-processing.md), [PostgreSQL и хранение](../design/postgresql-stateful-storage.md).

## Завершение процесса

При штатном удалении Pod подготовленный HTTP `preStop` даёт сетевому пути ограниченное время перестать выбирать завершающийся экземпляр, пока приложение ещё обслуживает запросы. Затем порядок внутри HTTP-приложения остаётся следующим:

```text
SIGTERM
→ приложение перестаёт считаться готовым к новой работе
→ уже принятые запросы получают ограниченное время на завершение
→ процесс завершается
```

Значение `terminationGracePeriodSeconds` должно быть согласовано с собственным сроком завершения приложения.

Задержка до `SIGTERM` добавлена после чистого прогона, в котором клиентские `503` были связаны с немедленным отказом старых процессов после сигнала. При одном повторном обновлении под заданной нагрузкой клиентских ошибок не было; это не гарантия для любого сетевого пути и профиля запросов. Прямой сигнал процессу не запускает hook.

Пометка Pod как завершающегося, изменение условий `EndpointSlice` и прекращение фактической маршрутизации через `Service` происходят в Kubernetes отдельно от обработки `SIGTERM` приложением. Их нельзя считать единым синхронным шагом: во время опыта фиксируются время каждого наблюдения, условия `ready`, `serving`, `terminating` и клиентские HTTP-ответы. Изменение `EndpointSlice` само по себе не доказывает, что каждый узел уже обновил сетевой путь.

## Обновление

Корректное обновление проверяется под постоянной нагрузкой. Успех команды `kubectl rollout status` недостаточен, если клиент в этот момент наблюдает ошибки.

Нужно различать состояние `Deployment`, готовность новых `Pod`, удаление старых конечных точек, клиентские ошибки и время завершения старых процессов.

Для опыта этапа 3 отдельный временный клиент обращается к `Service` и сохраняет показатели каждого запуска. Диагностический заголовок позволяет связать HTTP-ошибку с отвечавшим Pod; снимки состояния Pod и `EndpointSlice` имеют собственные отметки времени. Стратегия контроллера, завершение уже принятого HTTP-запроса и наблюдавшиеся ошибки клиента проверяются раздельно; описание конфигурации не заменяет результат выполнения.

## Ресурсы

Для Milestone 8 используются отдельные namespace и Helm releases наблюдаемости: Prometheus, Grafana, OpenTelemetry Collector, Tempo, Loki, Alloy и Alertmanager. Владение CRD, бюджет и доступ определены в [архитектуре наблюдаемости](../design/observability-architecture.md). [Метрики приложения](../verification/application-metrics.md), [зависимостей](../verification/dependency-metrics.md), [трассировка](../verification/application-tracing.md), [журналы](../verification/application-logging.md) и [оповещения](../verification/alerting.md) проверены отдельно. [Отказ Collector](../verification/collector-outage.md) подтвердил обработку задания при потере telemetry в условиях опыта; ограниченные очереди SDK не гарантируют сохранность всех spans. [Итоговая приёмка](../verification/grafana-dashboards.md#итоговая-приёмка-milestone-8) не является доказательством непрерывной доступности между снимками.

Requests участвуют в планировании. Limits ограничивают потребление ресурсов во время выполнения.

Для CPU ожидаемый симптом превышения ограничения — throttling и ухудшение задержки или пропускной способности. Для памяти возможен `OOMKilled`.

Числа в requests/limits сначала считаются лабораторной гипотезой. Они не называются промышленным подбором ресурсов без измерений.

## Масштабирование

HPA увеличивает число реплик приложения, но не увеличивает ёмкость зависимостей.

Для HPA по CPU в выделенном kind установлен отдельный Helm release Metrics Server в kube-system; прикладной /metrics не является источником resource metrics. Chart приложения не владеет компонентом кластера. [Metrics API](../verification/metrics-server.md) и [масштабирование HPA](../verification/hpa-autoscaling.md) имеют Passed в своих границах. Предварительные неполные прогоны сохранены в отчётах.

В chart приложения реализован профиль HPA: в обычном режиме Helm задаёт Deployment.spec.replicas, а при включённом HPA поле опущено и контроллер меняет подресурс scale. Полный временной ряд и клиентские наблюдения принадлежат [отчёту HPA](../verification/hpa-autoscaling.md), а не описанию архитектуры.

Перед увеличением количества реплик необходимо учитывать:

```text
число реплик × пул соединений одной реплики
число реплик × внутренний параллелизм
число worker × скорость потребления очереди
```

## Доступность

`PodDisruptionBudget` ограничивает добровольные прерывания работы и не защищает от внезапной потери узла.

Anti-affinity и topology spread используются только вместе со сценарием, в котором распределение реплик имеет наблюдаемый смысл.

## Сеть

Диагностика выполняется по слоям:

```text
процесс слушает порт
→ Pod имеет адрес
→ Service выбирает нужные Pod
→ EndpointSlice содержит готовые конечные точки
→ DNS разрешает имя
→ NetworkPolicy разрешает путь
→ Gateway/Ingress направляет внешний трафик
```

Для проверки `NetworkPolicy` создан отдельный кластер с Cilium: штатный `kindnet` не подтверждает применение этих правил. Предварительный опыт подтвердил базовый путь Pod → DNS → `Service` → API до добавления политик; границы результата записаны в [`../verification/service-dns-diagnostics.md`](../verification/service-dns-diagnostics.md). Применение политики и локальный путь через Gateway подтверждены отдельными опытами в их [отчётах](../verification/README.md); исходный кластер с прежними результатами не изменялся.

## Target: уровень узлов и кластера

После появления самостоятельно управляемого кластера из нескольких узлов добавляются `drain`, `uncordon`, внезапная потеря узла, обновление `kubeadm` и ограниченные эксперименты с компонентами `control plane`.

Эти сценарии не блокируют этапы уровня приложения.
