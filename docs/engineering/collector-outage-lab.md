# Отсутствие Collector при работающем приложении

Контракт — [прикладная трассировка](../design/application-tracing.md), результат — [отчёт](../verification/collector-outage.md). Опыт выполняет владелец в основном kind/Kubernetes 1.34. Останавливается настоящий Collector, прежний опыт с неверным endpoint не заменяет эту проверку. Отказ exporters метрик этим опытом не проверяется.

## Исходные условия и граница

API/publisher/worker используют прежние записанные образы с tracing profile и штатным внутренним endpoint; worker fixed=1, управляемые отказы сняты, pending/lag=0. Collector Deployment имеет одну реплику, им управляет Helm без внешнего автоматического восстановления replicas. Tempo, Loki и Prometheus остаются доступны. API port-forward 18081 держать в отдельном окне. Новые образы, миграции и переустановка стенда не требуются.

До отказа сохранить HEAD, состояние tracing, образы/UID/счётчики перезапусков приложения и состояние группы. Выполнить одно обычное задание и application-trace-read. Не создавать другие задания параллельно: команды используют последний locator.

Taskfile владеет остановкой и восстановлением Collector. collector-stop требует исходного replicas=1, уменьшает до 0 и ждёт удаления Pod; collector-start возвращает 1 и ждёт rollout. Контекст и namespace этих команд фиксированы. При сбое ожидания после scale восстановление всё равно обязательно. Перед опытом посмотреть Deployment и EndpointSlice: при внешнем контроллере или нескольких репликах остановиться и уточнить конфигурацию.

## Наблюдение отказа

В одном PowerShell try/finally вызвать collector-stop, проверить replicas=0 и отсутствие готовых endpoints Service lab-otel-collector. Поставить одно job-enqueue, сохранить его job/event/trace ID, дождаться завершения. Записать job-status, outbox-status, worker-group-status, logging-query и журналы трёх процессов с tracing_export_failed. Держать отказ около 90 секунд, чтобы экспортёр успел сообщить ошибку; это интервал наблюдения, не гарантия полного сброса очереди SDK.

Ожидаются HTTP 202 → succeeded, effects=1, outbox_rows=1, pending/lag=0, готовность всех трёх процессов и прежние UID/restarts. Проверить /livez и /readyz напрямую через работающий API forward. Приложение сохраняет контекст задания даже при недоступном приёмнике. Отсутствие ответа Tempo само по себе не доказывает отказ; необходимы состояние Collector/endpoints и ошибки SDK. Отсутствующий target Collector не равен числу 0 и не означает отказ API. Общую проверку всех targets во время остановки не использовать как критерий успеха приложения.

## Восстановление

В finally вызвать collector-start и проверить код завершения. После восстановления сохранить tracing-status, endpoints и метрики. Создать новое задание, записать его ID отдельно от задания периода отказа, проверить succeeded/effects=1/lag=0 и application-trace-read. Новая связанная трассировка доказывает возобновление доставки. Частичная или поздняя доставка spans задания периода отказа допустима, но гарантированная доставка накопленных spans не заявляется: очередь SDK ограничена и не является долговечным хранилищем.

Повторить targets/application-metrics-verify/dependency-metrics-verify/smoke, сравнить UID/restarts приложения до и после. Сохранить каталог доказательств и только затем удалить диагностические Pod через worker-diagnostics-cleanup. После любой ошибки вернуть Collector штатной командой collector-start; не удалять Helm releases, PVC, topics, offsets или журналы.
