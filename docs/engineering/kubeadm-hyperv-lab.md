# Подготовка кластера Kubernetes на Hyper-V с помощью `kubeadm`

**Состояние:** `Prepared`. Описаны подготовка, установка, проверка и удаление отдельной лабораторной среды. Фактическое создание кластера, проверка отказа виртуальной машины и его удаление пока не подтверждены. **Создание и удаление ресурсов выполняются только после отдельного разрешения.**

## Назначение и ограничения

Процедура предназначена для Windows 11 Pro с Hyper-V и трёх виртуальных машин Ubuntu Server 24.04 LTS: одного управляющего узла и двух рабочих. В отличие от [многонодового `kind`](multi-node-kubernetes-lab.md), машины имеют отдельные виртуальные диски и собственные гостевые ОС. Однако они используют один физический хост: отказ хоста не покрывается лабораторной схемой.

План установки и фактическая приёмка — разные этапы. Если проверка предварительных условий не пройдена, не создавайте коммутатор, виртуальные машины или диски.

## 1. Предварительная проверка (без изменений)

Запустите PowerShell с правами, достаточными для чтения конфигурации Hyper-V, и выполните:

```powershell
Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All
Get-CimInstance Win32_Processor
Get-VMHost
Get-Volume
Get-CimInstance Win32_OperatingSystem
Get-NetAdapter
Get-VMSwitch
Get-VM
```

Зафиксируйте версию Windows, состояние Hyper-V, поддержку аппаратной виртуализации, число доступных логических процессоров, объём свободной оперативной памяти и дискового пространства. Проверьте существующие имена VM, коммутаторы и сети, чтобы исключить конфликты. Если Hyper-V отключён или ресурсов недостаточно, завершите процедуру на этом этапе: включение компонента и изменение настроек компьютера не относятся к предварительной проверке.

## 2. План изолированной среды

Выберите уникальный префикс, например `kal10b-<id>`, и каталог, предназначенный только для этого стенда. До создания ресурсов подготовьте инвентарную таблицу с запланированными именами VM, коммутатором, путями виртуальных дисков, адресами и подсетями.

| Ресурс | Виртуальные CPU | Оперативная память | Диск |
|---|---:|---:|---:|
| `<prefix>-cp` | 2 | 4 ГиБ | 30 ГиБ |
| `<prefix>-w1` | 2 | 4 ГиБ | 35 ГиБ |
| `<prefix>-w2` | 2 | 4 ГиБ | 35 ГиБ |

Все три машины подключаются к отдельному приватному виртуальному коммутатору `<prefix>-net`. Заранее выберите непересекающиеся диапазоны адресов для VM, Pod и Service. Приватный коммутатор **не обеспечивает сам по себе** доступ к интернету или управление с хоста. Предусмотрите согласованный временный путь установки Ubuntu, пакетов и OCI-образов либо подготовьте их для автономной установки до отключения внешнего подключения.

Перед применением плана согласуйте конкретные версии Kubernetes и Calico, их совместимость и контрольные суммы скачанных пакетов или образов. Незаполненные идентификаторы в примерах ниже — не готовые значения для выполнения.

## 3. Создание виртуальных машин (требуется разрешение)

Перед каждой командой проверьте отсутствие существующих ресурсов с теми же именами и путями. Создайте только запланированный коммутатор:

```powershell
New-VMSwitch -Name <prefix>-net -SwitchType Private
```

Для каждой VM используйте параметры из инвентаря:

```powershell
New-VM -Generation 2 -Name <name> -MemoryStartupBytes 4GB -NewVHDPath <owned-path> -NewVHDSizeBytes <size> -SwitchName <prefix>-net
Set-VMProcessor -VMName <name> -Count 2
```

Здесь `<name>`, `<owned-path>`, `<size>` и `<prefix>` — заполнители. Для Ubuntu при включённом Secure Boot используйте шаблон `MicrosoftUEFICertificateAuthority`. Установите Ubuntu из проверенного ISO, назначьте каждой машине собственное имя и статический IP-адрес. После создания сохраните фактические VM ID, идентификатор коммутатора и абсолютные пути VHDX. Не переиспользуйте виртуальные диски других машин.

## 4. Настройка Linux и `kubeadm`

На **каждой** VM отключите swap, загрузите `overlay` и `br_netfilter`, закрепите их загрузку через `modules-load.d`, включите `net.ipv4.ip_forward` и `net.bridge.bridge-nf-call-iptables`. Настройте `containerd` как CRI с `SystemdCgroup=true` и перезапустите службу. Проверьте, что container runtime и kubelet используют совместимую конфигурацию cgroups.

Из `pkgs.k8s.io` установите одинаковые заранее согласованные и закреплённые версии `kubelet`, `kubeadm` и `kubectl`; после установки удерживайте версии пакетов от случайного обновления. Сохраните результаты команд проверки версий.

На `<prefix>-cp` выполните `kubeadm init` с адресом управляющего узла в приватной сети и Pod CIDR выбранного CNI. Установите совместимую закреплённую версию Calico. Два рабочих узла присоедините **только** к созданному стенду командой `kubeadm join`, выданной для этой установки.

Токен присоединения, сертификаты и `admin.conf` храните локально; не добавляйте их в Git или публичные отчёты. Используйте отдельный файл `kubeconfig` и каждый раз проверяйте текущий контекст перед командами изменения ресурсов.

## 5. Подтверждение результата

Приёмка включает фактические наблюдения, а не только успешное завершение установки:

1. Все три `Node` имеют состояние `Ready`; CoreDNS успешно развернут.
2. Контейнерный образ Go API доступен **из виртуальных машин**. Приложение установлено существующим `helm/lab-api` с двумя репликами.
3. Сохранены имена и UID Pod, назначенные узлы и успешный HTTP-ответ из отдельного Pod-клиента через `Service`.
4. При явно разрешённом эксперименте остановлена **одна собственная** рабочая VM. Зафиксированы изменение доступности узла, поведение Pod и HTTP, затем восстановление VM, `Ready` и доступности приложения.
5. Сохранены версии инструментов, проверенный Git SHA, фактические параметры среды и временные отметки. В отчёт не включены токены и закрытые ключи.

Две реплики и три VM сами по себе не доказывают непрерывную доступность при отказе. При отсутствии результатов статус остаётся `Prepared`.

## 6. Удаление стенда (отдельное разрешение)

Удаление необратимо для данных на виртуальных дисках. Перед выполнением сопоставьте **каждую** VM по имени и VM ID с инвентарём, проверьте абсолютные пути VHDX и убедитесь, что ни один диск не подключён к посторонней VM. При несовпадении любого идентификатора остановитесь.

Последовательность: штатно остановить только VM стенда, удалить их по подтверждённым идентификаторам, удалить **только перечисленные** VHDX в выделенном каталоге, затем удалить отдельный коммутатор по его ID после проверки, что другие подключения отсутствуют. Не удаляйте файлы по общему префиксу без пофайловой сверки.

Сохраните итоговый инвентарь и журнал удаления без конфиденциальных данных. Пока этапы создания, испытаний и удаления не выполнены и не документированы, соответствующие результаты нельзя отмечать как `Passed`.
