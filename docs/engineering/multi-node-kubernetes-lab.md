# Многонодовый стенд `kind`: запуск проверок

**Состояние:** `Prepared`. В репозитории есть конфигурация и автоматизированные сценарии этапа 10A, но результаты их фактического выполнения ещё не представлены. Перечень ожидаемых проверок — в [отчёте](../verification/multi-node-kubernetes.md), архитектурные ограничения — в [контракте](../design/multi-node-kubernetes.md).

## Назначение и границы

Сценарии проверяют размещение двух реплик Go API на двух рабочих узлах, ограничения планировщика, обслуживание и имитацию недоступности рабочего узла, а также применение сетевых политик. Каждый запуск создаёт **новый кластер** `kind` с одним управляющим и двумя рабочими узлами в отдельных контейнерах на **одном хосте**. Проверки PostgreSQL, Kafka и платформы наблюдаемости сюда не входят.

Сбой контейнерного узла на общем хосте не равнозначен отказу физического сервера. Даже успешное выполнение не докажет высокую доступность независимых машин.

## Предварительные условия

Для локального запуска необходимы Linux с доступным Docker Engine, `kind` 0.33.0, `kubectl` 1.35.9, Helm 3.17.3, `jq`, Bash и возможность собрать образ приложения. В CI используется Ubuntu 24.04 и закреплённый образ узла Kubernetes 1.34.0. Для сетевого опыта требуется доступ к манифестам Calico 3.33.0.

Перед началом:

1. Убедитесь, что Docker доступен, а хост располагает ресурсами для трёх узлов. Сценарий записывает фактические CPU и память в `runner.json`; их достаточность заранее не гарантируется.
2. Сохраните `git rev-parse HEAD` и `git status --short`. Для воспроизводимого отчёта используйте зафиксированную ревизию без незакоммиченных изменений.
3. Проверьте, что никакие важные данные не хранятся в будущих временных кластерах. Скрипт удаляет **только созданный им кластер**, но это всё равно операция удаления.

## Запуск в GitHub Actions

Откройте workflow **Multi-node Kubernetes** в GitHub Actions и запустите `workflow_dispatch`. Значение `all` выполняет по отдельности пять групп: `bootstrap`, `scheduler`, `maintenance`, `outage` и `network`. Можно выбрать одну группу. Для pull request в `dev` workflow также запускается при изменении определённых файлов приложения и конфигурации стенда.

Группы выполняются последовательно (`max-parallel: 1`) на отдельных runner; это не один непрерывный кластер. Сохраняйте run URL, SHA, статус каждой группы и загруженные артефакты. В Actions срок хранения артефактов составляет **14 дней**.

## Локальный запуск

Из корня репозитория:

```bash
export REVISION="$(git rev-parse HEAD)"
export IMAGE="lab-multinode-api:$REVISION"
docker build -f docker/api.Dockerfile --build-arg "REVISION=$REVISION" -t "$IMAGE" .
GROUP=bootstrap bash scripts/ci-multinode.sh
```

Чтобы проверить другую группу, укажите соответствующее значение `GROUP`. Скрипт требует `IMAGE` и `REVISION`, самостоятельно создаёт уникальное имя `lab-mn-*`, использует временный `KUBECONFIG`, загружает собранный образ в кластер и устанавливает Helm release `multinode-api` в namespace `multinode`. Не задавайте имя действующего кластера вручную.

## Сценарии и ожидаемые результаты

| Группа | Проверяемое свойство |
|---|---|
| `bootstrap` | Три узла `Ready`, две готовые реплики на разных рабочих узлах, HTTP через `Service` и совпадение `/version.revision` с `REVISION`. |
| `scheduler` | `nodeSelector`, обязательное и предпочтительное `nodeAffinity`, `Pending` при несовместимом условии, восстановление после изменения метки, `NoSchedule` и разрешающее исключение `toleration`. |
| `maintenance` | `cordon` и `uncordon`, запрет выселения при строгом `PodDisruptionBudget`, разрешённое выселение после изменения бюджета, `drain`, готовность двух реплик и HTTP после перемещения. |
| `outage` | Остановка **своего** контейнера рабочего узла, переход узла в `Ready=Unknown`, замена реплики с другим UID, доступность HTTP после восстановления и возврат узла в `Ready`. |
| `network` | Отдельный кластер с Calico: доступность до политики, запрет подключения к `ClusterIP`, разрешение выбранному клиенту, запрет другому и возврат исходного доступа. Проверка DNS выполняется отдельно. |

Профиль размещения использует `topologySpreadConstraints` с `ScheduleAnyway`. Это **предпочтение**, а не жёсткое требование размещения на разных узлах; сценарий `bootstrap` дополнительно проверяет фактическое распределение.

Во время `maintenance` HTTP измеряется выборочно. Успешный ответ не доказывает отсутствия кратковременных ошибок между запросами. Для `outage` учитывайте штатное ожидание Kubernetes до удаления Pod недоступного узла; немедленное восстановление не ожидается.

## Результаты и диагностика

Каждый сценарий сохраняет данные в `.cache/multinode/evidence/<cluster>/`, в том числе `run.json`, `runner.json`, `kubernetes.json`, снимки Pod/Node, события, ответы HTTP и `scenario-status.json`. `cleanup.json` сообщает, удалось ли удалить временный кластер. При локальном повторе сначала сохраните прежний каталог доказательств: новые запуски используют другое имя, но вручную удалять незнакомые артефакты не следует.

При ошибке установите, на каком шаге произошёл отказ: создание кластера, запуск CNI, планирование Pod, готовность приложения, сетевой доступ или восстановление узла. Сохраните фактическую ошибку и артефакты. `Ready` без HTTP-ответа не доказывает исправность `Service`, а ошибка сетевого запроса без проверки DNS не доказывает срабатывание `NetworkPolicy`.

## Очистка и ограничения

При штатном завершении скрипт собирает последние наблюдения, удаляет собственный кластер и записывает результат очистки. Если выполнение было прервано, откройте **точный** `run.json`, проверьте имя и принадлежность кластера и только после этого выполните:

```bash
kind delete cluster --name <имя-кластера-из-run.json>
```

Угловые скобки обозначают значение, которое нужно подставить; не копируйте команду без проверки. Не удаляйте общий или чужой кластер. После очистки сопоставьте `cleanup.json`, возвращённый код сценария и содержимое артефактов.

**Критерий `Passed`:** успешный фактический запуск выбранной группы с её доказательствами, привязанными к точной ревизии и среде. Наличие скрипта, workflow или конфигурации само по себе сохраняет статус `Prepared`.
