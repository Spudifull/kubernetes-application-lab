# Архитектурные решения

В этом разделе записано, **почему проект устроен именно так**. Каждый ADR фиксирует выбранный подход, рассмотренные альтернативы и последствия решения. Текущие настройки и порядок запуска описаны в [проектных контрактах](../design/README.md) и [инженерных инструкциях](../engineering/README.md).

| Решение | Зачем оно принято |
|---|---|
| [ADR-0001. Отдельный Kubernetes-стенд](0001-separate-deployment-lab.md) | Изучать эксплуатацию Kubernetes, не усложняя продуктовый проект. |
| [ADR-0002. Разделение управления инфраструктурой и приложением](0002-application-delivery-boundaries.md) | Не допускать конкурирующего управления одними ресурсами. |
| [ADR-0003. `kind` и отдельный кластер на `kubeadm`](0003-dual-cluster-model.md) | Разделить быстрые опыты с приложением и изучение инфраструктуры узлов. |
| [ADR-0004. Проверка через реальные сценарии](0004-failure-scenarios-as-verification.md) | Подтверждать поведение системы, а не только корректность конфигурации. |

Все четыре решения имеют статус `Accepted`. Этот статус означает, что **решение принято**. Фактические результаты находятся в [отчётах о проверках](../verification/README.md).

## Как оформлять новые ADR

Новая запись нужна, когда принятое архитектурное решение заметно влияет на устройство проекта или дальнейшую работу. В ней достаточно пяти частей:

1. **Контекст** — какая проблема возникла.
2. **Решение** — что выбрано.
3. **Почему так** — какие альтернативы рассмотрены и почему они не подошли.
4. **Последствия** — что становится проще и какие ограничения появляются.
5. **Как это отражается в проекте** — где увидеть применение решения, со ссылкой на действующий документ.

В заголовке указываются номер и название, в начале — дата и статус. Допустимы `Accepted` и `Superseded`; при замене решения нужна ссылка на новый ADR. Не следует дублировать в ADR команды, версии инструментов или результаты экспериментов: для них есть отдельные документы.
