# ADR-0003: `kind` для приложения, `kubeadm` для инфраструктуры узлов

**Статус:** `Accepted`  
**Дата:** 2026-10-04

## Контекст

Для проверки `Pod`, `Deployment`, `Service`, Helm и обновлений приложения нужен кластер, который можно быстро создавать и удалять.

## Решение

Использовать два типа лабораторной среды:

- **`kind`** — для основной разработки, автоматизированных проверок и большинства сценариев уровня приложения.
- **Кластер на `kubeadm` с отдельными виртуальными машинами** — для изучения подготовки узлов, сетевой инфраструктуры, установки Kubernetes и обслуживания кластера.

Для обоих типов среды по возможности используется один Helm chart приложения. Различия задаются конфигурацией окружения.

## Почему так

Начать сразу с `kubeadm` означало бы тратить время на подготовку виртуальных машин даже при проверке простого HTTP-маршрута. Использовать только `kind` — значит не изучить инфраструктуру независимых узлов и её жизненный цикл.

Два типа стендов разделяют эти задачи.

## Последствия

Опыты с приложением не зависят от готовности виртуальных машин. Когда требуется изучить работу узлов, используется отдельная среда без изменения базовой модели поставки.

При этом **несколько узлов `kind` на одном хосте не равнозначны нескольким независимым машинам**. Результаты одного стенда нельзя автоматически переносить на другой. Решение использовать `kubeadm` само по себе не означает, что его установка и сценарии отказов уже проверены.
