# ADR-0004: Проверять поведение системы через сценарии отказов

**Статус:** `Accepted`  
**Дата:** 2026-10-04

## Контекст

Корректный Kubernetes-манифест ещё не означает, что приложение работает так, как ожидается. Например, `readinessProbe` может быть настроена правильно по синтаксису, но не исключать неисправный `Pod` из обработки запросов.

## Решение

Подтверждать важные эксплуатационные свойства **воспроизводимыми сценариями**, а не только проверкой конфигурации.

Каждый сценарий должен отвечать на четыре вопроса:

1. **Что проверяем?** Конкретное ожидаемое поведение.
2. **Как создаём условие проверки?** Нагрузка, обновление, отказ компонента или изменение конфигурации.
3. **Что наблюдаем?** Состояние Kubernetes, ответы клиента, метрики, журналы либо данные приложения — в зависимости от проверяемого свойства.
4. **Как восстанавливаем стенд?** Явные действия и признаки возвращения к рабочему состоянию.

## Почему так

Статическая проверка и `helm template` позволяют заранее найти ошибки в конфигурации. Но они не показывают реальное поведение приложения. Скриншот панели без условий опыта и исходных данных тоже не даёт достаточного объяснения результата.

Совместное использование статических и сценарных проверок позволяет отделить корректность описания ресурсов от работоспособности системы.

## Последствия

На подготовку опытов и сохранение результатов требуется больше времени. Зато можно проверить не только наличие механизма, но и его действие: например, сохранение записи после замены Pod, обработку повторной доставки или завершение принятого запроса при обновлении.

Если сценарий только подготовлен, нельзя считать свойство подтверждённым. Неудачные попытки и ограничения наблюдения тоже остаются частью результата.
