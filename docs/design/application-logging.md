# Централизованные журналы приложения

API, publisher и worker пишут структурированные события в stdout. Alloy читает журналы их Pod через Kubernetes API и отправляет записи в Loki. Grafana позволяет найти события по идентификатору задания, а по trace ID перейти к соответствующей трассировке в Tempo.

**Состояние:** `Current`. Сбор и поиск событий проверены в [лабораторном опыте](../verification/application-logging.md).


## Источники журналов и права доступа

Компонент [`loki.source.kubernetes`](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.kubernetes/) получает через Kubernetes API журналы Pod `lab-api`, `lab-publisher` и `lab-worker` в пространстве имён `kubernetes-application-lab`.

Хотя такое решение не требует доступа к файлам узла, `hostPath`, `hostNetwork`, привилегированных контейнеров или `DaemonSet`, есть и обратная сторона — дополнительная нагрузка на Kubernetes API/kubelet по сравнению с чтением файлов непосредственно с узла.

Alloy использует отдельный `ServiceAccount` и роль в пространстве имён приложения. Разрешены `get`, `list`, `watch` для `pods` и `get` для `pods/log`; не разрешены чтение `Secret`, выполнение команд в контейнере, доступ к узлам или изменение ресурсов. Для обращений к Kubernetes API Alloy получает проецируемый токен сервисной учётной записи.

**Важная граница:** роль позволяет читать журналы всех Pod указанного пространства имён, отбор трёх приложений выполняется конфигурацией Alloy и **не является ограничением RBAC**, Loki и сами процессы API/publisher/worker не получают дополнительных токенов для сбора журналов.

## Состав и индексация записей

Приложение продолжает формировать структурированные журналы через Go `slog`: время UTC, `service`, `event` и необходимые поля контекста. Полные сообщения Kafka, SQL-запросы с параметрами, пароли и секреты не должны появляться в записях.

В индекс Loki разрешены только метки `namespace`, `service`, `pod` и `container`. Идентификаторы `job_id`, `event_id`, `trace_id`, `span_id` и ID запросов остаются полями исходного JSON. Сделано так, чтобы не создавался отдельный индексный ряд на каждое задание или событие.

Поиск конкретного задания выполняется **по содержимому журнала**; поиск по произвольно добавленным меткам запрещён. Метаданные обнаружения Pod необходимы для Kubernetes API и удаляются после обработки. Диагностическая CLI-команда проверяет ответ Loki на появление неожиданных индексных меток.

Прикладные журналы, метрики и трассировки дополняют друг друга; событие `worker_effect_committed` в Loki требует независимого подтверждения SQL-результата; событие `worker_offset_committed` — проверки фактического смещения группы Kafka.

## Хранение и ограничения ресурсов

Loki работает одним процессом (`-target=all`) с TSDB v13, файловым хранилищем и коэффициентом репликации `1`. Доступен только по внутреннему `ClusterIP` на порту `3100`.

| Параметр Loki | Значение |
|---|---|
| PVC | `data-lab-loki-0` |
| Объём | `2Gi` |
| StorageClass | `standard` |
| Режим доступа | `ReadWriteOnce` |
| Срок хранения | `24h` |
| Отсрочка удаления компактором | Ещё `2h` |

WAL размещается на том же PVC. Очистка по сроку хранения выполняется не мгновенно. Значения ограничения скорости приёма, числа потоков, размера строк и параметров запросов выбраны для небольших лабораторных заданий.

PVC сохраняется при удалении `StatefulSet` и уменьшении числа реплик, однако выставлен флаг `reclaimPolicy: Delete` у `StorageClass`, чтобы при удалении самого PVC удалялись и данные.

| Компонент | CPU: запрос / лимит | Память: запрос / лимит |
|---|---|---|
| Loki | `100m` / `500m` | `512Mi` / `1Gi` |
| Alloy | `50m` / `300m` | `128Mi` / `256Mi` |

Предварительная проверка учитывает занятые ресурсы узла, доступную память хоста и запас `128Mi`. Итоговый дополнительный бюджет составляет `768Mi` запросов и `1408Mi` лимитов памяти. При повторной установке действующие Pod учитываются консервативно.

## Доставка, повторы и поведение при отказе

Alloy использует ограниченный `emptyDir`, пакеты отправки `256KiB`, тайм-аут `5s` и конечные повторные попытки в соответствии с компонентом [`loki.write`](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.write/). Позиции чтения Kubernetes API сохраняются в `emptyDir` и теряются при пересоздании Pod. Постоянная дисковая очередь не используется.

При отказе Loki, длительной недоступности сети или пересоздании Alloy возможны **потери или повторное чтение строк**. Сборщик не участвует в транзакции приложения; гарантия доставки журналов ровно один раз отсутствует. Готовность Alloy подтверждает состояние самого сборщика.

`NetworkPolicy` описывают необходимые соединения: Alloy → DNS/Kubernetes API/Loki, Grafana/Prometheus → Loki, Prometheus → Alloy. Для обращения к Kubernetes API допускаются TCP `443`/`6443` из-за преобразования адресов `Service`.

## Проверка и Grafana

`logging-render` формирует манифесты для изучения без изменения кластера. `logging-install` перед установкой проверяет пространство имён, `StorageClass`, соответствие существующих Helm releases, наличие необходимых CRD, ресурсы и результат server-side dry-run. Устанавливается только `lab-logging`; приложение, миграции и Kafka при этом не пересоздаются. При неуспехе ресурсы и диагностические данные сохраняются.

Отдельные `PodMonitor` позволяют наблюдать процессы сбора журналов, не смешивая их метрики с метриками самого приложения.

`logging-query` принимает UUID или заранее сохранённый идентификатор задания, читает данные за последние `30` минут и ограничивает ответ `500` строками через Kubernetes API proxy. Достижение лимита трактуется как неполный результат, а не как успешная проверка; отсутствие строк тоже не считается подтверждением доставки.

`logging-verify` проверяет наличие и согласованность событий:

- API — `job_accepted`;
- publisher — `outbox_broker_ack`;
- worker — `worker_received`, `worker_effect_committed`, `worker_offset_committed`.

Также сверяются названия сервисов, общий `trace_id` и совпадение `event_id` publisher/worker. Для этой проверки требуется диагностический профиль трассировки: при отключённом SDK `trace_id` отсутствует. `logging-retry-verify` дополнительно проверяет два различимых события `worker_retry_scheduled`.

В Grafana Loki добавлен как источник данных с UID `loki`. Поле `TraceID` позволяет перейти из результатов Loki в Tempo по идентификатору трассировки. Если после обновления Grafana изменился её Pod, старый `port-forward` необходимо создать заново.

## Граница ответственности

Loki не участвует в транзакции задания. Журнал события `worker_effect_committed` помогает найти нужную операцию, но фактический SQL-эффект и подтверждённое Kafka-смещение необходимо проверять независимо. При длительной недоступности Loki или перезапуске Alloy часть записей может потеряться либо быть прочитана повторно. Инструкция запуска — [application-logging-lab](../engineering/application-logging-lab.md).
