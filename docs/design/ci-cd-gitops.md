# Контракт CI/CD и GitOps

Состояние: Current для лабораторной цепочки stateless API feature → dev → main и одного отдельного GitOps kind с двумя namespaces. [CI](../verification/evidence-restoration-ci.md), [runtime, promotion и ограничения](../verification/gitops-development.md).

Обычные PR получают `contents: read`; jobs чтения собственных CI artifacts дополнительно `actions: read`. Они не используют `pull_request_target`, registry login или credentials действующих кластеров. Быстрые Go/Helm/evidence и container/kind — отдельные jobs одного `ci.yml`, публикация вынесена в reusable workflow. Actions закреплены полными SHA, tools — версиями. Имена required checks сохранены.

Поставка связывает Git SHA → проверенный image digest → Helm desired state → Pod imageID → `/version`. Публикация GHCR выполняется после проверок с минимальными permissions отдельного job. PR из fork не получает право публикации. Локальные Helm-профили `pullPolicy: Never` сохраняют своё назначение.

Argo CD должен работать в отдельном kind-кластере, управлять только выделенным приложением и не менять основной PostgreSQL/Kafka/PVC. Git-driven rollout, drift/self-heal и неисправный rollout с восстановлением требуют фактических наблюдений. При auto-sync восстановление выполняется через возврат desired state в Git. Подготовленные конфигурации не считаются доказательством этих свойств.

Passed требует сохранённых Git SHA, workflow run ID/URL, digest, версий Kubernetes/Argo CD, наблюдений Service HTTP и ограничений. Для лабораторной stateless-цепочки эти результаты сохранены в verification; остальные свойства из её границ не выводятся.

## Ветки и продвижение

Изменения проходят `feature/*` или `codex/*` → PR в `dev` → Release PR в `main`. `dev` содержит интеграционные кандидаты, `main` — подтверждённую стабильную версию. Required checks обеих веток: `go`, `evidence`, `helm`; для dev после успешного PR №2 добавлены `container`, `kind`. Для main после первого успешного Release PR №7 добавлен `release-gate`. Он проверяет архивированный development runtime proof, trusted source CI/publishing runs, текущую registry identity и неизменность API build inputs. Это не новая live-проверка локального кластера. Подробные ограничения — в [verification](../verification/gitops-development.md).

Один опубликованный image digest сначала проверяется в development, затем переносится в stable без повторной сборки. `source_commit_sha` обозначает исходники сборки; `promotion_commit_sha` — commit, утвердивший выпуск. Gate должен сравнить влияющие на бинарный файл входы сборки (`cmd`, `internal`, `go.mod`, `go.sum`, Dockerfile и build arguments) с источником проверенного артефакта. Совпадение двух строк values не заменяет проверку фактического Pod imageID и `/version`.

## Окружения

Один отдельный GitOps kind-кластер, namespaces `lab-dev` и `lab-stable`. Независимы Deployment, Service, release, values, desired digest и Argo CD Application. Оба окружения развёрнуты на одном проверенном GHCR digest; равенство реальных Pod imageID и независимость UID ресурсов подтверждены. Development следует dev с self-heal после первой manual sync; stable следует main с manual sync. Namespaces создаются явно в выделенном кластере. AppProject разрешает только этот репозиторий, две destination namespace и namespaced Deployment/Service; cluster-scoped ресурсы, PVC и Secret не разрешены. Это логическое разделение workloads, не HA и не проверенная сетевая изоляция.

Первый sync обоих окружений ручной. Development auto-sync/self-heal включается только после первой runtime-проверки. Stable остаётся manual, без автоматического prune. Recovery возвращает известный рабочий Git desired state. Ветка не меняет destination. Успешный release, development failed rollout/recovery и drift/self-heal подтверждены отдельными [наблюдениями](../verification/gitops-development.md); отдельный отказ stable не проверялся.

## Контейнерная проверка

Jobs `container` и `kind` в `ci.yml` отделены от быстрых checks. Изменения только документации не создают kind-кластер. Buildx linux/amd64, govulncheck, Trivy и проверенный API archive сохраняют прежние назначения. Обычные PR не получают packages write; tag/push использует тот же archive без build. CI OCI manifest и registry Docker manifest могут отличаться; config ID и source identity сверяются отдельно.

Reusable `publish.yml` вызывается через `needs: [go, evidence, helm, container, kind]` только на push/dev текущего репозитория при `ENABLE_GHCR_PUBLISH=true`. Он получает source SHA и checked run ID, которые обязаны совпасть с GitHub metadata текущего запуска; Go `publish-context` проверяет это до загрузки archive. Failed/skipped prerequisite исключает публикацию. Выбор другого run и polling отсутствуют. Go `publish-check` сверяет source/non-root image; tag/push не выполняет build. `publish-receipt` сохраняет digest, config ID и оба run ID, promotion SHA до выпуска null. Новые checked/publish run IDs совпадают: это один CI run. Только publishing job получает packages write. Push runs не отменяются новым push во время возможной публикации; устаревшие PR runs отменяются. Reusable publishing путь проверен реальным success в новом [security-релизе](../verification/security-release.md): проверенный dev archive опубликован, принят в dev и продвинут тем же digest в stable. Флаг публикации отсутствует.

На PR/push main контейнерная сборка отключена: stable использует проверенный dev artifact, а не новый image с SHA merge commit. Быстрый CI обеих веток продолжает работать; готовность Release PR проверяет release-gate. Сам gate не заменяет фактическую stable runtime-приёмку после merge.

Один required job `container` последовательно проверяет API, publisher и worker: Buildx, govulncheck и Trivy для каждого. Изменение общих Go-исходников, любого Dockerfile или CI запускает весь набор; отказ любого компонента блокирует job. В kind передаётся только API archive. Отрицательная runtime-проверка требует реального `ProgressDeadlineExceeded` и Pod `ErrImageNeverPull`, затем успешного восстановления; отдельно проверяются отказ Service и Ready EndpointSlice. Диагностика включает Deployment/Pod, события и журналы приложения.

`release-gate.yml` запускает одну Go-команду `release-verify`. Offline `release-check` сохранён отдельно. Go проверяет same-repository dev → main по GitHub event, читает baseline через `git show` по точному base SHA, проверяет API inputs/runtime proof, runs/jobs и текущий GHCR. Исторические container/publish runs поддерживаются; новый кандидат из `ci.yml` требует go/evidence/helm/container/kind и успешный `publish / publish` того же run. Успешный CI с пропущенной публикацией не подходит.

Для нового кандидата Go сверяет config ID с исходным CI artifact до истечения retention: проверяет SHA-256 ZIP и единственный root `image.json`, не извлекая файлы на диск. Принятая main identity повторно используется только при совпадении source SHA, repository, digest, обоих run ID и всего registry receipt, включая неизвестные поля. Изменение любой части требует исходного artifact. Anonymous registry check сверяет hash тела manifest и config digest. HTTP/ZIP ограничены размером и временем, отмена сохраняется; bearer token снимается при redirect скачивания, ошибки не содержат ответов/токенов/signed URL. Архивная квитанция не означает свежий runtime или security scan. Первое продвижение нового кандидата после истечения retention требует нового проверенного кандидата.

Security gate интерпретирует JSON findings через `labctl govulncheck --file`: source/symbol protocol v1.0.0, config и SBOM обязательны. Called-symbol findings блокируют независимо от severity; module/package-only выводятся отдельно. Ошибка формата блокирует. Exit=0 JSON scanner сам по себе не является приёмкой. Raw JSON и summary сохраняются для API/publisher/worker и CLI. Проверка и границы нового security-кандидата — в [verification](../verification/security-release.md).
