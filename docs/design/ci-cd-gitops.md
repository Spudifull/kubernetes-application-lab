# CI/CD и GitOps

Поставка приложения связывает исходный код, проверенный контейнерный образ и реально запущенную версию. Образ сначала проходит проверки в CI, затем публикуется в GHCR. GitOps задаёт, какой digest должен работать в development и stable; продвижение между окружениями не пересобирает образ.

**Состояние:** `Current` для лабораторного выпуска stateless API. CI анализирует образы API, publisher и worker, но его сценарий в `kind` запускает только API. Проверки выпуска описаны в [отчётах](../verification/milestone9-completion.md) и [security-release](../verification/security-release.md).


## Путь изменения и разделение ответственности

```text
изменение исходников
→ PR: Go, доказательства, Helm, анализ контейнеров, kind
→ dev: проверенный кандидат и разрешённая публикация
→ GHCR: идентичность артефакта (digest и config ID)
→ Argo CD: проверка фактически запущенного образа в development
→ Release PR и release gate
→ main: перенос прежнего digest в stable
→ отдельная проверка stable
```

В рабочем процессе различаются **исходная ревизия сборки** (`source_commit_sha`), **ревизия утверждения выпуска** (`promotion_commit_sha`), digest опубликованного образа, его config ID, версия в `/version` и фактический `Pod imageID`. Они отвечают на разные вопросы и не подменяют друг друга.

Для нового выпуска требуется связать Git SHA с результатами CI, затем с опубликованным образом, декларативной конфигурацией и запущенным Pod. Равенство строк в двух файлах Helm values не доказывает, что оба кластера используют именно этот образ.

## Ветки и обязательные проверки

Рабочее изменение проходит через `feature/*` или `codex/*` и PR в `dev`. Отдельный Release PR переносит проверенный кандидат из `dev` в `main`. Ветка `dev` используется для интеграции и лабораторной проверки, `main` — для утверждённой стабильной конфигурации.

| Проверка | Назначение |
|---|---|
| `go` | Тесты Go, проверки гонок и статический анализ проекта |
| `evidence` | Проверка целостности архивов результатов и связанных автоматических условий |
| `helm` | Проверка и формирование Kubernetes YAML для поддерживаемых профилей |
| `container` | Последовательная сборка и анализ образов API, publisher и worker; неуспех любого компонента блокирует общий job |
| `kind` | Работающий API в временном кластере, отрицательные сценарии развёртывания и проверка восстановления |
| `release-gate` | Проверка происхождения выпуска, неизменности входов сборки и идентичности опубликованного образа перед переносом в `main` |

Имена обязательных проверок сохраняются: `go`, `evidence`, `helm` для основных веток, `container` и `kind` для `dev`, `release-gate` для Release PR в `main`. Подробности их включения зафиксированы в [проверке этапа 9](../verification/milestone9-completion.md). Изменения только документации не должны запускать тяжёлый контейнерный сценарий без необходимости.

Общий workflow `.github/workflows/ci.yml` содержит быстрые и контейнерные jobs. Проверки обычных PR используют `contents: read`, а чтение собственных артефактов CI дополнительно `actions: read`. Токены публикации и учётные данные работающих кластеров PR не получают. Не применяется `pull_request_target`. Внешние GitHub Actions закреплены по полным SHA, инструменты — по версиям.

## Сборка, анализ и проверка контейнеров

Для API, publisher и worker в одном обязательном контейнерном job последовательно выполняются Buildx, проверка зависимостей Go и анализ уязвимостей Trivy. При изменении общих Go-исходников, Dockerfile или конфигурации CI проверяется весь набор, а не только затронутый по названию процесс.

Временный `kind` получает **проверенный архив образа API**. Он не пересобирает его. Проверяются `Deployment`, готовность `EndpointSlice`, HTTP `/readyz` и `/version` через внутрикластерный Service, а также реальные отрицательные сценарии:

- заведомо недоступный образ приводит к `ProgressDeadlineExceeded` и `ErrImageNeverPull`;
- после возврата рабочего образа развёртывание снова становится готовым;
- отдельная ошибка настройки Service обнаруживается и устраняется;
- состояние `Pod`, `Deployment`, `EndpointSlice`, события и журналы сохраняются до удаления временного кластера.

Это проверка одного stateless API, а не эксплуатационная приёмка PostgreSQL, Kafka, publisher и worker под реальной нагрузкой. Клиентские HTTP-проверки не заменяют длительное нагрузочное испытание.

### Проверка уязвимостей

Сканирование Go выполняется в машиночитаемом формате. Команда `labctl govulncheck --file` интерпретирует JSON-протокол `v1.0.0`, требует метаданные конфигурации и SBOM и отклоняет неполные или повреждённые отчёты. Уязвимость, для которой найден вызываемый символ в соответствующем стеке вызовов, блокирует проверку независимо от заявленной серьёзности. Находки только на уровне модуля или пакета сохраняются отдельно и не приравниваются к доказанному вызову уязвимой функции.

Возврат кода `0` самим JSON-сканером недостаточен: решение принимает отдельная проверка содержимого результата. Для Trivy находки HIGH/CRITICAL по образам остаются блокирующими. Первичные JSON и сводки сохраняются, в том числе при отказе задания. Пример исправления OpenTelemetry `1.44.0 → 1.45.0` и реальные результаты выпуска описаны в [отчёте безопасности](../verification/security-release.md). Наличие предупреждений только о требуемых зависимостях не выдаётся за полное отсутствие известных уязвимостей.

## Публикация образа в GHCR

Публикация отделена в повторно используемый workflow `.github/workflows/publish.yml`. Он вызывается из `ci.yml` для разрешённого push в `dev` текущего репозитория только после успешных `go`, `evidence`, `helm`, `container`, `kind` и при явном `ENABLE_GHCR_PUBLISH=true`.

До загрузки образа `publish-context` сверяет исходный SHA, событие, репозиторий и идентификатор текущего успешного CI-запуска с GitHub metadata. Нельзя выбрать произвольный старый run, подождать чужой запуск или считать пропущенное задание успешным. `publish-check` проверяет свойства архива и идентичность образа. Операция tag/push использует уже проверенный архив, **без повторной сборки**. Только задание публикации получает `packages: write`.

`publish-receipt` фиксирует digest, config ID, SHA исходников и идентификаторы проверочного и публикующего запусков. Для новой цепочки они относятся к одному CI run. До утверждения выпуска `promotion_commit_sha` остаётся `null`. Публикация не должна отменяться следующим push посреди работы; повторяющиеся PR-проверки могут отменяться по отдельной политике.

Реальная повторно используемая публикация пройдена для source `348373135c844c06a3b53fa3d729d7ee1df05348`. Её результат позднее проверен в development и перенесён в stable. Флаг публикации после завершения отключён. Действующая политика не предполагает публикацию образа из обычного PR или автоматическую пересборку при переносе в `main`.

## Окружения Argo CD

Для GitOps используется **отдельный** кластер `kind-kubernetes-application-lab-gitops`. Он не управляет PostgreSQL, Kafka, PVC и прочими объектами основных лабораторных кластеров. В нём определены два независимых пространства имён и приложения:

| Окружение | Ветка | Управление синхронизацией | Граница |
|---|---|---|---|
| `lab-dev` | `dev` | Первая синхронизация вручную, затем автоматическая с `selfHeal` | Проверка кандидата и восстановление желаемого состояния |
| `lab-stable` | `main` | Ручная синхронизация, без автоматического удаления ресурсов (`prune`) | Перенос утверждённого образа |

Каждое окружение имеет собственные `Deployment`, `Service`, Helm release, values и объект Argo CD `Application`. `AppProject` ограничивает допустимые репозитории, пространства имён и namespaced ресурсы. Доступ к cluster-scoped объектам, PVC и Secret через этот проект не предоставляется. Такое разделение не доказывает физическую отказоустойчивость или сетевую изоляцию между пространствами имён.

Для проверки недостаточно состояния `Synced/Healthy`: нужны точная Git-ревизия, фактический `Pod imageID`, вывод `/version` и HTTP-доступность. Управляемые опыты проверили изменение версии из Git, отклонение фактической конфигурации (`drift`) и `selfHeal`, неудачное обновление development и восстановление прежнего желаемого состояния. Отказ stable как самостоятельный сценарий не выполнялся.

При включённой автоматической синхронизации восстановление следует проводить возвращением согласованного **желаемого состояния Git**, а не неявным ручным изменением ресурсов. Успешное исправление `Deployment` не является доказательством сохранности состояния SQL/Kafka, которые не входят в эту лабораторную цепочку.

## Проверка перед Release PR

Workflow `.github/workflows/release-gate.yml` вызывает `labctl release-verify`. Эта проверка контролирует переход из `dev` в `main` внутри того же репозитория и сравнивает исходную ревизию, фактические результаты CI и опубликованный образ. Входы сборки API (`cmd/api`, `internal`, `go.mod`, `go.sum`, Dockerfile, `.dockerignore` и параметры сборки) не должны незаметно измениться относительно проверенного source.

Для нового кандидата необходимы успешные основные CI jobs, работающая публикация из того же запуска и доступный исходный контейнерный артефакт. Приёмка проверяет SHA-256 ZIP, единственный корневой `image.json`, config ID, идентичность registry manifest и фактическое состояние ранее проверенного development. Архив читается с ограничениями размера и времени, без распаковки произвольных путей на диск. Секреты и подписанные URL не выводятся в сообщения об ошибках; права GitHub и анонимные обращения к registry разграничены.

Повторное использование уже принятой в `main` идентичности допустимо лишь при полном совпадении исходного SHA, репозитория, digest, обоих run ID и registry receipt, включая дополнительные поля. При изменении какого-либо из этих значений нужен исходный артефакт нового выпуска. Если срок хранения исходного CI artifact истёк, нельзя выдавать архивную квитанцию за новую независимую проверку: требуется новый кандидат с действительными подтверждениями.

`release-gate` не выполняет новую проверку работающего GitOps-кластера вместо разработчика. После утверждения и переноса образа в stable требуется отдельное фактическое наблюдение.

## Границы подтверждённой поставки

В двух пространствах имён проверена работа одного digest API и соответствие `/version` и фактического `imageID`. Это не подтверждает новый запуск PostgreSQL, Kafka и наблюдаемости после обновления зависимостей и не означает отказоустойчивость отдельных физических кластеров. Инструкция — [ci-cd-gitops-lab](../engineering/ci-cd-gitops-lab.md); фактические наблюдения — [gitops-development](../verification/gitops-development.md).
