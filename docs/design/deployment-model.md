# Развёртывание приложения в Kubernetes

`kind` предоставляет воспроизводимую среду, Helm описывает ресурсы приложения, а Kubernetes поддерживает желаемое состояние Pod. Эта модель отделяет сборку контейнера от его установки, а готовность отдельного Pod — от доступности приложения через Service.

**Состояние:** `Current` для локального приложения и stateless API в GitOps. Многонодовые сценарии пока `Prepared`; соответствующие условия описаны [отдельно](multi-node-kubernetes.md).


## Границы ответственности

| Компонент | Назначение |
|---|---|
| `docker/api.Dockerfile` | Сборка исполняемого файла и конечного контейнерного образа. |
| `helm/lab-api/` | Описание `Deployment`, `Service` и необязательных ресурсов приложения. |
| `k8s/namespace.yaml` | Отдельная подготовка пространства имён и ограничений Pod Security. |
| `Taskfile.yml` | Команды сборки, установки, проверки и удаления локального стенда. |
| `cmd/labctl/` | Выполнение составных операций, проверка контекста Kubernetes и обработка диагностических данных. |
| `gitops/` и Argo CD | Описания окружений development и stable и согласование состояния выделенного GitOps-кластера с Git. |

Основной Helm chart не создаёт `Namespace` и не закрепляет его имя в шаблонах. После установки Helm управляет ресурсами приложения, а подготовка пространства имён выполняется отдельно. Это предотвращает конкуренцию между разными способами изменения одних и тех же ресурсов.

PostgreSQL, Kafka и система наблюдаемости устанавливаются независимо от основного приложения. Базовый профиль API не требует этих компонентов. Подробности находятся в [контракте PostgreSQL](postgresql-stateful-storage.md), [контракте Kafka](kafka-event-processing.md) и [архитектуре наблюдаемости](observability-architecture.md).

## Контейнерный образ

`docker/api.Dockerfile` собирает статический Go-бинарник в отдельной стадии. Конечный образ основан на `scratch`, содержит `/lab-api` и запускает процесс от UID/GID `65532`. Средства компиляции и командная оболочка в него не входят.

Для локального стенда `task image-build` создаёт образ и записывает ссылку на него в файл `.local-image-ref`, исключённый из Git. Тег соответствует полному идентификатору собранного образа без префикса `sha256:`. Команда `task deploy` читает эту ссылку, загружает образ в `kind` и передаёт параметры образа в Helm. Новая отличающаяся сборка приводит к изменению `Deployment.spec.template.spec.containers[].image`; повторная установка без пересборки использует прежний образ.

Значение `/version.revision` независимо от идентификатора образа: оно содержит ревизию исходного дерева, а при наличии незакоммиченных изменений — суффикс `-dirty`. Время сборки передаётся отдельно и не служит идентификатором исходного состояния.

В локальном профиле используется `imagePullPolicy: Never`, поскольку образ предварительно загружается на узел. В GitOps-профилях используется опубликованный образ GHCR, выбранный по digest. Эти способы получения образа не следует смешивать без явного изменения конфигурации.

## Локальный кластер и установка

`task cluster-up` создаёт выделенный одноузловой кластер `kind` или пропускает создание, если он уже доступен. Образ узла закреплён на Kubernetes `v1.34.0` по digest `sha256:7416a61b42b1662ca6ca89f02028ac133a309a2a30ba309614e8ec94d976dc5a`. Это зафиксированная лабораторная конфигурация, а не требование использовать наиболее новую версию Kubernetes.

Обычный путь установки:

```text
исходный код
→ сборка контейнерного образа
→ выделенный кластер kind
→ подготовка Namespace
→ загрузка образа на узел
→ helm upgrade --install
→ ожидание готовности
→ проверка HTTP через Service
```

`Taskfile.yml` предоставляет единый набор команд для поддерживаемых сред. Сложные действия выполняются через `cmd/labctl/` с явной проверкой контекста Kubernetes и пространства имён. PowerShell не является обязательным условием для базового запуска; фактические проверки переносимости и их ограничения задокументированы [отдельно](../verification/cross-platform-tooling.md).

`task deploy` не присваивает Helm существующие ресурсы, ранее созданные через `kubectl apply`. При переходе старого учебного окружения на Helm такие ресурсы необходимо удалить явно либо пересоздать **только выделенный лабораторный кластер**. Автоматического удаления неизвестных ресурсов нет.

Для проверки сетевого пути используется `task smoke`. Команда создаёт временный клиентский `Pod`, обращается к `http://lab-api.kubernetes-application-lab.svc/version` через DNS и `ClusterIP Service`, получает ответ API и выводит сведения об `EndpointSlice`. Клиентский `Pod` удаляется по завершении процедуры. Запрос через `task smoke-api-proxy` использует другой сетевой путь и не заменяет эту проверку.

`task undeploy` удаляет Helm release приложения, но сохраняет пространство имён и кластер. `task cluster-down` удаляет соответствующий кластер `kind`, включая находящиеся в нём данные; перед выполнением необходимо проверить его назначение. Эти команды не вызываются автоматически после проверки.

## Ресурсы основного приложения

В `helm/lab-api/` определены `Deployment` и `ClusterIP Service`; при включении отдельных профилей добавляются `HorizontalPodAutoscaler` и `HTTPRoute`. Шаблон `Deployment` также поддерживает необязательные `topologySpreadConstraints`, которые используются в подготовленном многонодовом профиле.

Для стандартного release имя ресурсов — `lab-api`. Метки выбора используют `app.kubernetes.io/name` и `app.kubernetes.io/instance`; они не зависят от версии образа или chart. Именованный `targetPort: http` соответствует порту контейнера `8080`. Имя `Pod` передаётся приложению через Downward API в `LAB_POD_NAME` и возвращается в заголовке `X-Lab-Pod`.

В обычном режиме Helm задаёт число реплик через `Deployment.spec.replicas`. По умолчанию используется одна реплика, поэтому при замене единственного `Pod` возможен краткий перерыв в обслуживании запросов.

`Chart.yaml.version` обозначает версию Helm chart, а `appVersion` — версию приложения. Изменение только контейнерного образа не требует обязательного изменения версии chart. Установка и обновление выполняются через `helm upgrade --install`; отдельный `kubectl rollout restart` в штатном пути не используется.

### Ограничения безопасности

Для приложения применяются следующие настройки:

- `runAsNonRoot: true`, UID/GID `65532`;
- `allowPrivilegeEscalation: false`;
- `readOnlyRootFilesystem: true`;
- удаление всех Linux capabilities;
- `seccompProfile: RuntimeDefault`;
- `automountServiceAccountToken: false`.

Приложение не обращается к Kubernetes API, поэтому токен ServiceAccount ему не нужен. Пространство имён локального стенда подготавливается с ограничениями Pod Security уровня `restricted`. Фактическое отклонение запрещённой конфигурации проверялось в [сценарии Pod Security Admission](../verification/pod-security-admission.md); наличие метки `enforce` само по себе не доказывает результат проверки.

## Проверки состояния и завершение Pod

| Механизм | Маршрут | Поведение |
|---|---|---|
| `startupProbe` | `/livez` | Ограниченное окно запуска: период 1 с, порог 10 неудач. |
| `livenessProbe` | `/livez` | После запуска проверяет состояние процесса; период 10 с, порог 3 неудач. |
| `readinessProbe` | `/readyz` | Определяет готовность к новой работе; период 2 с, порог 1 неудача. |
| HTTP `preStop` | `/_prestop` | Выдерживает три секунды перед сигналом завершения. |

`terminationGracePeriodSeconds` равен 20 секундам. При удалении `Pod` расчётный путь включает трёхсекундный `preStop`, трёхсекундное окно после `SIGTERM` и до десяти секунд на `http.Server.Shutdown` — всего до 16 секунд. Оставшееся время служит запасом и не гарантирует завершения любого запроса. Поскольку в конечном образе нет командной оболочки, используется HTTP-хук, а не `exec` с командой `sleep`.

Задержка перед сигналом введена после опыта, в котором клиент получил три ответа `503` от завершающихся экземпляров. В следующем чистом повторе под заданной нагрузкой все 1799 запросов завершились успешно. Проверка не доказывает отсутствие ошибок при других профилях нагрузки или конфигурациях сети. Подробности приведены в [отчёте об обновлении под нагрузкой](../verification/rolling-update-under-load.md) и [контракте приложения](application-runtime.md#завершение-процесса).

Смена готовности процесса, условия `EndpointSlice` и фактическое прекращение маршрутизации через `Service` происходят независимо. Для диагностики необходимо сопоставлять состояние `Pod`, `EndpointSlice` и ответы клиента, а не опираться только на результат `kubectl rollout status`.

## Профили обновления и масштабирования

### Обновление двух реплик

Профиль `values-rollout.yaml` включает две реплики, экспериментальный маршрут `/work` и параметры `maxSurge: 1`, `maxUnavailable: 0`. При штатном обновлении контроллер может временно создать третий `Pod`, сохраняя требуемое число доступных реплик.

Показатель доступности `Deployment` не равен фактическому отсутствию ошибок у HTTP-клиента. Поэтому сценарий использует временный клиент, который обращается к `Service` и сохраняет коды ответов, ошибки соединений и сведения об обслуживших запросы экземплярах. Обновление и откат проверены в отдельных [отчётах](../verification/rolling-update-under-load.md) и [сценарии неудачного развёртывания](../verification/failed-rollout-rollback.md).

### Автоматическое масштабирование HPA

Профиль `values-hpa.yaml` создаёт `autoscaling/v2 HorizontalPodAutoscaler` для того же `Deployment`: минимум две, максимум четыре реплики, целевое использование CPU — `60%` от запроса ресурсов.

В этом профиле приложение получает CPU request `100m`, limit `1000m`, memory request `32Mi`, limit `64Mi`. Экспериментальный маршрут `/cpu` включён. HPA сопоставляет измеренное потребление CPU именно с request, а не с limit.

При включении HPA шаблон `Deployment` опускает `spec.replicas`, чтобы контроллер мог управлять числом экземпляров. При переходе с фиксированного числа реплик возможно кратковременное применение значения по умолчанию; поэтому после `task deploy-hpa` требуется отдельно подтвердить наличие двух готовых экземпляров. Обратное переключение на `task deploy-rollout` удаляет HPA и возвращает статическое число реплик; во время измерения уменьшения масштаба этого делать нельзя.

Для опыта окно стабилизации уменьшения масштаба сокращено до 120 секунд. Это параметр испытания, а не обещание, что число реплик изменится ровно через две минуты. [Масштабирование HPA](../verification/hpa-autoscaling.md) проверено в указанной там среде.

Отдельное масштабирование обработчика по задержке потребления Kafka выполняется с помощью KEDA и описано в [контракте Kafka](kafka-event-processing.md); результаты приведены в [отчёте KEDA](../verification/keda.md). Увеличение числа обработчиков не увеличивает автоматически ёмкость PostgreSQL или брокера.

## Ресурсы и диагностические эксперименты

### Базовые ограничения

В обычном профиле установлены requests `25m` CPU и `32Mi` памяти, limits `250m` CPU и `64Mi` памяти. Это значения для воспроизводимого опыта, а не рекомендация по настройке промышленной системы.

### Ограничение CPU

Профили `values-cpu-high.yaml` и `values-cpu-low.yaml` задают одну реплику и одинаковые CPU request `100m`, memory request `32Mi` и memory limit `64Mi`. Отличается только CPU limit: `1000m` и `100m` соответственно.

Временный клиент создаёт одинаковую нагрузку, а приложение возвращает накопительные счётчики cgroup. Сравниваются приращения за каждый опыт в пределах одного контейнера; после смены профиля создаётся новый контейнер, поэтому сравнение абсолютных значений некорректно. [Отчёт по CPU throttling](../verification/cpu-throttling.md) фиксирует наблюдавшееся ограничение квоты и рост задержки.

### Завершение из-за нехватки памяти

Сценарий `OOMKilled` использует отдельный клиентский `Pod` из `scripts/kubernetes/oom-pod.yaml`, а не основной API. У него `restartPolicy: Never`, memory request `16Mi`, memory limit `64Mi`, `activeDeadlineSeconds: 90`.

Клиенту разрешено выделить не более `128Mi` и удерживать память не более 60 секунд. В проверенном опыте был выбран буфер `96Mi` с удержанием до 15 секунд. Результат `OOMKilled` относится к временному контейнеру; доступность основного приложения подтверждена отдельно. Этот опыт не доказывает механизм восстановления `Deployment` после нехватки памяти в API. См. [отчёт](../verification/oomkilled.md).

### Проверка планировщика

Временный `Pod` запрашивает CPU больше, чем `allocatable` единственного узла, на `1000m`. Ожидается состояние без назначенного узла и событие `FailedScheduling` с причиной нехватки CPU. Эксперимент не потребляет запрошенный объём вычислений и не изменяет `Deployment`. Повторный прогон и очистка зафиксированы в [отчёте о планировании](../verification/scheduling-capacity.md).

## Отдельный сетевой кластер

Для проверки сетевых политик используется второй одноузловой `kind` с `disableDefaultCNI: true` и Cilium `1.20.3`. Он отделён от основного стенда; установка Cilium в исходный кластер для этих опытов не требуется. Выбранная конфигурация соответствует Kubernetes `1.34`, использует штатный `kube-proxy` и не предполагает автоматического включения Gateway или service mesh.

В пространстве имён `kubernetes-application-lab-policy` применяются ограничения `restricted`. API устанавливается тем же Helm chart под отдельным именем release; для экспериментов создаются только временные клиенты и сетевые политики. Исследованные разрешающие и запрещающие правила, а также очистка ресурсов описаны в [отчёте NetworkPolicy](../verification/network-policy-isolation.md). Работающая конфигурация Cilium не доказывает применение этих правил без явной отрицательной проверки.

### Gateway и TLS

Для экспериментов с Gateway API установлен Envoy Gateway `v1.9.2` с Gateway API `v1.6.1`. Контроллер, `GatewayClass`, `Gateway`, `EnvoyProxy` и связанные объекты относятся к инфраструктуре кластера. Дополнительный `HTTPRoute` создаётся через необязательный профиль chart приложения.

Плоскость данных использует `ClusterIP`; доступ с хоста организован через `kubectl port-forward` на `127.0.0.1`. Проверяется имя `api.lab.test` и точный путь `/version`. Запросы с другим именем или путём должны отклоняться правилами маршрутизации, не попадая в API.

Для HTTPS создаётся отдельный лабораторный центр сертификации и сертификат сервера. Приватные ключи остаются в исключённом из Git каталоге `.local-gateway-certs/`; Kubernetes `Secret` создаётся явно в пространстве имён `Gateway`. Клиент проверяет тестовый сертификат с указанным CA. TLS завершается на Gateway, а не в Go API. Это не публично доверенный сертификат и не проверка отзыва. Результаты — в [отчёте Gateway](../verification/gateway-routing-tls.md).

### Разграничение доступа RBAC

В основном API остаётся `automountServiceAccountToken: false`. Отдельный `ServiceAccount/lab-rbac-reader` используется только в пространстве имён сетевых экспериментов. Его `Role` разрешает `get` одного `Pod/lab-rbac-client`, а `RoleBinding` связывает это разрешение с выделенным аккаунтом.

Временный клиент получает проецируемый токен для запросов к Kubernetes API, но не записывает его в журнал. Эти ресурсы не входят в основной Helm chart. Положительные и отрицательные проверки разрешений находятся в [отчёте RBAC](../verification/rbac-access-control.md).

## Данные и выпуск изменений

В базовом профиле API не хранит состояния. PostgreSQL подключается через отдельный Helm release и постоянный том; Kafka устанавливается отдельно. Контракт и порядок восстановления данных описаны в [PostgreSQL](postgresql-stateful-storage.md) и [Kafka](kafka-event-processing.md).

Публикация в GHCR и Argo CD не заменяют Helm как описание ресурсов: GitOps указывает версию желаемого состояния, Helm формирует ресурсы, Kubernetes запускает контейнеры. Подробнее — [CI/CD и GitOps](ci-cd-gitops.md). Фактические проверки `Deployment`, сети, ресурсов и обновлений перечислены в [каталоге](../verification/README.md).
