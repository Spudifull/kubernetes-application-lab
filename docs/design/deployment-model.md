# Модель поставки приложения

**Состояние: Current для описания ресурсов в Helm chart; обновление с HTTP `preStop` проверено под заданной нагрузкой на чистой ревизии. Это не общая гарантия непрерывной доступности.**

## Текущий путь поставки

`docker/api.Dockerfile` собирает статический бинарный файл в отдельной стадии с Go toolchain. Конечный образ основан на `scratch`, запускает `/lab-api` от UID/GID `65532` и не содержит Go toolchain или командную оболочку.

Локальная сборка создаёт образ с тегом, равным полному ID собранного образа без префикса `sha256:`. Ссылка сохраняется в игнорируемом Git файле `.local-image-ref`. `task deploy` загружает именно этот образ в `kind` и передаёт имя репозитория образа и тег в Helm. Следующая отличимая сборка меняет `spec.template.spec.containers[].image`; повторный `task deploy` без новой сборки использует прежнюю ссылку. Значение `/version.revision` отдельно отражает Git SHA с суффиксом `-dirty` для изменённого дерева.

`Taskfile.yml` остаётся публичным интерфейсом разработки. Повторяющаяся логика определения ревизии и записанного образа, а также сценарии с условиями и разбором Kubernetes JSON выполняются через `cmd/labctl/` на Go, без обязательного PowerShell. CLI принимает контекст и namespace явно; перед изменением Kubernetes проверяется текущий контекст. Это исполняемая реализация; выполненные профильные проверки и оставшиеся пробелы эквивалентности описаны в [отчёте о переносимости](../verification/cross-platform-tooling.md).

`task cluster-up` закрепляет node image `kindest/node:v1.34.0` по digest `sha256:7416a61b42b1662ca6ca89f02028ac133a309a2a30ba309614e8ec94d976dc5a`, опубликованному в release `kind` v0.30.0. Это версия воспроизводимой лабораторной среды, а не утверждение о последней версии Kubernetes.

Значение `imagePullPolicy: Never` ограничивает эту конфигурацию локальным стендом: узел использует загруженный образ и не получает его из реестра.

Имя Pod передаётся приложению через Downward API в `LAB_POD_NAME` и возвращается диагностическим заголовком `X-Lab-Pod`. Это не значение Helm values и не метка метрик.

Каталог `helm/lab-api/` определяет `Deployment` и `ClusterIP Service`, а в экспериментальном профиле также `HorizontalPodAutoscaler`. Helm release `lab-api` даёт ресурсам имя `lab-api`; для другого имени release имя каждого ресурса совпадает с ним. Стабильные поля `selector` используют `app.kubernetes.io/name` и `app.kubernetes.io/instance`; версия приложения и chart в них не входят.

Для Milestone 6 отдельный каталог `helm/lab-postgres/` и release `lab-postgres` владеют PostgreSQL StatefulSet, Service, ConfigMap и NetworkPolicy. Secret создаётся вне Helm; PVC создаётся через `volumeClaimTemplates` и удерживается при удалении StatefulSet. Основной chart имеет только необязательный профиль `values-db.yaml`; базовый `task deploy` не зависит от БД. Подробный контракт — [PostgreSQL и сохраняемое состояние](postgresql-stateful-storage.md). Поведение этого профиля пока не подтверждено кластерным прогоном.

`k8s/namespace.yaml` остаётся отдельной подготовкой среды и задаёт Pod Security Standards уровня `restricted`. Helm chart не создаёт `Namespace` и не фиксирует `metadata.namespace` в шаблонах. После установки Helm — единственный владелец `Deployment` и `Service`; `kubectl apply` управляет только `Namespace`. В отдельном namespace сетевых опытов [проверка Pod Security Admission](../verification/pod-security-admission.md) подтвердила отклонение конкретного нарушения `hostPID`; сама метка `enforce` без проверки не была бы доказательством отказа.

Значения chart ограничены числом реплик для обычного режима, ссылкой на образ, политикой его получения, ресурсами контейнера, лабораторным флагом, стратегией обновления и отдельным режимом HPA. `Chart.yaml.version` отражает версию шаблонов, `appVersion` — версию приложения. Замена только образа не требует изменения версии chart. Установка и обновление выполняются через `helm upgrade --install` с ожиданием готовности; обычный путь не использует `kubectl rollout restart`.

Helm не присваивает себе старые ресурсы, созданные `kubectl apply`. Для прежнего выделенного локального стенда безопасный переход — явно удалить старое лабораторное развёртывание либо пересоздать выделенный кластер `kind` и затем выполнить обычный путь установки. `task deploy` не удаляет старые ресурсы автоматически.

Одна реплика выбрана для исследования базового жизненного цикла. Краткий перерыв между удалением единственного Pod и готовностью замены ожидаем и не является высокой доступностью.

## Профиль обновления

Базовый профиль сохраняет одну реплику и выключенный `/work`. `values-rollout.yaml` задаёт две реплики, `maxSurge: 1`, `maxUnavailable: 0` и включает лабораторный маршрут. При штатном обновлении контроллер может создать третий Pod до удаления старого, а заданный предел недоступности требует сохранять две доступные реплики. Это ограничение состояния `Deployment`, не гарантия нулевых клиентских ошибок и не устойчивость к отказу узла одноузлового `kind`.

Временный Pod клиента обращается к DNS-имени `Service` и записывает количество ответов по классам и сетевые ошибки. Helm release остаётся владельцем только `Deployment` и `Service`: клиентский Pod создаётся отдельно для опыта. Сценарии обновления и отката описаны в [`../verification/rolling-update-under-load.md`](../verification/rolling-update-under-load.md) и [`../verification/failed-rollout-rollback.md`](../verification/failed-rollout-rollback.md).

## Профиль HPA

Профиль `values-hpa.yaml` включает `autoscaling/v2 HorizontalPodAutoscaler` для того же `Deployment`: минимум 2, максимум 4 реплики, цель CPU utilization `60%`. Контейнер API получает CPU request `100m`, limit `1000m`, memory request `32Mi`, limit `64Mi`; экспериментальный маршрут `/cpu` включён. HPA сравнивает измеренное потребление CPU с request `100m` каждой реплики, не с limit `1000m`. Эти значения — гипотеза для одноузлового опыта, а не промышленный подбор.

В базовом профиле и `values-rollout.yaml` HPA отсутствует, а Helm задаёт `Deployment.spec.replicas`. При включённом HPA шаблон `Deployment` опускает `spec.replicas`: после начального перехода этим полем управляет HPA, и последующие Helm upgrades в том же профиле не должны возвращать число реплик к статическому значению. Переключение существующего `Deployment` с фиксированного числа на отсутствие поля может однократно привести к значению по умолчанию 1 до согласования HPA; поэтому после `task deploy-hpa` требуется отдельно дождаться двух Ready-реплик и сохранить наблюдение. Обратный переход через `task deploy-rollout` удаляет HPA из release и вновь задаёт две реплики; не выполнять его во время измерения scale-down.

Для ограниченного локального опыта окно стабилизации уменьшения числа реплик установлено в 120 секунд вместо обычных 300. Изменение нужно для наблюдения scale-down после пятиминутной нагрузки в одном сеансе, но не означает, что уменьшение произойдёт ровно через 120 секунд. Отчёт остаётся [`Prepared`](../verification/hpa-autoscaling.md) до выполнения проверки на чистой ревизии.

## Probes и завершение

`startupProbe` и `livenessProbe` обращаются к `/livez`, но применяются на разных этапах жизненного цикла: первая даёт до 10 секунд на запуск, вторая после запуска обнаруживает неспособный отвечать процесс. `readinessProbe` обращается к `/readyz`. При удалении Pod Kubernetes также устанавливает условия завершения в `EndpointSlice`; изменение состояния приложения и обновление сетевого пути не синхронны.

Значение `terminationGracePeriodSeconds` равно 20 секундам. Оно включает HTTP `preStop` с ожиданием 3 секунды до `SIGTERM`, трёхсекундное окно наблюдения NotReady и десятисекундный срок `http.Server.Shutdown`: расчётные 16 секунд оставляют 4 секунды запаса. Конечный образ на основе `scratch` не содержит `sleep`, поэтому используется HTTP hook, а не `exec`.

Причина задержки подтверждена в [`../verification/rolling-update-under-load.md`](../verification/rolling-update-under-load.md): при чистом неуспешном прогоне три запроса через `Service` попали в старые Pod уже после `SIGTERM` и получили ответ middleware `503`. Hook оставляет приложение способным отвечать на такие запросы до сигнала, пока Kubernetes обновляет маршрутизацию. В следующем чистом прогоне все 1799 запросов клиента завершились успешно, а прямые наблюдатели подтвердили отказ после `SIGTERM`. Отдельный опыт с принятым восьмисекундным запросом на чистой ревизии `c0cfd4e80fe8` дал ответ `200` после hook и сигнала; его вывод ещё нужно внести в профильный отчёт. Увеличение `terminationGracePeriodSeconds` не сделано.

## Ресурсы и ограничения процесса

Контейнер получает requests `25m` CPU и `32Mi` памяти, limits `250m` CPU и `64Mi` памяти. Это начальные лабораторные значения, а не промышленный подбор ресурсов. Позднее они служат исходной точкой для отдельных экспериментов с ограничением CPU по квоте и `OOMKilled`.

Отдельные CPU-профили `values-cpu-high.yaml` и `values-cpu-low.yaml` задают одну реплику, включают экспериментальные маршруты, сохраняют request `100m` CPU и `32Mi` памяти, limit `64Mi` памяти; CPU limit составляет соответственно `1000m` и `100m`. Это сравнение одного изменённого параметра, а не рекомендуемые значения для приложения. Временный клиентский Pod не входит в Helm release. Счётчики cgroup снимаются до и после его нагрузки в каждом профиле; после смены профиля создаётся новый контейнер, поэтому накопительные значения между контейнерами напрямую не сравниваются. Один чистый локальный опыт подтвердил ограничение квоты и рост задержки: [`../verification/cpu-throttling.md`](../verification/cpu-throttling.md).

Для опыта с memory limit используется отдельный Pod из `scripts/kubernetes/oom-pod.yaml`, а не контейнер API. В нём работает существующий бинарный файл лабораторного клиента в явно выбранном режиме `memory`; Pod имеет `restartPolicy: Never`, memory request `16Mi`, memory limit `64Mi` и общий срок `activeDeadlineSeconds: 90`. Клиент ограничен выделением не более `128Mi` и удержанием не более 60 секунд; конкретный опыт задаёт буфер `96Mi` и удержание до 15 секунд, если контейнер не завершён раньше. Этот Pod не принадлежит Helm release и не обслуживает `Service`. Один локальный опыт подтвердил `OOMKilled` отдельного контейнера и доступность основного release после него, но не автоматическое восстановление `Deployment`: [`../verification/oomkilled.md`](../verification/oomkilled.md).

Отдельный Pod для проверки планирования вычисляет CPU request как `allocatable` единственного узла плюс `1000m`. При таком request планировщик должен оставить Pod без назначенного узла и записать `FailedScheduling` с причиной нехватки CPU; сценарий не потребляет этот объём CPU и не меняет `Deployment`. Повторный прогон после фиксации сценария в Git показал ожидаемую причину; удаление временного Pod подтверждено: [`../verification/scheduling-capacity.md`](../verification/scheduling-capacity.md).

Контейнер запускается без root, без повышения привилегий и без Linux capabilities. Корневая файловая система доступна только для чтения. Токен `ServiceAccount` не монтируется, потому что приложение не обращается к Kubernetes API.

Поле `selector` объекта `Deployment`, метки Pod и поле `selector` объекта `Service` используют общие значения `app.kubernetes.io/name: lab-api` и `app.kubernetes.io/instance: lab-api` для стандартного release. Именованный `targetPort: http` соответствует `containerPort: 8080`.

Подготовленная повторная проверка восстановления находится в [`../verification/pod-recovery.md`](../verification/pod-recovery.md).

## Проверка сетевого пути Service

`task smoke` создаёт временный Pod с ограничениями уровня `restricted` из `scripts/kubernetes/smoke-client.yaml`. Клиент обращается к `http://lab-api.kubernetes-application-lab.svc/version`, поэтому успешный ответ требует работы Kubernetes DNS, `ClusterIP Service`, готового `EndpointSlice` и приложения. Отложенное удаление Pod регистрируется до создания клиента и выполняется при успехе и ошибке.

API-server proxy остаётся отдельной диагностической границей `task smoke-api-proxy` и не считается доказательством внутрикластерной сети Service. Сценарий ожидает повторного выполнения на стабильной ревизии: [`../verification/service-networking.md`](../verification/service-networking.md).

## Target: выделенный сетевой кластер

Для исследования `NetworkPolicy` создан второй одноузловой `kind` с тем же закреплённым образом узла Kubernetes v1.34.0 и с `disableDefaultCNI: true`. Из двух кандидатов выбран только Cilium 1.20.3: [официальная матрица](https://docs.cilium.io/en/stable/network/kubernetes/requirements/) включает Kubernetes 1.34, а [инструкция для kind](https://docs.cilium.io/en/stable/installation/kind/) описывает замену штатного CNI. Calico не устанавливается параллельно. [Системные требования](https://docs.cilium.io/en/stable/operations/system_requirements/) Cilium включают Linux kernel не старее 5.10 и возможности eBPF; в выполненном опыте ядро Docker Desktop было `6.6.87.2-microsoft-standard-WSL2`. Cilium установлен отдельным Helm release `cilium` в `kube-system`, не chart приложения. Число реплик оператора для одноузлового опыта равно одному. `kube-proxy` остаётся штатным; возможности Gateway Cilium не предполагаются автоматически.

Ресурсами API в обоих кластерах владеет один и тот же chart `helm/lab-api`. Предварительный прогон подтвердил создание второго кластера, готовность Cilium/CoreDNS и базовый путь Pod → DNS → Service → API; его границы и `-dirty` образ находятся в [сценарии DNS и Service](../verification/service-dns-diagnostics.md). Исходный кластер и его release не менялись.

Для проверки правил подготовлен отдельный namespace `kubernetes-application-lab-policy` с уровнем `restricted`. Тот же chart устанавливает в нём второй Helm release API; отдельной копии Deployment/Service нет. Только экспериментальные Pod и `NetworkPolicy` определены отдельно. Правила выбирают API и три клиента по явным меткам, не затрагивая основной namespace. Новый прогон после фиксации сценария подтвердил все проверяемые переходы deny/allow; граница доказательства находится в [отчёте NetworkPolicy](../verification/network-policy-isolation.md).

## Current: Gateway API

Для отдельного сетевого кластера выбран Envoy Gateway `v1.9.2`: [официальная матрица](https://gateway.envoyproxy.io/news/releases/matrix/) для ветки 1.9 включает Kubernetes v1.34 и Gateway API v1.6.1. Это самостоятельный контроллер Gateway API, а не второй CNI или service mesh. Контроллер установлен; HTTP/HTTPS-путь через него проверен в локальном стенде. Штатный Cilium продолжает отвечать за сеть Pod и `NetworkPolicy`; экспериментальные политики другого namespace не распространяются автоматически на трафик Envoy.

Кластерная инфраструктура владеет отдельным Helm release контроллера и CRD, объектами `EnvoyProxy`, `GatewayClass`, `Gateway` и listener. `EnvoyProxy` задаёт тип Service плоскости данных `ClusterIP`, чтобы не создавать внешний `LoadBalancer` или `NodePort`. Доступ с хоста ограничен явным `kubectl port-forward` на `127.0.0.1`. Helm chart приложения владеет только необязательным `HTTPRoute`, направленным на собственный `Service/lab-api:80`; базовое развёртывание маршрута не создаёт. Hostname лаборатории — `api.lab.test`, единственное положительное правило маршрута — точное совпадение `/version`. Неизвестный hostname и иной путь не попали в API при выполненной проверке. Условия ресурсов и фактические клиентские ответы зафиксированы в [сценарии Gateway](../verification/gateway-routing-tls.md).

Лабораторный CA и сертификат сервера создаются отдельным локальным действием. Приватные ключи остаются в игнорируемом Git каталоге `.local-gateway-certs/`; `Secret/lab-gateway-tls` явно создаётся в namespace объекта `Gateway`, а HTTPS listener добавляется только после него. Проверка клиента явно использует этот тестовый CA и имя `api.lab.test`; соединение без указанного CA отвергается. Сертификат не предназначен для публичного доверия, а TLS завершается на Gateway, не в Go API. Наблюдения и ограничение проверки отзыва находятся в [отчёте Gateway](../verification/gateway-routing-tls.md).

## Current: лабораторная авторизация RBAC

У основного API сохраняется `automountServiceAccountToken: false`: приложение не обращается к Kubernetes API. Отдельный `ServiceAccount/lab-rbac-reader` находится только в namespace `kubernetes-application-lab-policy`. Его `Role` разрешает `get` единственного объекта `Pod/lab-rbac-client` в том же namespace; `RoleBinding` связывает только эту идентичность. Временный клиент получает проецируемый токен и CA для прямых HTTPS-запросов к Kubernetes API, но не выводит токен в журнал. Эти ресурсы не входят в Helm chart приложения и не меняют его права. В локальном опыте клиентские ответы и независимая проверка разрешений согласовались; временный Pod удалён. Граница опыта определена в [сценарии RBAC](../verification/rbac-access-control.md).

## Target: другие среды

Текущий chart пригоден для локального `kind` и образов, загруженных непосредственно в узел. Для другой среды ещё отсутствуют опубликованный образ и проверенный режим его получения. Только после их появления появится обоснование для отдельного файла значений среды.
