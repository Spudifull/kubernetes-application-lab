  т  мм  # Сквозная трассировка задания

HTTP-запрос создаёт задание, но его обработка продолжается после ответа API. Поэтому контекст трассировки нужно сохранить в PostgreSQL и передать через Kafka, иначе действия publisher и worker окажутся не связанными с исходной операцией.

**Состояние:** `Current`. Проверены успешная обработка, замена publisher, повторные попытки, DLQ и отдельные сценарии недоступности телеметрии. Результаты — в [отчёте](../verification/application-tracing.md).


## Границы и распространение контекста

В текущем `go.mod` компоненты OpenTelemetry Go имеют версию **`1.45.0`**. Первоначальные сквозные эксперименты выполнялись до этого обновления, на OpenTelemetry `1.44.0`; их результаты сохраняются как исторические доказательства, а не как новая приёмка версии `1.45.0`. Во всех трёх процессах используется OTLP/HTTP exporter.

```text
POST /jobs
   │
   ▼
SQL-транзакция: задание + outbox + trace_parent
   │
   ▼
publisher: чтение outbox → публикация с Kafka header traceparent
   │
   ▼
worker: получение сообщения → SQL-эффект → подтверждение offset
```

### API и PostgreSQL

HTTP-инструментирование ограничено маршрутами `POST /jobs` и `GET /jobs/{id}`. В атрибуты спанов попадает шаблон маршрута, но не полный URL, строка запроса, тело или произвольные HTTP-заголовки. `/livez`, `/readyz` и `/metrics` не создают спаны. При наличии действительного контекста ответ содержит `X-Lab-Trace-ID` и `traceparent`. Идентификатор трассировки ответа `GET /jobs/{id}` относится к этому HTTP-запросу и не обязан совпадать с трассировкой первоначального приёма задания.

Миграция `004_outbox_trace_context.sql` добавляет `lab_outbox.trace_parent`: пустая строка для старых записей или `traceparent` W3C длиной 55 символов. Миграции `001`–`003` не изменяются. Миграция `004` применяется **до** обновления API и publisher; новые версии требуют её наличия даже при выключенном SDK. Старые бинарные файлы продолжают работать с добавленным столбцом, поэтому для отката приложения удалять столбец и накопленные значения не требуется.

Контекст спана постановки сохраняется **в той же SQL-транзакции**, что и задание с записью outbox. Он не входит в бизнес-событие и не меняет вычисление `request_hash`. Повтор запроса с тем же ключом идемпотентности сохраняет первоначальный контекст, а не заменяет его новым.

### Publisher и Kafka

Publisher восстанавливает контекст после получения записи из outbox. Каждая попытка публикации получает отдельный спан. Операция захвата записи измеряется с фактическими временными границами; пустой опрос таблицы не создаёт трассировку. Отметка `published_at` и подтверждение брокером — отдельные события, не равнозначные завершению задания.

При публикации передаётся ровно один Kafka-заголовок `traceparent`. Worker извлекает его через стандартный механизм W3C и создаёт спан потребления с дочерними спанами работы, SQL-операций и подтверждения смещения. Повторная обработка создаёт ещё один спан потребления в той же цепочке контекста. Учебная повторная публикация использует уже сохранённый контекст outbox и не добавляет к трассировке спан диагностического процесса. При переходе в DLQ контекст также передаётся дальше, но содержимое бизнес-конверта DLQ не изменяется.

Сообщение без контекста начинает самостоятельную трассировку на границе worker. Пустой или некорректный заголовок **не должен приводить к отказу обработки задания**.

В качестве модели связи выбран родительский спан обработки одного сообщения, соответствующий [OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/). HTTP-спан заканчивается при отправке ответа; асинхронные потомки могут начаться позже. Время ожидания события в outbox не изображается как непрерывный HTTP-вызов.

Поддерживается только `traceparent`. `tracestate`, `baggage` и остальные заголовки не сохраняются и не распространяются. Некорректные, неоднозначные или слишком длинные значения отбрасываются. Для разбора сообщения рассматривается не более `64` Kafka-заголовков; размер `traceparent` ограничен `55` символами.

## Сегменты трассировки и журналы

| Компонент | Основные спаны и события |
|---|---|
| API | HTTP-шаблон маршрута, `jobs.validate`, `jobs.enqueue.transaction`, `jobs.get`, HTTP-статус и классификация ошибки БД |
| Publisher | `outbox.publish_attempt`, `outbox.claim`, `lab.jobs.v1 publish`, `broker_ack`, `retry_scheduled`, `outbox.mark_published.transaction`, `outbox.schedule_retry` |
| Worker | `lab.jobs.v1 process`, `jobs.start.transaction`, `worker.work`, состояние повторов, `jobs.complete.transaction`, подготовка/публикация/квитанция DLQ, `lab-workers commit`, `duplicate_observed`, `attempt_canceled` |

Имена SQL-спанов фиксированы: текст SQL, значения параметров и содержимое строк в трассировку не включаются. Ошибки кодируются предопределёнными категориями без необработанных сообщений драйвера БД или клиента Kafka. Для диагностики допускаются `job_id`, `event_id`, partition, offset и номер попытки. Эти значения **не используются как метки Prometheus**.

Существующее журналирование `slog` сохраняется: JSON, время UTC, `service`, `event`, `msg`, имя Pod и предметные поля события. Прикладные операции добавляют `trace_id` и `span_id`. Идентификатор может присутствовать и у контекста, для которого решение о семплировании не предусматривает экспорт. **Запись `trace_id` в журнале не доказывает наличие спана в Tempo**. Сбор журналов через Loki описан в [отдельном контракте](application-logging.md).

## Семплирование, ограничения и отказы

По умолчанию прикладной SDK отключён в Helm values. После включения используется `ParentBased` с семплированием `10%` новых корневых трассировок; решение действительного родителя сохраняется. Это правило уменьшения объёма телеметрии, а не ограничитель поступления бизнес-запросов. Диагностический профиль для коротких опытов выбирает `100%`.

| Ограничение SDK в каждом процессе | Значение |
|---|---|
| Очередь | `128` спанов |
| Размер пакета | `32` спана |
| Интервал отправки | `1s` |
| Тайм-аут экспорта | `1s` |
| Предел повторных попыток экспорта | `1s` |
| Атрибуты спана | Не более `32` |
| Длина значения атрибута | Не более `256` символов |
| События и ссылки | До `16` событий и `8` links |
| Завершение SDK | Не более `2s` |

Добавление спана в очередь не блокирует работу приложения. При переполнении очереди, `SIGKILL`, длительном отказе или истечении срока экспорта данные могут теряться. Система не обещает гарантированной или однократной доставки телеметрии.

Сроки завершения Pod не увеличены: API `20s`, publisher `35s`, worker `30s`. В расчёт включены:

- API: `preStop 3s` + ожидание состояния NotReady `3s` + завершение HTTP-сервера `10s` + SDK `2s`;
- publisher: текущая попытка до `25s` + освобождение SQL-ресурсов до `2s` + HTTP health до `3s` + SDK `2s`;
- worker: обработка до `18s` + выход из группы до `2s` + HTTP health до `3s` + SDK `2s`.

Некорректная локальная конфигурация SDK считается ошибкой запуска. Недоступность Collector или Tempo не участвует в проверках `/livez` и `/readyz`, не меняет SQL-транзакции и не разрешает преждевременный Kafka offset commit. Сообщение `tracing_export_failed` выдаётся с ограничением частоты — не чаще одного раза за `30s` — и не содержит исходную ошибку с потенциально чувствительными данными.

Проверки [недоступного telemetry endpoint](../verification/application-tracing.md) и [остановки настоящего Collector](../verification/collector-outage.md) подтвердили выполнение заданий с одним SQL-эффектом и восстановление доставки новой трассировки после возврата приёмника. Они не доказывают отсутствие потерь спанов во время недоступности и не заменяют измерения накладных расходов.

## Диагностика аварийной повторной доставки

Команда `tracing-worker-crash` использует существующий механизм аварийного завершения worker перед подтверждением Kafka offset. При этом активен диагностический профиль трассировки; намеренно аварийный процесс не обязан проходить readiness. Обычное развёртывание через `tracing-worker-deploy` снимает установленный отказ по штатной Helm-процедуре.

При принудительном `os.Exit` не выполняются отложенные `End` и `flush`. Поэтому часть спанов первой попытки может отсутствовать, а последующий повтор формирует собственные спаны. Недостающие сегменты нельзя восстанавливать по предположению — их отсутствие является наблюдаемой особенностью аварии.

`application-trace-inspect` сохраняет исходный ответ Tempo и нормализованный список спанов, проверяет принадлежность к нужному `trace ID`, уникальность `span ID`, допустимость временных интервалов и родительские связи. Для аварийного сценария допускается неполная трассировка с явно указанными отсутствующими родителями. Число спанов не доказывает успешность SQL-операции и не заменяет проверку Kafka offsets.

Обычный `application-trace-read` проверяет более строгую структуру успешного пути. Инспектор подходит и для неисправного или DLQ-сценария: он не должен требовать `succeeded` от задания, закончившегося ошибкой.

## Что трассировка не заменяет

Трассировка показывает связь операций и их время. Она не служит источником истины о фиксации данных. Успешное завершение задания требует самостоятельной проверки SQL-эффекта и Kafka offset; при аварийном `os.Exit` часть спанов может отсутствовать. Неудачная отправка трассировки не должна менять готовность приложения или отменять транзакции. Транспорт Collector/Tempo описан [отдельно](tracing-infrastructure.md).
