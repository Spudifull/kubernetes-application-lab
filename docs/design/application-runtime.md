# Контракт приложения во время выполнения

**Состояние: Current для базового API и ограниченных лабораторных маршрутов. PostgreSQL проверен в границах [Milestone 6](../verification/README.md#milestone-6--postgresql-и-состояние). Отдельный Kafka worker имеет [Passed для третьей итерации](../verification/kafka-worker.md); аварийная redelivery, retry/DLQ и остальные будущие сценарии этим не подтверждены.**

## Процесс API

Точка входа `cmd/api` запускает один HTTP-сервер на порту `8080`. Базовый профиль не имеет внешних зависимостей и не записывает данные в файловую систему. Необязательный DB-профиль и его контракт описаны отдельно в [PostgreSQL и сохраняемом состоянии](postgresql-stateful-storage.md).

После регистрации маршрутов запуск считается завершённым, и приложение становится готовым. Версия, ревизия исходного кода и дата сборки передаются через параметры сборки; локальный запуск без них использует определённые значения `dev` и `unknown`, а не случайные данные.

## HTTP API

| Маршрут | Назначение | Успешный ответ |
|---|---|---|
| `GET /` | минимальная пользовательская проверка доступности | `200` |
| `GET /livez` | процесс способен продолжать работу | `200` |
| `GET /readyz` | процесс принимает новую работу | `200`; после начала завершения `503` |
| `GET /metrics` | метрики приложения в текстовом формате Prometheus | `200` |
| `GET /version` | версия, ревизия и дата сборки | `200` и JSON |
| `GET /_prestop` | ограниченное ожидание для HTTP lifecycle hook Kubernetes | `200` через 3 секунды |
| `GET /work?duration_ms=N` | имитация принятой длительной работы только при `LAB_ENABLE_EXPERIMENTS=true` | `200` после N мс; `400` при неверном N |
| `GET /cpu?units=N` | фиксированный объём вычислений только при `LAB_ENABLE_EXPERIMENTS=true` | `200` и JSON; `400` при неверном N; `429` при занятых местах |
| `GET /cpu-stat` | счётчики квоты CPU из cgroup контейнера только при `LAB_ENABLE_EXPERIMENTS=true` | `200` и JSON; `503` при недоступных данных |

`/livez` не проверяет внешние зависимости. В базовом профиле их нет; в DB-профиле недоступность PostgreSQL влияет на `/readyz`, но не должна приводить к перезапуску процесса.

`/work` отсутствует в базовом режиме. При включении допускается ровно одно целое значение `duration_ms` от 1 до 8000. Завершение клиентского контекста прерывает ожидание. Журнал содержит `work_started`, `work_completed` или `work_canceled`, а необязательный заголовок `X-Lab-Run-ID` связывает запрос с запуском сценария. Значение параметра и идентификатор запуска не входят в метки метрик: маршрут учитывается как `GET /work`.

`/cpu` также отсутствует в базовом режиме. Он принимает ровно одно целое значение `units` от 1 до 100; одна единица соответствует миллиону целочисленных операций. Вычисление ограничено двумя одновременными запросами и восемью секундами на запрос, периодически проверяет контекст клиента и не сохраняет результат после ответа. При достижении срока возвращается `504`; при отмене клиентом вычисление прекращается. Уже принятый запрос не отменяется самим `BeginShutdown`, а новый запрос после него получает `503`. Журнал `cpu_work_started`, `cpu_work_completed` или `cpu_work_stopped` содержит имя Pod и необязательный `run_id`. Параметр, идентификатор и контрольная сумма не становятся метками Prometheus.

`/cpu-stat` читает не более 4096 байт на файл из смонтированной cgroup контейнера. Для cgroup v2 он возвращает `usage_usec`, `nr_periods`, `nr_throttled`, `throttled_usec`, `cpu.max`; для cgroup v1 — `nr_periods`, `nr_throttled`, перевод `throttled_time` из наносекунд в микросекунды и параметры квоты. Поле `usage_usec` для v1 пока отсутствует. Значения являются накопительными для текущего контейнера: сравнивать следует разности снимков одного Pod, не абсолютные значения разных Pod. Этот маршрут служит прямым сигналом ограничения квоты; `kubectl top` его не заменяет.

Каждый HTTP-ответ содержит диагностический заголовок `X-Lab-Pod`: в Kubernetes имя берётся из `metadata.name` через Downward API, а вне кластера без заданного имени используется `unknown`. Заголовок устанавливается до обработки маршрута, поэтому присутствует и в ответе `503` при завершении. Любой ответ с кодом от `400` записывается как `http_response_error` с кодом и именем Pod; отказ прикладному запросу после начала завершения дополнительно записывается как `work_rejected_during_shutdown` с именем Pod и, если передан, `run_id`; отказ `/readyz` — как `readiness_rejected`. Имя Pod и `run_id` не добавляются в метки Prometheus.

## Ограничения HTTP-сервера

Сервер использует следующие начальные лабораторные значения:

- `ReadHeaderTimeout`: 2 секунды, чтобы ограничить медленную передачу заголовков;
- `ReadTimeout`: 5 секунд, так как текущие маршруты не принимают объёмные тела запросов;
- `WriteTimeout`: 10 секунд, что превышает верхнюю границу ожидания `/work` и восьмисекундный предел вычисления `/cpu`;
- `IdleTimeout`: 60 секунд для повторного использования соединения без неограниченного простоя;
- `MaxHeaderBytes`: 1 MiB как явная верхняя граница заголовков.

Эти значения являются исходной гипотезой стенда, а не результатом промышленного подбора.

## Завершение процесса

При удалении Pod Kubernetes сначала вызывает HTTP `preStop` на `/_prestop`. Обработчик записывает `prestop_started`, ждёт три секунды и записывает `prestop_completed`. Он не меняет readiness и продолжает обслуживать прикладные запросы, которые ещё могут прийти через `Service`. Задержка нужна потому, что чистый прогон на `5a5290f9254b` связал три клиентских `503` с немедленным отказом приложения после `SIGTERM` при ещё поступавших запросах через `Service`. Это ограниченный лабораторный механизм, а не гарантия завершения распространения сетевых правил за три секунды.

`SIGINT` и `SIGTERM` затем обрабатываются через единый управляемый путь; при прямом сигнале без удаления Pod этап `preStop` отсутствует:

```text
получен сигнал
→ readiness меняется на false
→ все недиагностические маршруты получают 503
→ в течение 3 секунд состояние NotReady остаётся наблюдаемым
→ http.Server.Shutdown получает срок 10 секунд
→ принятые запросы получают возможность завершиться в пределах срока
→ процесс завершается
```

Это порядок внутри приложения, а не обещание синхронного удаления Pod из сетевой маршрутизации. Журнал `signal_received` отдельно фиксирует полученный сигнал; наблюдаемое состояние `EndpointSlice` и фактический ответ через `Service` проверяются отдельно. Один чистый прогон на `c0cfd4e80fe8` подтвердил порядок hook → `SIGTERM` и ноль ошибок клиента при заданной нагрузке; его границы приведены в [`../verification/rolling-update-under-load.md`](../verification/rolling-update-under-load.md).

Для удаления Pod расчётный путь составляет до 3 секунд `preStop` + 3 секунды после `SIGTERM` + 10 секунд `http.Server.Shutdown`, то есть до 16 секунд из `terminationGracePeriodSeconds: 20`. Оставшиеся четыре секунды — запас на запуск hook и накладные расходы, не измеренная гарантия. При прямом сигнале без hook расчётный путь по-прежнему не превышает 13 секунд. Если срок `Shutdown` истекает, сервер принудительно закрывается и процесс завершается с ошибкой; этот аварийный путь не выдаётся за корректное завершение.

После `SIGTERM` доступны только диагностические маршруты `/livez`, `/readyz`, `/metrics` и `/version`. Список разрешённых диагностических путей задаётся явно; любой существующий или будущий прикладной маршрут автоматически получает `503 Service Unavailable` после начала завершения, если отдельный контракт не определит другое поведение. `/_prestop` вызывается до `SIGTERM` и не входит в этот список.

Доказательство перехода готовности и завершения обычного Pod находится в [`../verification/graceful-termination.md`](../verification/graceful-termination.md).
Отдельный сценарий для уже принятого `/work` находится в [`../verification/inflight-request-shutdown.md`](../verification/inflight-request-shutdown.md): повтор на чистой ревизии `5d233c29e7ec` связал серверный журнал после `preStop` и `SIGTERM` с ответом `200` принятого восьмисекундного запроса и отказом новой работе.

## Метрики

Текущая поверхность содержит:

- `lab_http_requests_total`;
- `lab_http_request_duration_seconds` с `sum` и `count`, без вычисления квантилей в процессе;
- `lab_http_request_latency_seconds` с фиксированными cumulative buckets, sum/count для оценки квантилей на стороне Prometheus;
- `lab_http_requests_active`;
- `lab_build_info`.

HTTP-метрики используют только ограниченные labels: нормализованный метод, шаблон зарегистрированного маршрута и код ответа. Полный URL, идентификаторы запросов и пользовательские значения в labels не попадают.

Прежние имена summary сохранены. Histogram и метрики publisher/worker/outbox подготовлены для новой runtime-проверки; семантика, ограничения и источники принадлежат [контракту наблюдаемости](observability-architecture.md#прикладные-метрики), результаты — [отчёту Prepared](../verification/application-metrics.md).

## Отдельный worker

`cmd/worker` — отдельный процесс, не фоновый обработчик API. Семантика Kafka, транзакционного SQL-эффекта, ручных offsets, rebalance и ограниченного завершения принадлежит [контракту обработки заданий](kafka-event-processing.md#worker-offsets-и-идемпотентность). Подготовленные сценарии не означают проверенную доставку; retry/DLQ и аварийная redelivery остаются Target.
