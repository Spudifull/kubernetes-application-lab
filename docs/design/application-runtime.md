# Работа Go-приложения

Go API выполняет две разные задачи. В базовом режиме он помогает исследовать поведение HTTP-приложения в Kubernetes без внешних сервисов. Дополнительный профиль включает хранение данных и приём асинхронных заданий; их выполняют отдельные процессы publisher и worker.

**Состояние:** `Current`. Настройки и сценарии описаны ниже; результаты конкретных проверок собраны в [каталоге](../verification/README.md).


## Состав приложения и режимы работы

`cmd/api` запускает HTTP-сервер на порту `8080`. В базовом режиме PostgreSQL и Kafka не нужны. Это отделяет проверку жизненного цикла Pod от работы зависимостей.

Дополнительные возможности включаются явно:

| Режим | Условие | Назначение |
|---|---|---|
| Базовый API | Без дополнительных флагов | Диагностика доступности, завершения и версии приложения. |
| Лабораторные маршруты | `LAB_ENABLE_EXPERIMENTS=true` | Управляемая задержка ответа, вычислительная нагрузка и чтение счётчиков CPU. |
| Работа с PostgreSQL | `LAB_DB_ENABLED=true` | Операции с сохраняемыми записями и проверка доступности базы данных. |
| Обработка заданий через API | `LAB_JOBS_ENABLED=true` при настроенном подключении к PostgreSQL | Создание заданий и чтение их состояния; публикация и выполнение происходят в отдельных процессах. |

Последние два режима используют [контракт PostgreSQL](postgresql-stateful-storage.md) и [контракт обработки заданий](kafka-event-processing.md). При запуске приложения сведения о версии, ревизии исходного кода и времени сборки передаются через параметры сборки. Для локального запуска без них используются предсказуемые значения `dev` и `unknown`.

## HTTP-интерфейс

### Основные и диагностические маршруты

| Маршрут | Назначение | Ответ |
|---|---|---|
| `GET /` | Простой ответ приложения | `200` |
| `GET /livez` | Проверка работоспособности процесса | `200`, пока процесс способен обслуживать HTTP |
| `GET /readyz` | Проверка готовности принимать новую работу | `200` в готовом состоянии, `503` после начала завершения или при недоступной обязательной зависимости |
| `GET /metrics` | Метрики в формате Prometheus | `200` |
| `GET /version` | Версия, ревизия исходников и время сборки | `200`, JSON |
| `GET /_prestop` | Задержка перед отправкой сигнала завершения при удалении `Pod` | `200` после трёхсекундного ожидания |

`/livez` не зависит от состояния PostgreSQL. В режиме работы с базой данных её недоступность отражается на `/readyz`, но сама по себе не должна вызывать перезапуск API. Различие между проверками работоспособности и готовности принципиально: восстановление зависимости не требует уничтожать работающий процесс.

При включении PostgreSQL доступны `POST /records/{key}` и `GET /records/{key}`. При включении обработки заданий — `POST /jobs` и `GET /jobs/{id}`. Дополнительные требования к данным, транзакциям и идентификаторам определены в профильных контрактах.

### Лабораторные маршруты

Эти маршруты отсутствуют, пока не установлен `LAB_ENABLE_EXPERIMENTS=true`.

| Маршрут | Назначение | Ограничения и ответы |
|---|---|---|
| `GET /work?duration_ms=N` | Имитирует длительный запрос | Одно целое `N` от 1 до 8000; `200` после ожидания, `400` при неверном параметре |
| `GET /cpu?units=N` | Создаёт ограниченную вычислительную нагрузку | Одно целое `N` от 1 до 100; не более двух одновременных запросов; `429` при превышении параллелизма, `504` при превышении времени |
| `GET /cpu-stat` | Возвращает накопительные счётчики CPU контейнера | `200` и JSON либо `503`, если счётчики недоступны |

`/work` прерывает ожидание при отмене контекста запроса. События `work_started`, `work_completed` и `work_canceled` позволяют сопоставить начало, завершение и отмену работы. Необязательный заголовок `X-Lab-Run-ID` связывает события с конкретным экспериментом.

Для `/cpu` одна единица означает миллион целочисленных операций. Вычисление ограничено восемью секундами, периодически проверяет отмену контекста и не сохраняет результат после отправки ответа. События `cpu_work_started`, `cpu_work_completed` и `cpu_work_stopped` содержат сведения о выполнении. Уже принятая работа не прерывается только потому, что началось штатное завершение процесса.

`/cpu-stat` читает не более 4096 байт из каждого используемого файла cgroup. Для cgroup v2 доступны `usage_usec`, `nr_periods`, `nr_throttled`, `throttled_usec` и сведения о квоте из `cpu.max`. Для cgroup v1 возвращаются счётчики периодов и ограничений, а время `throttled_time` переводится из наносекунд в микросекунды; `usage_usec` в этом режиме не предоставляется.

**Счётчики CPU накапливаются в пределах жизни контейнера.** Для измерения влияния нагрузки следует сравнивать разности двух снимков одного контейнера. Нельзя сопоставлять абсолютные значения разных `Pod` как результаты одного непрерывного измерения. `kubectl top` показывает другую группу показателей и не заменяет чтение cgroup.

## Ограничения HTTP-сервера

| Параметр | Значение | Назначение |
|---|---:|---|
| `ReadHeaderTimeout` | 2 с | Ограничить время получения заголовков. |
| `ReadTimeout` | 5 с | Ограничить время чтения запроса. |
| `WriteTimeout` | 10 с | Оставить время для завершения ограниченных лабораторных маршрутов. |
| `IdleTimeout` | 60 с | Ограничить простой повторно используемых соединений. |
| `MaxHeaderBytes` | 1 MiB | Установить верхнюю границу размера заголовков. |

Это параметры учебного стенда, а не результат подбора под производственную нагрузку.

## Завершение процесса

### Удаление Pod и предварительная задержка

При штатном удалении `Pod` Kubernetes вызывает HTTP-хук `preStop` по пути `/_prestop`. Обработчик записывает `prestop_started`, выдерживает три секунды и записывает `prestop_completed`. Пока хук выполняется, приложение ещё обслуживает входящие запросы и не переводит себя в состояние неготовности.

Задержка появилась после проверки, в которой три запроса клиента получили `503` от старых экземпляров после `SIGTERM`, хотя запросы ещё проходили через `Service`. Она даёт сетевой конфигурации время обновиться, но не гарантирует завершения распространения изменений за три секунды.

### Обработка сигнала

`SIGINT` и `SIGTERM` запускают один путь управляемого завершения:

```text
получение сигнала
→ переход в состояние NotReady
→ отказ новым прикладным запросам (503)
→ трёхсекундное окно наблюдения состояния NotReady
→ http.Server.Shutdown с ограничением 10 секунд
→ завершение принятых запросов в пределах доступного времени
→ выход из процесса
```

После сигнала сохраняется доступ только к диагностическим маршрутам `/livez`, `/readyz`, `/metrics` и `/version`. Новый прикладной маршрут по умолчанию также получает `503`, пока для него явно не установлен другой контракт. Маршрут `/_prestop` используется до сигнала и не относится к разрешённому набору.

При прямой отправке сигнала процессу `preStop` не выполняется. При штатном удалении `Pod` расчётное время составляет до 3 секунд на хук, 3 секунд на наблюдение NotReady и 10 секунд на `Shutdown` — всего до 16 секунд из `terminationGracePeriodSeconds: 20`. Оставшиеся четыре секунды представляют собой запас, а не измеренную гарантию. При истечении срока `Shutdown` соединения могут быть закрыты принудительно; такой исход не считается корректным завершением всех запросов.

Переход приложения в NotReady, изменение условий `EndpointSlice` и прекращение реальной маршрутизации — отдельные процессы. Их нельзя считать одним синхронным событием.

[Проверка штатного завершения](../verification/graceful-termination.md), [завершение принятого запроса](../verification/inflight-request-shutdown.md) и [обновление под нагрузкой](../verification/rolling-update-under-load.md) содержат наблюдения, включая ранее неудачные прогоны. В одном из чистых повторов обновления клиент получил 1799 успешных ответов из 1799; этот результат не гарантирует отсутствие ошибок в других условиях.

## Метрики приложения

В базовом HTTP-интерфейсе используются:

- `lab_http_requests_total` — количество запросов;
- `lab_http_request_duration_seconds` — суммарная длительность и количество наблюдений;
- `lab_http_request_latency_seconds` — гистограмма задержки с фиксированными границами интервалов;
- `lab_http_requests_active` — число активных запросов;
- `lab_build_info` — сведения о сборке.

HTTP-метрики не содержат полные URL, идентификаторы заданий, значения параметров и идентификаторы экспериментов. Метрики публикации, обработки заданий и состояния outbox описаны в [контракте наблюдаемости](observability-architecture.md). Проверенные измерения приведены в [отчёте о метриках приложения](../verification/application-metrics.md).

## Отдельные процессы обработки заданий

`cmd/publisher` читает записи transactional outbox из PostgreSQL и публикует соответствующие события в Kafka. Отметка о публикации записывается только после подтверждения брокера. `cmd/worker` получает события, сохраняет результат обработки в SQL-транзакции и только затем подтверждает смещение Kafka.

Повторная доставка допустима; идемпотентность предотвращает повторное применение уже сохранённого результата. Конечные повторы, отправка в DLQ, аварийная повторная доставка и восстановление после недоступности брокера реализованы и проверялись отдельными сценариями. Подробности, включая ограничения гарантий, определены в [контракте обработки заданий](kafka-event-processing.md). Отчёты о [повторной доставке](../verification/kafka-redelivery.md), [повторах и DLQ](../verification/kafka-retry-dlq.md) и [недоступности брокера](../verification/kafka-broker-outage.md) фиксируют результаты выполненных опытов.
