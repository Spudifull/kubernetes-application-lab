# Многонодовый `kind`

Для опытов с планировщиком, обслуживанием узлов и сетевыми политиками одного узла недостаточно. Поэтому этап 10A использует отдельный кластер `kind`: один control plane и два worker. Все три узла — контейнеры на **одном Linux runner**, а не независимые физические серверы.

**Состояние:** `Prepared`. Конфигурация и сценарии добавлены, но [отчёт](../verification/multi-node-kubernetes.md) пока не содержит подтверждённого выполнения workflow.

## Размещение приложения

В тестовый кластер устанавливается существующий Helm chart `lab-api` без PostgreSQL, Kafka или стека наблюдаемости. Работают две реплики API. Для их распределения используется `topologySpreadConstraints`:

| Параметр | Значение |
|---|---|
| `replicaCount` | `2` |
| `topologyKey` | `kubernetes.io/hostname` |
| `maxSkew` | `1` |
| `whenUnsatisfiable` | `ScheduleAnyway` |

`ScheduleAnyway` — предпочтение, **не гарантия** размещения на разных worker. Проверка должна смотреть фактические `spec.nodeName` каждого Pod.

## Что проверяется

| Группа workflow | Сценарий |
|---|---|
| `bootstrap` | Три `Ready`-узла, две готовые реплики на разных worker, HTTP через Service и совпадение `/version` с ревизией образа. |
| `scheduler` | `nodeSelector`, обязательное и предпочтительное affinity, `taints` и `tolerations`, причины `Pending` и восстановление. |
| `maintenance` | `cordon`, ограничения `PodDisruptionBudget`, `drain` и `uncordon`, замена Pod и выборочные HTTP-запросы. |
| `outage` | Остановка контейнера worker, переход `Node Ready` в неизвестное состояние, создание замены и возвращение узла. |
| `network` | Отдельный кластер с Calico 3.33.0, запрет и разрешение трафика к ClusterIP с отдельной проверкой DNS. |

Сценарии запускаются независимо, каждый в своём кластере и kubeconfig. Результаты сохраняются в `.cache/multinode/evidence/`; GitHub Actions удерживает артефакты 14 дней.

## Ограничения эксперимента

Потеря контейнера worker на общем runner не проверяет физический отказ сервера. Выборочный HTTP-ответ во время `drain` не гарантирует отсутствие кратких ошибок между проверками. Кластер не содержит постоянных данных приложения, поэтому сохранность PVC не рассматривается.

Порядок воспроизведения и очистки — в [инструкции](../engineering/multi-node-kubernetes-lab.md). Для отдельных виртуальных машин предусмотрен [сценарий с `kubeadm`](../engineering/kubeadm-hyperv-lab.md), который имеет собственные требования и статус проверки.
