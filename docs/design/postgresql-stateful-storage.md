# PostgreSQL: хранение данных и восстановление

PostgreSQL хранит состояние, которое должно переживать замену Pod. Приложение обращается к базе через ограниченный пул соединений, а изменение схемы выполняется отдельным миграционным Job. Отказ БД влияет на готовность зависимого API, но не должен приводить к автоматическому перезапуску самого HTTP-процесса.

**Состояние:** `Current`. Проверки постоянного хранения, миграций, отказа зависимости и резервного копирования приведены в [отчётах](../verification/README.md).


## Границы ответственности

PostgreSQL развёртывается независимо от основного приложения. Это позволяет проверять состояние базы данных, не изменяя базовый профиль API.

| Компонент | Назначение |
|---|---|
| Helm release `lab-postgres` | Управляет `StatefulSet/lab-postgres`, двумя `Service`, `ConfigMap` и `NetworkPolicy`. |
| `StatefulSet` | Запускает один экземпляр PostgreSQL и создаёт постоянный том через `volumeClaimTemplates`. |
| `Secret/lab-postgres-credentials` | Содержит учётные данные; создаётся отдельной командой и не входит в Helm release. |
| Миграционный `Job` | Применяет SQL-миграции независимо от Helm release приложения и базы данных. |
| Helm release `lab-api` | По умолчанию не использует PostgreSQL; подключение включается через `values-db.yaml`. |

Используется один экземпляр PostgreSQL. Репликация, автоматическое переключение на резервный сервер и распределённое хранение в этом профиле отсутствуют. Миграционный `Job` запускается отдельно, чтобы можно было проверить его результат и сохранить журнал выполнения.

## Постоянный том и жизненный цикл PostgreSQL

`StatefulSet` создаёт `PVC/data-lab-postgres-0` со следующими параметрами:

| Параметр | Значение |
|---|---|
| Запрошенная ёмкость | `1Gi` |
| Режим доступа | `ReadWriteOnce` |
| `StorageClass` | `standard` |
| `persistentVolumeClaimRetentionPolicy` | `Retain` |
| Образ PostgreSQL | `postgres:16.14-bookworm` |
| UID/GID процесса | `999` / `999` |
| `fsGroup` | `999` |
| `terminationGracePeriodSeconds` | `60` |

В проверенном кластере `standard` использовал `rancher.io/local-path`, `volumeBindingMode: WaitForFirstConsumer` и `reclaimPolicy: Delete`; расширение тома было отключено. Эти свойства установлены для конкретной среды 24 октября 2026 года, а не для любого кластера с `StorageClass` такого имени.

Политика `Retain` сохраняет PVC при удалении или уменьшении числа реплик `StatefulSet`, но **не изменяет** `reclaimPolicy` самого `StorageClass`. Поэтому удаление PVC может привести к удалению PV и данных. Обычные команды очистки не должны удалять этот PVC. Замена `Pod` при сохранённом томе и потеря тома или узла — принципиально разные случаи.

Размер запрошенного PVC не является жёсткой квотой физического диска для используемого local-path provisioner. Одноузловой `kind` не обеспечивает сохранность данных после потери узла, Docker-хранилища или всего кластера.

Образ закреплён тегом, но не digest. При воспроизведении опыта необходимо сохранять фактический `imageID`, поскольку один и тот же тег не гарантирует неизменности содержимого реестра.

`PGDATA` расположен в подкаталоге смонтированного тома. Проверки `startupProbe` и `readinessProbe` вызывают `pg_isready` с параметрами подключения, сформированными из `POSTGRES_USER` и `POSTGRES_DB`. Значения `PGUSER` и `PGDATABASE` обеспечивают использование нужной роли и базы, а не неявных значений по умолчанию. **Успешный `pg_isready` подтверждает ответ сервера, но не проверяет корректность пароля, таблиц приложения и миграций.**

Проверка запуска с указанными правами и сохранения тома приведена в [отчёте о StatefulSet](../verification/postgresql-statefulset.md). Работа с другими драйверами хранения не проверялась.

### Сетевой доступ

`NetworkPolicy` описывает разрешённый TCP-доступ к порту `5432` для основного API, диагностического профиля `lab-api-badcred`, миграционного `Job` и процесса публикации событий `lab-publisher` в том же пространстве имён.

Эти правила определяют желаемую конфигурацию, но не доказывают фактическую изоляцию в основном кластере с `kindnet`. Проверка применения сетевой политики требует CNI, который её исполняет, и отдельного опыта с запрещённым подключением. Настройка доступа для publisher относится также к [контракту Kafka](kafka-event-processing.md).

## Конфигурация и учётные данные

`ConfigMap` содержит имя базы `lab`, адрес сервиса `lab-postgres` и порт `5432`. Данные для входа хранятся в `Secret/lab-postgres-credentials` с ключами `username` и `password`.

Команда `task db-secret-create` создаёт `Secret` отдельно от Helm. Локальные учётные данные находятся в исключённом из Git файле `.local-db/credentials.json`; команда не должна печатать пароль. Для файла запрашивается режим доступа `0600`, однако соответствие файловых ACL в Windows отдельно не подтверждено.

Если `Secret` уже существует, команда не заменяет его содержимое. При повторном создании отсутствующего `Secret` используются сохранённые локальные данные. Отсутствие `Secret` должно останавливать процедуру развёртывания до установки зависимого профиля. Для восстановления необходимо отдельно выполнить создание `Secret` и повторить развёртывание.

`Secret` Kubernetes не заменяет полноценное управление секретами и сам по себе не подтверждает шифрование данных в хранилище кластера. Учётные данные не должны попадать в Git, журналы или артефакты проверок.

## Подключение Go-приложения

### Пул соединений и время ожидания

Подключение активируется через `LAB_DB_ENABLED=true`. Приложение использует `database/sql` и драйвер `pgx/v5`.

| Параметр | Значение |
|---|---:|
| Максимум открытых соединений на реплику API | 4 |
| Максимум простаивающих соединений | 2 |
| Максимальный срок жизни соединения | 5 минут |
| Максимальное время простоя соединения | 1 минута |
| Ограничение времени подключения | 2 секунды |
| Ограничение времени чтения и записи | 2 секунды |

Для `N` реплик верхняя граница пула API составляет `4 × N` соединений. Миграционные и административные операции используют дополнительные соединения и учитываются отдельно. После штатного завершения HTTP-сервера пул закрывается.

### HTTP-интерфейс записей

Маршруты доступны только в профиле с PostgreSQL.

| Маршрут | Действие | Ответ |
|---|---|---|
| `POST /records/{key}` | Создаёт или обновляет запись через параметризованный SQL-запрос | `204` при успехе |
| `GET /records/{key}` | Читает сохранённое значение | JSON при успехе, `404` при отсутствии записи |

Ключ содержит от 1 до 64 символов ASCII из диапазона `[A-Za-z0-9_-]`. Для записи принимается JSON вида `{"value":"..."}` размером не более 1024 байт; значение ограничено 512 символами Unicode. При недоступности базы данных возвращается `503` без раскрытия подробностей SQL и пароля.

### Готовность и доступность

В профиле с PostgreSQL `/readyz` проверяет обязательную зависимость и схему с ограничением времени 500 мс. Ошибка подключения, отсутствие нужной таблицы или превышение срока приводят к ответу `503`. При этом `/livez` остаётся независимым от базы данных и возвращает `200`, пока процесс работоспособен.

Это намеренное различие: недоступность обязательной зависимости должна исключать API из маршрутизации `Service`, но не обязана приводить к перезапуску процесса. Если база недоступна для всех экземпляров API, все они могут одновременно стать NotReady; текущая архитектура допускает такой исход.

В журналах различаются `authentication_failed`, `schema_missing` и `database_unavailable`. Пароли и содержимое записей не включаются в диагностические сообщения. В лабораторных опытах готовность восстанавливалась после исправления учётных данных либо схемы **без перезапуска рабочего API**; условия опыта указаны в [отчёте об отказе зависимости](../verification/database-dependency-failure.md).

## Миграции схемы

Исходную таблицу записей создаёт `internal/database/migrations/001_lab_records.sql`. Миграции последующих этапов добавляют таблицы заданий и обработки событий; их контракт описан в [документе Kafka](kafka-event-processing.md).

Миграционный `Job` запускает существующий образ API в режиме `migrate`. Учёт применённых версий ведётся в `lab_schema_migrations`. Для исключения конкурентного изменения схемы используется advisory lock PostgreSQL.

Правила применения миграций:

1. SQL-файлы обрабатываются в порядке имён.
2. Проверяется, применялась ли версия ранее.
3. Новая миграция и запись её версии выполняются в одной транзакции.
4. При ошибке транзакция откатывается; повторно применённые версии пропускаются.

Миграционный `Job` использует `backoffLimit: 0` и `activeDeadlineSeconds: 90`. Журнал сохраняется до очистки по TTL, установленному в 24 часа; если вывод нужен как доказательство, его необходимо получить до удаления `Job`.

### Проверка отката миграции

Отрицательный сценарий создаёт `public.lab_migration_rollback_probe` и затем выполняет заведомо неверный SQL **в той же транзакции**. Успешный откат подтверждается отсутствием контрольной таблицы после ошибки при сохранности основной таблицы, исходной записи и реестра миграций.

Перед выполнением сценарий проверяет, что контрольной таблицы ещё нет. Если она существует, процедура останавливается, не удаляя чужой объект. Итоги проверки находятся в [отчёте о миграциях](../verification/database-migrations.md).

## Резервное копирование и восстановление

`task db-backup` запускает `pg_dump -Fc` внутри контейнера и сохраняет поток в файл хоста `.local-db/backup.dump`, исключённый из Git. Архив не создаётся на файловой системе `Pod`; существующий файл резервной копии не перезаписывается автоматически.

`task db-restore` восстанавливает архив в **отдельную базу `lab_restore` того же экземпляра PostgreSQL**, используя `pg_restore --exit-on-error`. Основная база не перезаписывается. После восстановления проверяется контрольная запись и её значение; удаление тестовой базы выполняется отдельной командой.

[Проверка резервного копирования](../verification/database-backup-restore.md) подтвердила разделение состояний: в восстановленной базе сохранилось значение `before-backup`, тогда как в рабочей базе после создания архива находилось `after-backup`.

Такой опыт подтверждает возможность восстановить состояние на момент копирования **внутри доступного экземпляра PostgreSQL**. Он не проверяет восстановление после уничтожения кластера, узла, хранилища или самого экземпляра базы данных.

## Что гарантирует эта модель

Замена Pod при подключённом прежнем PVC сохраняет данные. Это не означает устойчивости к потере самого тома или кластера: в лаборатории один PostgreSQL, без репликации и автоматического переключения. Восстановление из резервной копии проверяется отдельно от повторного запуска Pod. Подробные шаги приведены в [инструкции](../engineering/database-lab.md), а фактические результаты — в [проверке StatefulSet](../verification/postgresql-statefulset.md), [миграций](../verification/database-migrations.md) и [резервного копирования](../verification/database-backup-restore.md).
