# PostgreSQL и сохраняемое состояние

**Состояние: Current для конфигурации и проверенных локальных сценариев Milestone 6, включая отсутствующий Secret, отсутствующую таблицу, восстановление готовности после исправления конфигурации и схемы и базовый API без работающей БД. Этап закрыт в границах этих проверок; результаты и ограничения — в [каталоге проверок](../verification/README.md#milestone-6--postgresql-и-состояние).**

## Владение и границы

Отдельный Helm release `lab-postgres` владеет `StatefulSet/lab-postgres`, двумя Service, ConfigMap и NetworkPolicy. Он не создаёт Secret. Основной release `lab-api` по умолчанию остаётся stateless; `values-db.yaml` включает подключение только после успешной миграции. Это один экземпляр PostgreSQL без репликации и автоматического переключения. Миграционный Job создаётся командой `labctl` отдельно от обоих release, чтобы его результат и журнал оставались доступны после выполнения.

## Хранилище

`StatefulSet` создаёт PVC `data-lab-postgres-0` ёмкостью `1Gi`, режимом `ReadWriteOnce` и явно выбранным StorageClass `standard`. 24 октября 2026 года владелец проверил в существующем kind: provisioner `rancher.io/local-path`, `volumeBindingMode: WaitForFirstConsumer`, `reclaimPolicy: Delete`, расширение выключено. Поэтому при потере Pod том должен остаться привязан к PVC, но удаление PVC может удалить PV и данные. `persistentVolumeClaimRetentionPolicy: Retain` защищает PVC при удалении или уменьшении числа реплик StatefulSet, не меняет `reclaimPolicy` самого StorageClass. Удаление PVC отсутствует в обычной очистке. Локальный том одноузлового kind не защищает от потери узла, Docker-хранилища или кластера.

Образ `postgres:16.14-bookworm` закрепляет версию на уровне тега, но не digest: повторное получение этого тега теоретически может дать иной образ. При проверке записать фактический `imageID`. Процесс работает с UID/GID 999 и `fsGroup: 999`; `PGDATA` находится в подкаталоге смонтированного тома. `startupProbe` и `readinessProbe` вызывают `pg_isready`; это проверка доступности процесса, а не пароля или схемы. Переменные libpq `PGUSER` и `PGDATABASE` получают значения из объявленных выше `POSTGRES_USER` и `POSTGRES_DB` при создании контейнера. Так обе проверки используют роль из Secret и базу из ConfigMap, не обращаясь по умолчанию к роли `postgres`. `terminationGracePeriodSeconds: 60` даёт PostgreSQL время на штатное завершение. Requests/limits и ограниченные `emptyDir` заданы в chart. Запуск с этими правами на выбранном StorageClass подтверждён в [локальном опыте](../verification/postgresql-statefulset.md); совместимость с другими хранилищами не проверена.

`NetworkPolicy` допускает TCP/5432 от Pod основного API, отдельного отрицательного профиля `lab-api-badcred`, миграционного Job и отдельного release `lab-publisher` в том же namespace. Разрешение publisher добавлено для [подготовленной интеграции Kafka](kafka-event-processing.md); его применение ещё не проверено. Исполнение политики зависит от CNI: в основном kind с kindnet это правило само по себе не доказывает изоляцию. Для проверки нужен отдельный кластер с Cilium и явная отрицательная проба.

## Конфигурация и секреты

ConfigMap содержит имя базы `lab`, адрес Service `lab-postgres` и порт `5432`. Secret `lab-postgres-credentials` содержит `username` и `password`; он создаётся явной командой `task db-secret-create`, не принадлежит Helm и не хранится в Git. Локальный `.local-db/credentials.json` исключён через `.gitignore`, создаётся с запрошенным режимом `0600` и не печатается командой; фактические ACL Windows отдельно не проверены. Если Secret уже существует, команда не меняет его; если он отсутствует, повтор использует прежний локальный файл. При отсутствии Secret развёртывание останавливается до Helm; восстановление — повторить `task db-secret-create` и развёртывание. Kubernetes Secret не заменяет внешний менеджер секретов и не обеспечивает шифрование сам по себе.

## API и миграция

При `LAB_DB_ENABLED=true` API открывает пул `database/sql` с драйвером `pgx/v5`: максимум 4 открытых и 2 простаивающих соединения на реплику, срок соединения 5 минут, простой 1 минута. При N репликах верхняя граница подключений API — `4 × N`, дополнительно одно соединение может держать Job. Подключение ограничено двумя секундами; запросы записи и чтения — двумя секундами. Логи не содержат паролей и значений записей. После управляемого завершения HTTP-сервера пул закрывается.

`POST /records/{key}` принимает JSON `{"value":"..."}` не более 1024 байт; ключ содержит 1–64 символа ASCII `[A-Za-z0-9_-]`, значение — не более 512 символов Unicode. Запись использует параметризованный upsert и возвращает `204`. `GET /records/{key}` возвращает JSON с ключом и значением, `404` для отсутствующей записи, `503` при ошибке БД. Маршруты существуют только в DB-профиле. При недоступной БД `/readyz` возвращает `503`, если запрос к схеме не завершился за 500 мс; `/livez` остаётся `200`. Журнал различает `authentication_failed`, `schema_missing` и `database_unavailable`, не записывая пароль. При общем отказе БД все реплики могут одновременно стать NotReady, и Service не будет маршрутизировать к ним; это осознанная политика для профиля, где операции с БД обязательны.

Файл `internal/database/migrations/001_lab_records.sql` создаёт таблицу. Job запускает тот же образ API с аргументом `migrate`. Таблица `lab_schema_migrations` хранит применённые версии, а advisory lock сериализует конкурирующие Job. Миграции и запись версий выполняются в одной транзакции; повторное применение версии пропускается. Новые миграции выбираются по имени файла в порядке сортировки. Неудачный лабораторный Job сначала создаёт обычную таблицу `public.lab_migration_rollback_probe` внутри той же транзакции, затем выполняет заведомо неверный SQL. Признак отката — отсутствие этой таблицы после ошибки при сохранении исходной записи и таблицы версий; он подтверждён в [опыте на чистом образе](../verification/database-migrations.md). Контрольная таблица должна отсутствовать до опыта; при её наличии Job отказывается продолжать, не удаляя существующий объект. `backoffLimit: 0`, `activeDeadlineSeconds: 90`; журнал Job сохраняется до TTL 24 часа и должен быть собран заранее.

## Резервное копирование

`task db-backup` запускает `pg_dump -Fc` в контейнере, но направляет поток в игнорируемый файл хоста `.local-db/backup.dump`; в файловой системе проверяемого Pod архив не создаётся. Повторная запись файла запрещена. `task db-restore` создаёт отдельную базу `lab_restore` в том же экземпляре, применяет архив `pg_restore --exit-on-error` и проверяет наличие контрольной записи; точное значение проверяется отдельным запросом при выполнении сценария. Восстановление состояния на момент копирования подтверждено [локальным опытом](../verification/database-backup-restore.md). Это изоляция на уровне базы, не отказоустойчивая копия и не проверка восстановления после потери узла. Целевая база удаляется только отдельной командой; основная база и PVC не удаляются.

Сценарии и результаты находятся в `docs/verification/postgresql-statefulset.md`, `persistent-storage-recovery.md`, `database-dependency-failure.md`, `database-migrations.md` и `database-backup-restore.md`. Все пять отчётов имеют статус `Passed` в границах локальных проверок. При недоступной БД API потерял готовность, сохранил жизнеспособность и восстановил чтение без перезапуска. Неверный пароль отдельного release дал отличимую причину `authentication_failed`, не нарушив чтение рабочего API. Отрицательная миграция откатила создание контрольной таблицы; следующий Job завершился успешно. Восстановленная база содержала `before-backup`, рабочая база сохранила `after-backup`, тестовая база затем удалена. Финальная регрессия базового API также подтверждена: при PostgreSQL `0/0` новый образ ответил через Service и сохранил готовность, затем БД восстановлена до `1/1`. Дополнительный опыт подтвердил `CreateContainerConfigError` при отсутствующем Secret, `schema_missing` при отсутствии таблицы и восстановление готовности после применения SQL только к тестовой базе. Успешные результаты Go-проверок после изменения отрицательной миграции владелец предоставил 25 октября 2026 года; они сохранены в отчёте о миграциях.
