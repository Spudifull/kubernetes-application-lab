# Обзор проекта

Kubernetes Application Lab — отдельный учебный стенд для развёртывания серверного приложения в Kubernetes.

Его задача — сделать навыки проверяемыми. Наличие объекта `Deployment` или Helm chart само по себе не доказывает понимание Kubernetes; проект должен связывать конфигурацию с наблюдаемым поведением под нагрузкой и при отказах.

## Что находится в центре стенда

Минимальное Go-приложение используется как управляемый `workload`.

На первом этапе достаточно HTTP API с:

```text
GET /livez
GET /readyz
GET /metrics
GET /version
```

Позднее добавляются ограниченные механизмы создания задержки, нагрузки на CPU и память, а также фоновый `worker`. Эти механизмы нужны только для воспроизводимых лабораторных сценариев.

## Целевая схема

```text
                    клиент
                       |
                       v
                Gateway / Ingress
                       |
                       v
                     API
                  /       \
                 v         v
           PostgreSQL     очередь
                           |
                           v
                         worker
```

Эта схема является `Target`. На первом этапе база данных и очередь отсутствуют.

## Принцип наращивания сложности

```text
приложение
→ контейнерный образ
→ kind
→ базовые ресурсы Kubernetes
→ Helm
→ корректное обновление и завершение
→ ресурсы и масштабирование
→ сеть и права доступа
→ состояние и фоновые задания
→ наблюдаемость
→ CI/CD и GitOps
→ Terraform и kubeadm
→ сценарии отказов уровня узла и кластера
```

Terraform, Argo CD, `kubeadm`, KEDA и стек наблюдаемости не добавляются заранее.

## Что проект не пытается доказать

Стенд не является дистрибутивом Kubernetes, корпоративной платформой разработки, полноценной системой высокой доступности PostgreSQL или демонстрацией всех проектов CNCF.

Он должен показывать широкое и технически точное понимание поведения серверного приложения в Kubernetes и достаточную глубину для диагностики типовых проблем.

## Публичный снимок Milestones 1–8

Снимок включает PostgreSQL, Kafka/outbox/worker, KEDA/CronJob и наблюдаемость Prometheus/Grafana/Loki/Tempo/Alertmanager. Начать со stateless API по README; дополнительные профили включаются отдельно. Исторические доказательства и исключённые материалы описаны в docs/provenance.md.
