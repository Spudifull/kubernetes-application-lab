# Обзор проекта

Kubernetes Application Lab — учебный стенд для проверки поведения серверного приложения на Go в Kubernetes. Проект объединяет программный код, конфигурацию инфраструктуры, сценарии управляемых отказов и результаты наблюдений.

Его основная задача — установить связь между настройками системы и их фактическим действием. Например, успешное обновление `Deployment` ещё не доказывает отсутствие ошибок у клиентов, а готовность `Pod` сама по себе не подтверждает доступность приложения через `Service`.

## Как устроен стенд

В центре проекта находится Go-приложение с HTTP API. В базовом профиле оно работает без PostgreSQL и Kafka, что позволяет отдельно исследовать запуск контейнера, проверки готовности, обновление и завершение процесса, не добавляя зависимостей, которые не нужны конкретному опыту.

Дополнительные профили расширяют систему:

| Компонент | Назначение |
|---|---|
| PostgreSQL | Хранение заданий, результатов обработки и записей transactional outbox. |
| Сервис публикации событий | Передача записей из PostgreSQL в Kafka с возможностью повторной публикации после сбоя. |
| Kafka | Передача событий обработчикам заданий. |
| Обработчик заданий | Сохранение результата в PostgreSQL до подтверждения смещения Kafka; защита от повторного применения эффекта. |
| CronJob и KEDA | Запуск заданий по расписанию и масштабирование обработчиков в отдельных лабораторных сценариях. |
| Prometheus, Grafana, Loki, Alloy, OpenTelemetry и Tempo | Сбор и сопоставление метрик, журналов и трассировок. |
| Alertmanager | Проверка условий срабатывания оповещений и восстановления после отказов. |
| CI/CD и Argo CD | Проверки образов API, publisher и worker, публикация проверенного образа API и развёртывание одного digest в двух лабораторных окружениях. |

Связи между основными компонентами показаны в [README проекта](../README.md#архитектура). Подробное описание распределения ответственности находится в разделе [системной архитектуры](architecture/system-architecture.md).

## Разделение ответственности

Стенд различает четыре уровня, каждый из которых отвечает за свои свойства.

**Приложение** определяет HTTP-интерфейс, прикладную готовность, завершение принятой работы, операции с данными и обработку повторных событий.

**Контейнер** задаёт состав исполняемой среды, пользователя процесса, доступ к файловой системе и точку входа.

**Kubernetes** управляет желаемым числом реплик, проверками работоспособности, маршрутизацией через `Service`, обновлениями, ресурсными ограничениями и политиками доступа. Нл механизмы нужно проверять по наблюдаемому поведению, а не только по успешному применению манифестов, для чего и проводились отдельно эксперименты.

**Инфраструктура кластера** обеспечивает вычислительные узлы, сеть и хранилище. Основные проверенные сценарии выполнялись в локальном `kind`. В рамках одного из этапов дополнительно подготовлен трёхузловой `kind` на одном хосте с раздельными экспериментами планирования, обслуживания узлов и сетевых политик. Также был поднят кластер из отдельных виртуальных машин с `kubeadm` и управление инфраструктурой через Terraform и Ansible.

См. также [эксплуатационную архитектуру](architecture/operational-architecture.md) и [принятые решения](adr/README.md).

## Как развивался проект

Сложность добавлялась по мере появления проверяемых задач, изучение определенных тем и технологий.

| Этап | Основное содержание |
|------|---|
| 1–3  | Go API, контейнеризация, локальный кластер, Helm, обновление, откат и управляемое завершение. |
| 4–5  | Ограничение ресурсов, масштабирование, диагностика сетевого взаимодействия и политики безопасности. |
| 6    | PostgreSQL, постоянное хранилище, миграции и восстановление. |
| 7    | Kafka, transactional outbox, обработчик заданий, повторная доставка, DLQ, CronJob и KEDA. |
| 8    | Метрики, журналы, трассировки, панели Grafana и оповещения. |
| 9    | Проверки CI и трёх контейнерных образов, публикация API в GHCR, контроль уязвимостей и перенос того же digest между окружениями через Argo CD. |
| 10   | Трёхузловой `kind`, сценарии размещения, обслуживания узлов, управляемых отказов и `NetworkPolicy` с Calico. |

Для каждого механизма объём фактической проверки определяется его [отчётом](verification/README.md).

## Как подтверждаются результаты

В проекте различаются четыре уровня проверки:

1. **Статическая проверка:** исходный код проходит тесты, а конфигурация позволяет сформировать манифесты.
2. **Развёртывание:** кластер принимает ресурсы, и компоненты переходят в ожидаемое состояние.
3. **Проверка доступности:** клиент обращается к приложению через тот сетевой путь, который требуется проверить.
4. **Сценарный эксперимент:** создаётся нагрузка или управляемый отказ, сохраняются наблюдения и проверяется восстановление.

Каждый уровень подтверждает только соответствующие ему свойства. Например, успешный `helm upgrade` не проверяет, что во время обновления клиент не получил ошибку HTTP.

Порядок выбора проверок описан в [стратегии проверки](engineering/verification-strategy.md). Инструкции для повторного запуска находятся в [инженерном разделе](engineering/README.md), а наблюдавшиеся результаты — в [каталоге проверок](verification/README.md).

## Ограничения

Основные эксперименты проведены в одноузловой лабораторной среде. 

Проект не предназначен для подтверждения высокой доступности, полной защиты многопользовательской платформы или готовности к промышленной эксплуатации.
