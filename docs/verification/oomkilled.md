## Цель

Воспроизвести завершение отдельного контейнера из-за превышения memory limit, отличить `OOMKilled` от `Evicted` и проверить, что Helm release API продолжает обслуживать `Service`.

## Исходные условия

Перед изменениями проверить Kubernetes context и состояние выделенного кластера. Основной release должен иметь готовые Pod и успешный `task smoke`. Выполнить Go-тесты, тесты с детектором гонок и `go vet ./...`, затем собрать и загрузить клиентский образ из чистой Git-ревизии командой `task rollout-client-build`. Выполнить `task resources-oom-validate` для серверной проверки манифеста до создания Pod. Клиентский образ основан на `scratch`; внутри нет shell. Для опыта Pod имеет `restartPolicy: Never`, `activeDeadlineSeconds: 90`, request `10m` CPU и `16Mi` памяти, limit `100m` CPU и `64Mi` памяти. Профиль API и его limits не меняются.

## Способ создать нагрузку или отказ

Выполнить `task resources-oom-start`, затем `task resources-oom-wait` и `task resources-oom-status`. Единственный контейнер клиента запускается с `-mode=memory -memory-mib=96 -memory-hold=15s`. Бинарный файл выделяет не более 128 MiB по контракту, в этом опыте — 96 MiB, обращается к каждой странице памяти и сохраняет буфер живым во время ограниченного ожидания. Если контейнер переживёт выделение, он штатно завершится в пределах 15 секунд; такой исход нужно сохранить как фактический, а не назвать OOM. Общий срок Pod ограничен 90 секундами.

До удаления записать точный image ID контейнера из состояния Pod, конфигурацию ресурсов, `status.phase`, `status.reason`, `status.containerStatuses[].state.terminated.reason`, `exitCode`, отметки времени, события из `kubectl describe` и доступный журнал. По возможности отдельно снять фактическое потребление памяти во время опыта; отсутствие такого измерения не заменять предположением. После сохранения доказательств выполнить `task resources-oom-cleanup`, `task rollout-status` и `task smoke`.

## Ожидаемые признаки

Pod переходит в `Failed`, у завершённого контейнера указано `reason: OOMKilled`; `exitCode: 137` может быть дополнительным признаком. Основные API Pod остаются Ready, запрос через `Service` после опыта проходит. Поле `reason: Evicted` или `DeadlineExceeded` не удовлетворяет критерию OOMKilled.

## Диагностика

При неуспешном `resources-oom-wait` сначала выполнить `resources-oom-status`, не удаляя Pod. Если контейнер завершился штатно, проверить фактический limit, аргументы и состояние Pod; не увеличивать выделение сверх заданной границы без отдельного решения. Если Pod не запустился, проверить `Pending`, `ImagePullBackOff`, ограничения безопасности и события планировщика. Если указан `Evicted`, исследовать давление памяти узла, не смешивая его с превышением cgroup limit контейнера.

## Причина

Наблюдаемая причина завершения — `OOMKilled` отдельного контейнера при memory limit `64Mi` и заданном выделении `96Mi`. Программа обращается к страницам буфера и при штатном ходе удерживает его через `runtime.KeepAlive`, но журнал не содержит события о завершении касания всех страниц: точный достигнутый объём памяти не измерен. `exitCode: 137` согласуется с причиной, но сам по себе её не устанавливает. Исход не является `Evicted` Pod или `DeadlineExceeded`.

## Восстановление

Этот Pod имеет `restartPolicy: Never` и не перезапустился (`restartCount: 0`). После сохранения статуса и журнала пользователь удалил его явно. Основной `Deployment` не подвергался намеренному превышению памяти; после опыта подтверждены `2/2` Ready и успешный запрос через `Service`. Автоматическое восстановление контейнера в управляемом `Deployment` данным опытом не проверялось.

## Поведение Kubernetes

Kubernetes принял манифест, разместил Pod, запустил контейнер и сохранил `OOMKilled` в состоянии его завершения. Лимит `64Mi` присутствует в сохранённом состоянии Pod. В предоставленном выводе нет признака `Evicted`; наблюдение относится к ограничению контейнера, а не к доказательству поведения узла при общем давлении памяти.

## Поведение приложения

Основной API не имеет маршрута выделения памяти и не принимает экспериментальную опасную нагрузку. Временный клиент выделяет ограниченный буфер, затрагивает страницы, затем удерживает его не более 15 секунд при штатном ходе и освобождает с завершением процесса.

## Что результат подтверждает

В этом одноузловом `kind` отдельный контейнер с memory limit `64Mi` завершился с `reason: OOMKilled` при ограниченной попытке выделить `96Mi`, не перезапустился при `restartPolicy: Never`, а основной Helm release после опыта сохранил две Ready-реплики и ответил через `Service`.

## Что результат не подтверждает

Фактический пик памяти и полное касание всех `96Mi` страниц, автоматический перезапуск контейнера в `Deployment`, устойчивость к общему давлению памяти узла, производственный подбор memory limit и отсутствие влияния на другие процессы узла при более крупных опытах. Снимок доступности после опыта не доказывает непрерывную доступность во время его выполнения.

## Остаточный риск

Go runtime, кэш страниц и распределение памяти узла влияют на момент завершения. Журнал после OOM неполон; первичным доказательством остаётся `terminated.reason`. В предоставленном выводе не зафиксированы версия Kubernetes и результаты Go-тестов этого commit. Причины пяти прежних перезапусков API Pod требуют отдельной диагностики и не установлены этим сценарием.
