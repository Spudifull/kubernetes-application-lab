# Kafka worker: эффект, offsets и завершение

- Статус: `Passed` в границах третьей итерации Milestone 7.
- Дата: 25 октября 2026 года; времена ниже — UTC.
- Ревизия worker и сценариев: `858f2ee181e43afc83c3558a95b39834f44f1ca8`.
- Среда: Windows PowerShell, основной kind `kind-kubernetes-application-lab`, Kubernetes 1.34, namespace `kubernetes-application-lab`; Kafka находится в `kubernetes-application-lab-kafka`.
- Контракт: [Kafka и обработка заданий](../design/kafka-event-processing.md); воспроизведение — [порядок проверки](../engineering/kafka-worker-lab.md).

## Цель

Проверить путь новой заявки до SQL-результата, ручной offset commit после результата, дедупликацию повторно опубликованного события, распределение трёх partitions между двумя worker и завершение уже принятой восьмисекундной работы при SIGTERM. Это не закрытие всего Milestone 7.

## Способ создать нагрузку или отказ

Использованы задачи Taskfile: одиночный enqueue через API port-forward, намеренный replay прежнего события отдельным диагностическим клиентом с publisher identity, batch из 12 разных заявок, переход Helm release worker между одной и двумя репликами, затем остановка единственной реплики во время принятой восьмисекундной работы. Журнал остановленного Pod сохранён через `Tee-Object` до его удаления.

Диагностика группы не вступает в группу и не меняет offsets. Топики, offsets, задания и PVC не удалялись ради прохождения сценария.

## Диагностика, причина и история неуспешных попыток

Первые HTTP enqueue/get/batch не достигали приложения: `127.0.0.1:18081` отказывал в TCP-соединении из-за отсутствующего либо завершённого port-forward. Worker при этом обрабатывал сохранённые Kafka-события, а replay использовал прежний locator, поскольку новый enqueue не состоялся. После запуска port-forward свежий enqueue и batch прошли. Повторный запуск port-forward при занятом порте отдельно отказал в bind; исправления Kafka или удаления данных не требовалось.

Первая длинная заявка `d0edfa98-4cd3-4933-b98f-5a7f3b6a4672` завершилась и подтвердила offset в 13:39:30, а запрос завершения пришёл только в 13:39:44. Этот прогон не засчитан как завершение работы при SIGTERM. Следующая заявка `f2ccfe3e-fbd5-400f-9de0-269dece8f6da` завершилась успешно и имела один эффект, но журнал остановленного Pod не был сохранён; время Helm не принято за доказательство получения SIGTERM. Автоматическое ожидание `worker_work_started` и предварительное сохранение журнала дали приведённый выше достаточный повтор. Первые неуспешные попытки не скрыты успешным итогом.

## Поведение Kubernetes и приложения

Kubernetes изменял число реплик через Helm, назначал Pod, проверял готовность и инициировал завершение процесса; он не управлял SQL-транзакцией или Kafka commit. Kafka/client protocol распределял partitions, сохранял групповые offsets и позволял восстановленной реплике продолжить с них.

Приложение ограничивало работу, сохраняло SQL-результат до Kafka commit, распознавало повтор по надёжному эффекту и завершало принятую операцию после запроса остановки. Readiness сама по себе не является механизмом остановки consumer.

## Что результат подтверждает

- Работу чистого образа worker указанной ревизии с mTLS Kafka и существующей PostgreSQL.
- Один SQL-эффект на каждую из 19 наблюдавшихся заявок и дедупликацию намеренно повторно опубликованного события.
- Наблюдаемый порядок SQL-эффект → ручной commit следующего offset.
- Штатное распределение 2+1 и обработку batch обоими worker после rebalance.
- Завершение принятой восьмисекундной работы при остановке Pod, commit до выхода и восстановление одной готовой реплики.
- Очистку временных диагностических Pod и успешную регрессию API/состояния БД.

## Что результат не подтверждает и остаточный риск

Не проверены авария после SQL commit до Kafka commit, повторная доставка именно после такого падения, исчерпание конечных retry, DLQ, повреждённое событие, реальный broker outage, потеря assignment во время работы, SQL fencing по Kafka epoch, HA/потеря диска и CronJob. Exactly-once delivery не заявляется. Полный Milestone 7 остаётся незавершённым.

Pod UID в предоставленных worker-журналах не зафиксированы; сопоставление выполнено по именам Pod, client/member ID, образу и времени. Снимки offsets/log end раздельные, не атомарные. Неизменность result/completed_at дубликата установлена изолированным SQL-тестом, но не HTTP-снимком runtime-replay. NetworkPolicy в основном kind не считается доказанной изоляцией без проверки исполнения CNI.
