# Лабораторный сценарий: переносимость исполняемых проверок

- Статус: `Passed` для переноса публичных проверок на Go и их выполнения в Windows; запуск на Linux и macOS не проверен
- Ревизия Go CLI и Taskfile: `923695555153801027f3eb3448fe4ed767967aa9`; исходная основа изменений — `fe61a2359d47a2e75e304df06b1d12f712c26de8`
- Среда статических проверок: Windows, Go 1.26; сборка `labctl` для Windows/amd64, Linux/amd64, macOS/amd64 и macOS/arm64 выполнена без запуска на Linux и macOS
- Проверяемый контракт: [локальная разработка](../engineering/local-development.md) и [стратегия проверки](../engineering/verification-strategy.md)

## Цель и граница

Убрать зависимость публичных задач `Taskfile.yml` от Windows PowerShell. Условия, циклы, Kubernetes JSON и создание временных Pod выполняет `cmd/labctl/` через `context` и контролируемые вызовы установленных `kubectl`, `helm`, `kind` и Docker. Простые декларативные задачи остаются в Taskfile. CLI принимает явные `--context` и `--namespace`; изменение объектов требует проверки текущего контекста. Ни один сценарий не удаляет кластер или namespace автоматически.

Мигрированы пять исходных сценариев `inflight-work`, `observe-hpa`, `observe-rollout`, `rollout-probes` и `scheduling`. Также Go CLI заменяет прежние PowerShell-вызовы NetworkPolicy, Gateway, RBAC и Pod Security. При переносе старые файлы `.ps1` служили контрольными версиями; после проверки публичных задач они удалены из текущего дерева. Исторические отчёты `Passed` относятся к прежнему механизму и сами по себе не подтверждают поведение новых команд.

## Ожидаемые признаки

Названия задач `task` сохраняются. `inflight-work` не удаляет API Pod без совпадения события `work_started` и `run_id`; прямые наблюдатели подтверждают исходное `Ready`. Снимки Pod, `EndpointSlice` и HPA пишутся в NDJSON с временем UTC. Временные ресурсы сохраняются до явной команды очистки. Неожиданный код внешней команды приводит к ненулевому завершению CLI. Вызов из неверного текущего контекста отклоняется до изменения Kubernetes.

## Проверка Gateway probe через Go CLI

После commit `9236955` владелец запустил перенесённые `gateway-http-test`, `gateway-tls-test` и `gateway-negative-test` в выделенном сетевом кластере. В 00:25:27–00:25:30 UTC 19 октября 2026 года Go CLI сохранил UTC-события: HTTP и HTTPS `/version` вернули `200`, `X-Lab-Pod: lab-api-799899df5f-c7lp8` и ревизию приложения `92cf68d43214`; неизвестный hostname и несопоставленный путь вернули `404` без заголовка приложения. HTTPS без лабораторного CA был отвергнут с `unknown_authority`, как и ожидалось. Образ API был собран из прежней чистой ревизии `92cf68d`, а проверяемый Go CLI — из commit `9236955`; пересборка API для проверки клиента не требовалась.

После серверной проверки и создания двух диагностических `HTTPRoute` команда `gateway-negative-test` в 00:27:55 UTC получила `ResolvedRefs=False/BackendNotFound` и HTTP `500` для отсутствующего Service, `Accepted=False/NoMatchingParent` и HTTP `404` для отсутствующего listener. В обоих ответах не было `X-Lab-Pod`. `gateway-negative-status` сохранил условия ресурсов и журнал Envoy Gateway: контроллер не нашёл `Service/lab-api-does-not-exist` и настроил прямой ответ `500`. Эти данные подтверждают работу перенесённых Go-проб в данном стенде; их подробная трактовка остаётся в [отчёте Gateway](gateway-routing-tls.md).

Первые пробы использовали уже работавший `kubectl port-forward`: попытка запустить новый `task gateway-forward` завершилась отказом привязки, поскольку оба локальных порта `18080` и `18443` уже занимал прежний процесс `kubectl` (PID 53264). После освобождения портов владелец запустил новую Go-команду: она сообщила `Forwarding from 127.0.0.1:18080 -> 10080` и `Forwarding from 127.0.0.1:18443 -> 10443`, затем обработала три соединения на `18080`. Одновременный повтор `gateway-http-test` в 00:35:09 UTC получил `200` для `/version` и два ожидаемых `404`. В 00:36:51 UTC через тот же проброс `gateway-tls-test` получил HTTPS `200` с `X-Lab-Pod` и ревизией `92cf68d43214`, а без лабораторного CA — ожидаемый `unknown_authority`; окно проброса показало два соединения на `18443`. Таким образом, HTTP- и HTTPS-пути нового проброса подтверждены клиентскими ответами. После части соединений в журнале появились ошибки `wsarecv` об удалённом закрытии локального соединения; причина закрытия не установлена, но соответствующие клиентские пробы завершились с ожидаемыми результатами. После сохранения статусов владелец выполнил `gateway-negative-cleanup`: команда `kubectl delete ... --ignore-not-found=true --wait=true` завершилась без ошибки, но её вывод не различает удаление существовавших маршрутов и их отсутствие до вызова; отдельный снимок отсутствия ресурсов не предоставлен.

## Диагностика, восстановление и остаточный риск

При сбое нового сценария сохранить stdout/stderr, соответствующие `task *-status`, Kubernetes Events и журналы временных Pod до очистки. Сравнить с историческим результатом `.ps1` по порядку действий и сигналам. `gateway-forward` ограничен 30 минутами; если проба выполняется позже, запустить проброс заново и проверить его вывод. Не считать статические Go-тесты, успешный Helm render или кросс-компиляцию доказательством сетевого запрета, TLS, RBAC, Pod Security либо работы сценария на другой ОС.

Перенос публичных проверок подтверждён выполнением в Windows и отсутствием вызовов PowerShell в `Taskfile.yml`. Работа собранного CLI на Linux и macOS не подтверждена запуском; кросс-компиляция не заменяет такую проверку. Контрольные `.ps1` удалены; очистка временного каталога с закрытыми ключами и полная регрессия Milestones 1–5 остаются отдельными задачами.
