# Лабораторный сценарий: миграция и безопасный отказ Job

- Статус: `Passed` для повторного применения на существующей схеме, отката контрольной таблицы при SQL-ошибке и успешного следующего Job
- Ревизия выполнения: `803c1bc2363cc9a7a1fa2170308de46d190eb8e1`, чистое дерево перед сборкой; образ Job `kubernetes-application-lab-api:1f35ec63d00add6a7c548305b83a3a78a98d89b90ec083018655d5db04a4d00f`; runtime imageID Job отдельно не снят
- PostgreSQL: `postgres:16.14-bookworm`, imageID сохранён в [отчёте запуска](postgresql-statefulset.md); основной API продолжал использовать прежний образ `df935dc5bf08`
- Среда: Windows PowerShell, одноузловой `kind`, Kubernetes `v1.34.0`, StorageClass `standard`; ресурсы: StatefulSet/Service/PVC PostgreSQL и Job `lab-db-migration-*`
- Контракт: [PostgreSQL и сохраняемое состояние](../design/postgresql-stateful-storage.md)

## Цель и исходные условия

Проверить создание схемы отдельным Job, пропуск уже применённой версии и откат транзакции при неверном SQL. До прогона записать чистый Git SHA, готовность PostgreSQL, состояние PVC и отсутствие/состав таблицы версий.

## Процедура

1. `task image-build`, затем `task db-migrate`; сохранить имя Job, `task db-migrate-status`, `kubectl ... logs job/ИМЯ_JOB --timestamps`, `kubectl ... describe job ИМЯ_JOB`.
2. Повторить `task db-migrate` с новым именем Job и проверить `Complete` без повторного применения версии.
3. До отрицательного опыта убедиться, что `to_regclass('public.lab_migration_rollback_probe')` и `to_regclass('public.lab_intentionally_missing_table')` возвращают NULL; сохранить строки `lab_schema_migrations` и контрольную запись. Существующие одноимённые объекты не удалять автоматически.
4. Запустить `task db-migrate-fail` на новом образе с контрольной таблицей; дождаться `Failed`, сохранить Job, Pod, exit code и журнал до TTL-очистки. Ожидаемое сообщение `intentional migration failed after rollback probe creation` означает, что контрольная таблица была создана в транзакции до SQL-ошибки. Ошибка `migration rollback probe setup failed` не подтверждает этот путь.
5. Повторить проверку отсутствия `public.lab_migration_rollback_probe`, сравнить строки `lab_schema_migrations` и прочитать исходную запись. Затем выполнить обычный `task db-migrate` и проверить чтение/запись через API. Сочетание подтверждённого создания контрольной таблицы до ошибки и её отсутствия после завершения Job служит наблюдаемым признаком отката.

## Ожидаемые признаки

Первый и повторный Job достигают `Complete`; отрицательный Job получает ненулевой exit, не оставляет контрольную таблицу и сохраняет исходную запись и версии миграций. Контрольная таблица является обычной таблицей PostgreSQL, а не TEMP-объектом с автоматическим удалением при закрытии соединения. Все Job имеют один Pod, `backoffLimit: 0`, срок 90 секунд; advisory lock сериализует применение по реализации, конкурентный опыт не выполнялся.

## Наблюдение, диагностика и причина

24 октября 2026 года первичный Job `lab-db-migration-20261024145226` завершился `Complete` на предварительном образе `c2bb01cb7ccf-dirty` и записал `migration_completed`. После чистой сборки `df935dc5bf08` повторный Job `lab-db-migration-20261024150445` также достиг `Complete`; API прочитал существующую запись. Эти положительные результаты не доказывают откат отрицательной миграции.

После этих прогонов отрицательная ветвь усилена: перед заведомо неверным SQL она создаёт `public.lab_migration_rollback_probe` в той же транзакции. Раньше на уже применённой схеме Job мог завершиться ошибкой без предшествующего изменения, поэтому неизменность данных не различала наличие и отсутствие отката.

Владелец зафиксировал изменение в commit `803c1bc2363cc9a7a1fa2170308de46d190eb8e1`, показал пустой `git status --short` и собрал образ с `REVISION=803c1bc2363c` без `-dirty`. До опыта API прочитал `storage-proof=before-restart`; таблица версий содержала одну строку `001_lab_records`. Проверки отсутствия контрольной таблицы и заведомо отсутствующей таблицы вернули `t/t`.

| Job | Результат | Наблюдение |
|---|---|---|
| `lab-db-migration-20261024155501` | `Complete`, `1/1` | В 15:55:01.825 UTC журнал содержит `migration_completed` |
| `lab-db-migration-20261024155514` | `Failed`, exit code `1` | В 15:55:14.792 UTC журнал содержит `intentional migration failed after rollback probe creation` |
| `lab-db-migration-20261024155544` | `Complete`, `1/1` | Следующий обычный Job после отрицательного опыта завершился успешно |

`describe` отрицательного Job показал UID контроллера `e05b1ed6-4647-4ae0-9042-6d026ceb035a`, один неуспешный Pod `lab-db-migration-20261024155514-5z5bs`, `backoffLimit: 0`, `activeDeadlineSeconds: 90` и TTL 86400 секунд. Events содержали `SuccessfulCreate` и `BackoffLimitExceeded`; автоматического повторного запуска после SQL-ошибки не было. Все три Job использовали новый образ `1f35ec63...`.

После завершения отрицательного Job запрос `to_regclass('public.lab_migration_rollback_probe') IS NULL` вернул `t`. Сообщение ошибки в проверенной ветви кода возникает после успешного создания обычной контрольной таблицы внутри транзакции; её последующее отсутствие подтверждает откат этой операции. Таблица версий по-прежнему содержала только `001_lab_records`, API снова прочитал `storage-proof=before-restart`. PostgreSQL откатил транзакцию, Kubernetes сохранил неуспешный результат Job, а следующий явный Job успешно завершился.

Ошибка Job до подключения к БД или при создании контрольной таблицы не доказала бы этот путь; в данном прогоне зафиксировано именно намеренное падение после создания. Первичная инициализация пустой схемы через Job на чистом образе `803c1bc` отдельно не выполнялась. Поведение API при отсутствии таблицы и после её создания проверено дополнительным опытом ниже. Конкурентное выполнение миграций, произвольные будущие миграции и совместимость схемы с обновляемым API этим опытом не проверены.

## Дополнительный опыт API без таблицы

25 октября 2026 года по московскому времени владелец проверил чистую отдельную базу `lab_schema_probe` через release `lab-api-badcred` revision 2. После исправления ссылки на Secret процесс API запустился в 02:23:16 по Москве (24 октября, 23:23:16 UTC) с ревизией `803c1bc2363c`; с 23:23:18 UTC журнал содержал `database_readiness_rejected` с `reason=schema_missing`. Pod `lab-api-badcred-79b9d5885c-dbpxl` находился в `0/1 Running` без перезапусков. Это отличает отсутствие таблицы от ранее проверенных `authentication_failed` и `database_unavailable`.

Прямые запросы через `127.0.0.1:18084` в 23:23:58–23:24:01 UTC дали `/livez: 200`, `/readyz: 503`, `/records/schema-proof: 503`. Все ответы содержали `X-Lab-Pod` выбранного экспериментального Pod. Затем владелец передал существующий `001_lab_records.sql` в `psql -d lab_schema_probe`; PostgreSQL подтвердил `CREATE TABLE`. Это отдельная проверка восстановления API после появления таблицы, не новый прогон миграционного Job или его таблицы версий.

После создания таблицы rollout успешно завершился, в 23:24:15 UTC тот же Pod вернул `/readyz: 200` и `/records/schema-proof: 404` с телом `record not found`. Последний ответ означает успешный запрос к существующей таблице при отсутствующем ключе. Pod достиг `1/1 Running`, `restartCount` остался нулевым. Во время rollout Kubernetes сохранял прежний Pod с отсутствующим Secret до готовности новой реплики; после восстановления схемы старая реплика была выведена из обновления.

Владелец удалил экспериментальный release, тестовую базу и ConfigMap. Запрос каталога вернул `probe_db_exists=f`, а основная база сохранила `backup-proof=after-backup` и `storage-proof=before-restart`. Финальный внутрикластерный smoke основного API получил ревизию `803c1bc2363c`, временный smoke Pod удалён; EndpointSlice показывал адрес `10.244.0.114`. В последнем снимке экспериментальный Pod ещё был `Terminating`; его окончательное исчезновение отдельно не подтверждено. Дополнительный read-only запрос агента к API кластера завершился отказом локального доступа к сокету, поэтому не используется как доказательство состояния Pod и не трактуется как отказ самого кластера.

Обе дополнительные ветви имеют статус `Passed` для диагностированных причин и восстановленных HTTP-ответов. Основные Secret и база данных не изменялись этим опытом. Применённый образ зафиксирован в чистой ревизии `803c1bc2363cc9a7a1fa2170308de46d190eb8e1`; текущий при разборе HEAD `902a8d16eeb918fcdf1ff9d2fdc473181eb81354` не отличался по Go-коду, файлам модулей или chart API, локальные изменения касались документации.

## Проверки Go после изменения отрицательной миграции

25 октября 2026 года владелец предоставил успешный вывод `go test ./...`, `go test -race ./...` и `go vet ./...`. Обычные тесты использовали кэш, race-прогон включал новые результаты `cmd/lab-client` и `internal/app` и кэш остальных проверенных пакетов. `cmd/api` и `internal/database` сообщили `[no test files]`; наличие выполненного SQL-опыта не подменяется заявлением об автоматических тестах этих пакетов. Vet не вывел ошибок. В присланном Go-выводе отдельного SHA нет; при разборе HEAD был `902a8d16eeb918fcdf1ff9d2fdc473181eb81354` с чистым деревом, а `cmd`, `internal`, `go.mod` и `go.sum` не отличались от зафиксированного кода `803c1bc2363c`.

## Восстановление и граница

После намеренной SQL-ошибки новый обычный Job завершился `Complete`; вмешательство в основную таблицу и PVC не требовалось. Job и Pod сохранены для доказательства до TTL-очистки. При непредусмотренном отказе сохранить журнал и состояние, исправить причину и создать новый Job. Успех не доказывает применимость произвольных будущих миграций и не заменяет проверку совместимости схемы при реальном обновлении API.
