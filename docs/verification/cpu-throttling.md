## Цель

При сопоставимой CPU-bound нагрузке сравнить задержку ответов и прямые счётчики ограничения процессорной квоты при CPU limits `1000m` и `100m`. Сначала установить версию cgroup в текущем контейнере.

## Исходные условия

Кластер выделен для лаборатории; проверить текущий контекст перед развёртыванием. Из чистого commit SHA собрать новый образ API и образ клиента. Проверить Go-тесты, `go test -race ./...`, `go vet ./...`, `task helm-lint`, `task helm-render`, оба `task helm-lint-cpu-*` и оба `task helm-render-cpu-*`. Основной Helm release должен быть готовым перед опытом. Оба CPU-профиля используют одну реплику, request CPU `100m`, request памяти `32Mi`, limit памяти `64Mi`; меняется только CPU limit (`1000m` или `100m`). Клиентский Pod имеет request `10m` CPU/`16Mi` памяти и limit `100m` CPU/`32Mi` памяти.

## Способ создать нагрузку или отказ

Для каждого профиля отдельно: выполнить `task deploy-cpu-high` либо `task deploy-cpu-low`, записать SHA из `/version`, ссылку на образ, Helm revision и имя Ready Pod. Снять первый `task resources-cpu-cgroup`; сохранить `cgroup_version`, `quota_us`, `period_us`, `usage_usec`, `nr_periods`, `nr_throttled` и `throttled_usec`. Выполнить `task resources-cpu-start`, затем `task resources-cpu-wait`. Клиент последовательно отправляет запросы `GET /cpu?units=50` через `Service` в течение 90 секунд с интервалом не меньше 100 мс и сроком одного запроса 10 секунд. После завершения выполнить `task resources-cpu-status` и повторный `task resources-cpu-cgroup`. Если ожидание неуспешно, сначала сохранить состояние и журнал Pod. Сохранить журналы и только затем выполнить `task resources-cpu-cleanup` перед следующим профилем.

Сравнивать разности накопительных счётчиков **внутри одного и того же Pod**. Новый профиль пересоздаёт контейнер и обнуляет его счётчики; абсолютные значения высокого и низкого профилей несопоставимы. `usage_usec` вместе с временем между снимками даёт приблизительную среднюю загрузку в ядрах для cgroup v2; для cgroup v1 эта версия маршрута не возвращает использование CPU, поэтому измерение потребует отдельного источника метрик. Клиент сохраняет все HTTP-статусы, ошибки, задержки отдельных ответов в микросекундах и итоговые счётчики. Если контрольная сумма или длительность оказывается неподходящей для среды, зафиксировать наблюдение до изменения параметров опыта.

## Ожидаемые признаки

Оба профиля возвращают `200` при допустимой нагрузке. Для низкого limit ожидается больший прирост `nr_throttled` и `throttled_usec` относительно числа периодов, а задержка сопоставимых запросов может вырасти. Для высокого limit ожидается меньший прирост. `kubectl top`, если доступен, показывает использование CPU, но не доказывает throttling.

## Диагностика

Если `/cpu-stat` возвращает `503`, сохранить `cpu_stat_unavailable` из журнала API и проверить наличие и доступность файлов cgroup в контейнерной среде; у образа `scratch` нет shell или `cat`. Если `nr_throttled` не растёт, проверить фактическую квоту, достаточность нагрузки, продолжительность опыта, имя Pod до и после и конкурирующую нагрузку узла. Если клиент получает `504`, вычисление достигло восьмисекундного срока и выбранный объём работы требует калибровки. `429` означает достижение ограничения параллелизма; он не является свидетельством CPU throttling.

## Причина

CPU limit задаёт квоту процессорного времени cgroup; при исчерпании квоты исполнение откладывается до следующего периода. Request влияет на планирование, но не является лимитом времени выполнения. При одинаковых `units=50` и request `100m` низкий limit исчерпывал квоту почти в каждом наблюдавшемся периоде (`899` из `902`), что согласуется с прямым ростом времени throttling и увеличением задержки. Высокий limit за те же `902` периода не дал такого сигнала. Различие нельзя объяснить только приближением использования CPU к limit: показаны именно счётчики квоты.

## Восстановление

После сохранения результатов явно удалить только клиентский Pod, вернуть исходный профиль командой `task deploy` или `task deploy-rollout` с нужным записанным образом и выполнить `task smoke`. Кластер и namespace не удалять автоматически.

## Поведение Kubernetes

Kubernetes применяет CPU limit контейнера через cgroup. Изменение Helm-профиля создаёт новый Pod. Успешная готовность нового Pod сама по себе не является доказательством действия квоты.

## Поведение приложения

Запрос `/cpu` потребляет CPU до завершения фиксированного объёма работы или до отмены/восьмисекундного срока. Одновременно выполняются не более двух заданий; в базовом профиле маршрут отсутствует.

## Что результат подтверждает

В выделенном одноузловом `kind` при этой последовательной нагрузке снижение CPU limit с `1000m` до `100m` привело к прямому росту счётчиков cgroup v2 throttling и примерно десятикратному увеличению средней задержки HTTP-ответа. Приложение продолжило возвращать `200` во всех наблюдавшихся запросах; профиль обновления после опыта был восстановлен и один `task smoke` прошёл.

## Что результат не подтверждает

Производственную настройку ресурсов, поведение на многоузловом кластере, рост пропускной способности от масштабирования, причину любой отдельной задержки без сопоставления с квотой и счётчиками.

## Остаточный риск

Вычислительная скорость узла, работа других процессов, накладные расходы сети и планировщика меняют задержку. Счётчики cgroup накопительные и могут отражать также диагностические запросы и probes; интерпретировать только их прирост и профиль нагрузки. Для cgroup v1 доступность путей и измерение использования CPU требуют проверки в конкретном кластере.
