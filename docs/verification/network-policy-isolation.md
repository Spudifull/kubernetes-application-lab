# Лабораторный сценарий: изоляция трафика NetworkPolicy

- Статус: `Passed` — для проверенных переходов `NetworkPolicy` на одном узле; отдельная проверка API после очистки не выполнялась
- Ревизия сценария и правил при успешном повторе: `df2bbdf1286ed0ef25017c2add006e679705fec7`; неизменившийся образ API собран из чистой ревизии `518e284a81a74cb2b2fd71c00df58572e8259780`
- Среда: выделенный `kind-kubernetes-application-lab-net`, Kubernetes v1.34.0, Cilium 1.20.3, namespace `kubernetes-application-lab-policy`
- Проверяемый контракт: [модель поставки](../design/deployment-model.md) и [стратегия проверки](../engineering/verification-strategy.md)

## Цель

Проверить, что Cilium действительно применяет стандартные `networking.k8s.io/v1 NetworkPolicy`, а не только принимает их объекты: запрет ingress к API, узкое разрешение выбранному клиенту, отдельный запрет egress клиента и поэтапное восстановление DNS и HTTP.

## Исходные условия

Основной API в namespace `kubernetes-application-lab` должен проходить `task network-smoke`. API опыта устанавливается тем же Helm chart, но отдельным release в namespace с `restricted`; основной release и исходный кластер не меняются. Использовать образ из известной чистой ревизии; если ревизия сценария новее, отдельно установить, что код API и его развёртывание не менялись. Сохранить SHA сценария и образа, версии компонентов, состояние Cilium, namespace, метки трёх клиентов, селекторы Service и API Pod, готовую конечную точку, а также отсутствие прежних NetworkPolicy в экспериментальном namespace.

## Способ создать отказ

После `task network-policy-deploy` выполнить `task network-policy-validate` и `task network-policy-clients-start`. `task network-policy-test` сначала сохраняет успешные DNS- и HTTP-запросы без политик. Затем он поочерёдно применяет отдельные правила: deny ingress на API, разрешение ingress двум выбранным ролям клиента, deny egress только у клиента `lab-policy-egress`, разрешение DNS к CoreDNS на TCP/UDP `53` и разрешение HTTP к API Pod на TCP `8080`.

Каждый переход проверяется реальным запросом с отметкой UTC, именем источника, адресом назначения, протоколом, HTTP-кодом и кодом завершения клиента. HTTP-проверка использует адрес `Service`, но подставляет его `ClusterIP` через `curl --resolve`, чтобы при проверке egress HTTP не спутать запрет HTTP с отказом DNS. DNS отдельно проверяется `nslookup` по абсолютному имени с завершающей точкой и только для записи A: это исключает дополнительные поисковые запросы BusyBox из проверки действия политики. После изменения правила выполняются ограниченные повторные попытки: первое наблюдение сохраняется, асинхронное применение политики не скрывается. При неожиданном результате скрипт останавливается и оставляет ресурсы для диагностики.

## Ожидаемые признаки

До правил оба ingress-клиента и egress-клиент получают `200`, DNS разрешает Service. После ingress deny оба ingress-клиента теряют HTTP-доступ при сохранении Ready API и конечной точки. После ingress allow только `lab-policy-allowed` получает `200`, а `lab-policy-blocked` остаётся заблокированным. Клиент egress имеет отдельное разрешение ingress, поэтому его последующие отказы локализуются на исходящем пути.

После egress deny у него не проходят DNS и HTTP. Разрешение DNS восстанавливает только DNS; HTTP всё ещё заблокирован. Отдельное разрешение к API Pod на TCP `8080` восстанавливает HTTP. Другой ingress-клиент остаётся заблокированным. Ни одна политика не выбирает API и клиентов основного namespace.

## Диагностика

В первом прогоне отсутствие `NetworkPolicy` исключило экспериментальные правила как причину тайм-аута. В повторном прогоне каждый отказ сопоставлялся с готовностью API и `EndpointSlice`, успешным исходным запросом и восстановлением после узкого разрешения. Само создание объекта `NetworkPolicy` не служило доказательством: решающими были ответы клиентов. Если `nslookup` отсутствует в образе клиента или API теряет Ready, отказ нельзя приписывать действию политики без дополнительной диагностики.

## Причина

Причина остановки первого прогона — несовместимость имени запроса с поведением BusyBox 1.37 `nslookup`: [его реализация](https://sources.debian.org/src/busybox/1:1.37.0-6/networking/nslookup.c/) не добавляет поисковые суффиксы к имени с точками, а при однословном имени отправляет запросы с несколькими суффиксами и возвращает ошибку при `NXDOMAIN` одного из них. Это дефект проверочной команды, а не доказательство отказа Kubernetes DNS или действия политики. Исправленная DNS-проба адресует одну запись A по абсолютному имени; обычное разрешение сокращённых имён приложением отдельно этим сценарием не проверяется.

Последовательность повторного прогона согласуется с применением Cilium правил `NetworkPolicy`: одни и те же клиенты теряли и возвращали доступ после изменения только соответствующего правила. Другого подтверждения внутреннего решения Cilium по отдельным пакетам этот журнал не содержит.

## Восстановление

Перед предварительным прогоном владелец успешно выполнил `task network-policy-cleanup`: прежние три клиента были удалены, прежних правил не было. После него очистка удалила три экспериментальных Pod и все пять `NetworkPolicy`, а `task network-smoke` успешно получил `/version` через основной Service в сетевом кластере. Этот smoke использовал основной образ с ревизией `07b537514363-dirty`, а не API второго namespace. После нового успешного прогона владелец вновь выполнил `task network-policy-cleanup`: вывод подтверждает удаление трёх новых клиентов и всех пяти новых правил. API release, namespace и оба kind-кластера не удалялись. Повторный `network-smoke` и запрос к отдельному API после этой очистки в новом журнале отсутствуют; восстановление HTTP-пути после очистки не входит в доказанный результат этого повторного прогона.

## Поведение Kubernetes

После каждого изменения правила Deployment и конечная точка API оставались готовыми. Kubernetes сохранил пять объектов `NetworkPolicy`; наблюдаемые отказы и восстановления соответствовали их селекторам и направлениям трафика. Проверки `kubelet` не равнозначны обычному трафику между Pod, поэтому их готовность использовалась только для исключения недоступности API.

## Поведение приложения

API не менялся и продолжал отдавать HTTP `200` разрешённым клиентам. Запрещённые запросы не достигали HTTP-ответа приложения: `curl` фиксировал превышение срока соединения и `http_code=000`, а не HTTP `403` или `503`.

## Что результат подтверждает

На зафиксированной версии сценария после commit наблюдались все запланированные переходы ingress/egress deny/allow для трёх выбранных клиентов на одном узле. Отдельное разрешение DNS восстановило только DNS, а разрешение к API затем восстановило HTTP. Экспериментальные Pod и правила были удалены. Это наблюдение для конкретных Pod, портов и Cilium 1.20.3, не гарантия для любого трафика.

## Что результат не подтверждает

Прогон не проверяет межузловую изоляцию, Gateway API, `hostNetwork`-трафик, все варианты DNS и внутреннее решение Cilium по каждому пакету. Тайм-аут `curl` подтверждает только отсутствие успешного соединения в данном окне.

## Остаточный риск

Новый прогон после commit подтвердил действие проверенных правил, но не абсолютную чистоту всего рабочего дерева на момент запуска: отдельные изменения Gateway уже находились в работе. Образ API остался собранным из прежней чистой ревизии, поскольку прикладной код и его манифесты для опыта не менялись. HTTP-доступ к API экспериментального namespace после последней очистки отдельно не проверялся. Статус `Passed` относится к изоляции и выборочному восстановлению трафика в рамках самого сценария, а не к этим непроверенным свойствам.
