## Цель

Проверить, что Helm владеет `Deployment` и `Service`, чистая установка создаёт готовый Pod, а новая ссылка на локальный образ приводит к обновлению release и шаблона Pod без принудительного перезапуска.

## Исходные условия

Рабочее дерево Git чистое. Кластер `kind` выделен для стенда и не содержит старых `Deployment/lab-api` и `Service/lab-api`, созданных через `kubectl apply`. Docker использует контейнеры Linux; установлены Task, Helm, `kind` и `kubectl`.

## Способ создать нагрузку или отказ

1. Создать чистый кластер через `task cluster-up` и собрать образ через `task image-build`. Записать точный Git SHA и первую ссылку из `.local-image-ref`.
2. Выполнить `task helm-lint` и `task helm-render`. Просмотреть сформированные kinds, имена, selectors, probes, ресурсы и ограничения безопасности.
3. Выполнить `task deploy`, `task helm-status`, `task status` и `task smoke`.
4. Проверить состояние `deployed`, аннотации `meta.helm.sh/release-name` и метку `app.kubernetes.io/managed-by` у `Deployment` и `Service`. Записать ревизию release, имя Pod, фактический `image`, состояние `EndpointSlice` и ответ `/version`.
5. Повторить `task deploy` без новой сборки и убедиться, что ссылка на образ и Pod template не изменились и не потребовалась замена Pod. Номер ревизии Helm может увеличиться и без изменения Pod template.
6. Повторить `task image-build`. Убедиться, что новая ссылка в `.local-image-ref` отличается от первой. Выполнить `task deploy`, `task helm-history`, `task status` и `task smoke`.
7. Сравнить ревизии release, образ в `Deployment` и новом Pod, имя Pod, готовность и ответ через `Service`.

## Ожидаемые признаки

1. `helm template` формирует только `Deployment` и `Service`, без `Namespace` и дополнительных ресурсов.
2. Оба ресурса имеют аннотации владения Helm release `lab-api`; `Namespace` сохраняет ограничения уровня `restricted`.
3. После установки Pod достигает Ready, `EndpointSlice` содержит готовую конечную точку, а `task smoke` получает ответ `/version` через DNS-имя `Service`.
4. Образ Pod совпадает с первой ссылкой из `.local-image-ref`; ревизия `/version` соответствует Git SHA без `-dirty`.
5. Повторное развёртывание без сборки не заменяет Pod из-за изменения только истории release.
6. Новая сборка меняет ссылку на образ, Helm history показывает новую ревизию, `Deployment` создаёт Pod с новым образом, новый Pod становится Ready, `task smoke` проходит.

Часть сценария выполнена 24 октября 2026 года на чистом commit `5d233c29e7ec345d24bc27113f897a6929226a41`: `task image-build` записал образ `kubernetes-application-lab-api:9a82a16f2f6074b23d914f84e3bee3f7f683257d1281725545a0ee31acb2b7d3`, `task deploy` обновил существующий Helm release до revision 27 и получил одну Ready-реплику. `task status` показал аннотации владения Helm у `Deployment`, `EndpointSlice` с адресом нового Pod, а `task smoke` вернул `/version.revision=5d233c29e7ec` через Service. Однако это было **обновление существующего release**, а не установка в чистый кластер. Повтор без новой сборки и затем обновление на второй отличимый образ в рамках данного сценария на тот момент не были подтверждены предоставленным выводом; до полного повтора отчёт имел статус `Prepared`.

## Диагностика

При ошибке сохранить вывод `task deploy`, `task helm-status`, `task helm-history`, описание `Deployment`, события Pod, его журналы, фактический `image` и состояние `EndpointSlice`. Ошибка Helm о существующем ресурсе без аннотаций владения означает, что переход со старой установки не выполнен.

## Причина

Helm сохраняет состояние release и связывает его с ресурсами. Новая ссылка на образ изменяет `spec.template` объекта `Deployment`; контроллер создаёт Pod с новым образом. Тег по ID собранного образа различает две локальные сборки, даже когда обе имеют один `/version.revision`.

## Восстановление

При неудачном обновлении зафиксировать состояние release и решить, использовать ли предыдущую ревизию через `helm rollback` или исправить chart/образ и повторить развёртывание. В этом опыте восстановление после отказа не потребовалось. Временный кластер можно удалить через `task cluster-down CLUSTER_NAME=kubernetes-application-lab-helm-check` после сохранения результатов. Базовый профиль API в данном кластере не использует постоянные данные; основной кластер с PostgreSQL удалять не нужно.

## Поведение Kubernetes

Сервер API принимает `Deployment` и `Service`; контроллер `Deployment` обеспечивает нужное число реплик и заменяет Pod при изменении шаблона; `Service` выбирает готовую конечную точку.

## Поведение приложения

Новый процесс проходит проверки запуска и готовности и возвращает `/version` из собранного образа.
