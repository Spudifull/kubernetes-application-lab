# Лабораторный сценарий: внутрикластерный путь через Service

- Статус: `Passed` — положительный путь через Service и отрицательный путь после удаления release
- Ревизия образа: чистый commit `5d233c29e7ec345d24bc27113f897a6929226a41`; `/version.revision=5d233c29e7ec`
- Среда: `kind` с образом узла Kubernetes v1.34.0; фактическую версию `kind` указать после выполнения
- Проверяемый контракт: [`../design/deployment-model.md`](../design/deployment-model.md)

## Цель

Проверить разрешение DNS-имени Service и HTTP-доступ от временного клиентского Pod через `ClusterIP Service` к готовому Pod приложения.

## Исходные условия

Образ собран из чистого commit. Helm release `lab-api` владеет `Deployment/lab-api` и `Service/lab-api`; соответствующий `EndpointSlice` содержит готовую конечную точку.

## Способ создать нагрузку или отказ

Выполнить `task smoke`. Задача создаёт временный Pod `lab-api-smoke`, который обращается к `http://lab-api.kubernetes-application-lab.svc/version`, выводит ответ и удаляется после завершения.

После фиксации доказательств установки и обновления в выделенном кластере проверить ошибку клиента: выполнить `task undeploy`, затем `task smoke`. Без `Service` запрос должен завершиться ошибкой, команда — ненулевым кодом, а временный Pod — отсутствовать после выхода Task. Восстановить среду через `task deploy` и повторить успешный `task smoke`. Эта отрицательная проверка сбрасывает историю прежнего release, поэтому её результаты следует записать до удаления release.

## Ожидаемые признаки

1. Pod создаётся с `restartPolicy: Never` и проходит ограничения namespace уровня `restricted`.
2. DNS разрешает имя `lab-api.kubernetes-application-lab.svc`.
3. HTTP-запрос завершается с кодом успеха.
4. `/version.revision` совпадает с проверяемым Git SHA.
5. `EndpointSlice` содержит готовую конечную точку приложения.
6. Временный Pod удаляется после выполнения.
7. При отсутствии `Service` задача завершается ошибкой и также удаляет временный Pod.

## Наблюдавшиеся признаки

8 октября 2026 года пользователь выполнил предварительный прогон на образе `f9e7b663af7a-dirty` и прежних YAML-манифестах. `task smoke` получил `{"version":"0.1.0","revision":"f9e7b663af7a-dirty",...}` через DNS-имя `Service`; `EndpointSlice/lab-api-95tbr` содержал адрес `10.244.0.2:8080`; временный Pod был удалён.

Положительный путь повторён 24 октября 2026 года на чистом commit `5d233c29e7ec345d24bc27113f897a6929226a41` после обновления Helm release до revision 27. `task smoke` создал временный Pod `lab-api-smoke`, получил `/version.revision=5d233c29e7ec` через DNS-имя Service, показал `EndpointSlice` с адресом единственной Ready-реплики и удалил клиентский Pod. После отдельного удаления этой реплики `task verify-recovery` снова получил тот же ответ через Service от её замены.

После сохранения полного цикла неисправного обновления и отката владелец зафиксировал Helm history до revision 31 и выполнил `task undeploy`. Helm сообщил `release "lab-api" uninstalled`. Следующий `task smoke` создал временный Pod, но ожидание успешного завершения истекло через 90 секунд; задача завершилась ненулевым кодом и своим отложенным действием удалила Pod. Отдельный `kubectl get pod lab-api-smoke --ignore-not-found` не вывел объект. Затем `task deploy` установил новый Helm release revision 1 в том же кластере: `Deployment` имел одну Ready-реплику, `Service` получил `ClusterIP 10.96.166.105`, `EndpointSlice` — адрес `10.244.0.99`; повторный `task smoke` вернул `/version.revision=5d233c29e7ec` и удалил клиентский Pod.

Отрицательный вывод подтверждает отказ задачи при удалённом release и очистку временного клиента; он не содержит журнал самого клиентского Pod, поэтому точный ответ DNS или текст сетевой ошибки в этом опыте не установлен. Это новая установка release в существующем кластере, а не чистая установка кластера из отдельного сценария Helm.

## Диагностика

При ошибке сохранить вывод `task smoke`; отложенное удаление убирает клиентский Pod и после неудачи. Для дополнительных данных наблюдать события и журналы в другом терминале во время запуска либо отдельно повторить диагностический запрос. Проверить DNS, selector `Service`, `targetPort`, метки Pod и условия `EndpointSlice`.

## Причина

Успешный запрос требует совместной работы Kubernetes DNS, поля `selector` объекта `Service`, `ClusterIP`, готовой конечной точки и HTTP-сервера приложения.

## Восстановление

Задача удаляет временный клиентский Pod после успеха и ошибки. После принудительного прекращения процесса Task проверить, не остался ли `Pod/lab-api-smoke`, и удалить его перед повтором.

## Поведение Kubernetes

Kubernetes должен разрешить DNS-имя `Service`, выбрать готовую конечную точку и направить TCP-соединение к порту `8080` контейнера приложения.

## Поведение приложения

Приложение должно вернуть JSON `/version` с данными собранного образа.

## Что результат подтверждает

Сценарий подтвердил внутрикластерный путь временный Pod → DNS → `ClusterIP Service` → готовая конечная точка → Pod приложения, отказ задачи после удаления release и восстановление ответа после новой установки.

## Что результат не подтверждает

Сценарий не подтверждает работу Ingress или Gateway API, внешнюю доступность, действие `NetworkPolicy` или отказоустойчивость.

## Остаточный риск

Образ временного клиента закреплён точным tag, но не digest. Его доступность зависит от Docker Hub при первом запуске в новом кластере.
