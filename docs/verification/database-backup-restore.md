# Лабораторный сценарий: резервная копия и восстановление

- Статус: `Passed` для логического архива на хосте и восстановления в отдельную базу того же экземпляра PostgreSQL
- Ревизия CLI при разборе: `1679d214c64134a58579a64e505b29ec1c23d61e`; исходники `cmd/labctl` и Taskfile совпадают с `803c1bc2363cc9a7a1fa2170308de46d190eb8e1`. Отдельного вывода SHA в присланном backup/restore-прогоне нет; образ API не пересобирался и продолжал работать на прежней чистой ревизии `df935dc5bf08`
- PostgreSQL: `postgres:16.14-bookworm`, `pg_dump` сообщил версию `16.14`; imageID до опыта сохранён в [отчёте запуска](postgresql-statefulset.md), повторный runtime imageID в этом выводе не снят
- Среда: Windows PowerShell, одноузловой `kind`, Kubernetes `v1.34.0`, StorageClass `standard`; ресурсы: PostgreSQL StatefulSet/Service/PVC, отдельная база `lab_restore`
- Контракт: [PostgreSQL и сохраняемое состояние](../design/postgresql-stateful-storage.md)

## Цель и исходные условия

Проверить пригодность архива `pg_dump -Fc` для восстановления контрольной записи в другой базе, не разрушая основную. Файл `.local-db/backup.dump` до начала должен отсутствовать; каталог исключён из Git.

## Процедура

1. Зафиксировать контрольную запись: `task db-record-put KEY=backup-proof VALUE=before-backup`, `task db-record-get KEY=backup-proof`.
2. Выполнить `task db-backup`; записать размер архива и версию `pg_dump` через `kubectl ... exec pod/lab-postgres-0 -- pg_dump --version`, не печатать пароль.
3. После создания архива изменить контрольную запись в основной базе командой `task db-record-put KEY=backup-proof VALUE=after-backup` и подтвердить новое значение. Это позволит различить чтение основной базы и восстановленного состояния.
4. Выполнить `task db-restore KEY=backup-proof`: команда создаст только `lab_restore`, выполнит `pg_restore --exit-on-error` и проверит наличие контрольной записи. Отдельным запросом `psql` к `lab_restore` проверить точное значение `before-backup`; рабочий API должен по-прежнему читать `after-backup`. Сообщение команды о наличии записи само по себе не проверяет равенство значения.
5. Сохранить фактический результат, логи и события. После фиксации доказательства выполнить `task db-restore-cleanup`; подтвердить отсутствие `lab_restore` и повторно прочитать `after-backup` из основной базы.

## Ожидаемые признаки

Архив создан вне Pod и имеет ненулевой размер, восстановление в `lab_restore` успешно, контрольная запись содержит состояние на момент копирования `before-backup`, а основная база сохраняет внесённое после копирования значение `after-backup`. Восстановление и удаление тестовой базы не меняют основную базу или PVC. Любая ошибка завершает команду с ненулевым кодом.

## Наблюдение, диагностика и причина

24 октября 2026 года владелец проверил исходное отсутствие `.local-db/backup.dump` (`False`) и базы `lab_restore` (`restore_db_exists=f`), затем записал и прочитал `backup-proof=before-backup`. `pg_dump --version` вернул `PostgreSQL 16.14 (Debian 16.14-1.pgdg12+1)`.

`task db-backup` сохранил поток custom-архива в `.local-db/backup.dump` на хосте. Размер файла составил 2735 байт; `Get-FileHash -Algorithm SHA256` вернул `A3EFB0E65FF3D2B36E04BB610F61095FD9CA1B3BBB8192E4445D507AC8624D1B`. Содержимое архива не печаталось. После копирования рабочий API обновил контрольную запись до `after-backup` и подтвердил новое значение.

`task db-restore KEY=backup-proof` успешно выполнил создание отдельной базы, `pg_restore --exit-on-error` и проверку наличия записи. Дополнительный `psql`-запрос к `lab_restore` показал точное значение `before-backup`, тогда как рабочий API одновременно прочитал `after-backup`. Поэтому проверка различает восстановленное состояние на момент копирования и изменённое состояние основной базы. Сама команда восстановления проверяет наличие значения; его равенство ожидаемому в этом опыте подтверждено отдельным запросом.

После `task db-restore-cleanup` запрос к `pg_database` вернул `restore_db_exists=f`; рабочий API снова прочитал `after-backup`. Сравнения `pvc_uid_unchanged` и `pv_unchanged` дали `True`. Итоговый `task db-status` показал PostgreSQL `1/1 Ready`, Pod `lab-postgres-0` с IP `10.244.0.109`, нулём перезапусков и прежний PVC `data-lab-postgres-0`, связанный с PV `pvc-08e126ef-91ad-406a-86d1-db94b3f2acbe`. В Events оставалось прежнее предупреждение readinessProbe из опыта остановки БД; новых отказов восстановления этот вывод не показывает.

Проверка использует команды уже зафиксированной реализации; пересборки или замены основного API ради backup/restore не было. Результат доказывает пригодность конкретного архива для восстановления контрольной записи в отдельную базу на том же сервере. Время восстановления, поведение при одновременной нагрузке записи и восстановление на независимом экземпляре не измерялись.

## Восстановление и граница

После опыта тестовая база удалена, архив сохранён на хосте, основная база и PVC доступны. При ошибке повторного опыта сохранить вывод до удаления `lab_restore`; повтор требует явного удаления только тестовой базы и создания нового архива/пути. Сценарий не доказывает восстановление на новом узле или другой версии PostgreSQL и не заменяет внешнее долговременное хранение backup. Отдельная [финальная регрессия базового API](postgresql-statefulset.md#финальная-регрессия-базового-профиля-api) при остановленном PostgreSQL также выполнена успешно.
