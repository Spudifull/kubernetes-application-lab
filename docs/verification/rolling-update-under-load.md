# Лабораторный сценарий: обновление под непрерывной нагрузкой

- Статус: `Passed` для повторных обновлений с HTTP `preStop`; два прежних неуспешных результата сохранены ниже
- Ревизия успешного прогона: `c0cfd4e80fe8` по чистому `git status --short`, сборке и ответу `/version`
- Ревизия чистого неуспешного прогона: `5a5290f9254b` по `git status --short`, сборке и ответу `/version`
- Ревизия повтора через Go CLI: чистый commit `630e5e1f53fde62394411e164d93aab1bc27bd7b`, подтверждённый сборкой и ответом `/version`
- Среда: выделенный одноузловой `kind`, контекст `kind-kubernetes-application-lab`, namespace `kubernetes-application-lab`; версии запущенного Kubernetes и инструментов в предоставленном выводе не зафиксированы
- Ревизия прежнего предварительного прогона: `b01c0ad77c85-dirty` по ответу `/version`
- Проверяемый контракт: [`../design/deployment-model.md`](../design/deployment-model.md)

## Цель

Измерить клиентские ответы через `ClusterIP Service` до, во время и после обновления двух реплик. Сопоставить их с состояниями `Deployment`, `ReplicaSet`, Pod и `EndpointSlice`.

## Исходные условия

Сохранить Git SHA, версию chart, ссылку на образ и ревизию Helm. Выполнить `task rollout-client-build`, `task deploy-rollout`, `task rollout-status` и убедиться, что обе реплики Ready. Профиль задаёт `replicaCount: 2`, `maxSurge: 1`, `maxUnavailable: 0`. Подготовить второе окно терминала для нагрузки, третье — для наблюдения за Pod и `EndpointSlice`.

## Способ создать нагрузку или отказ

1. Выполнить `task rollout-load-start`; убедиться по `task rollout-load-status`, что клиент записывает `load_progress` с ненулевым числом запросов.
2. В отдельном окне выполнить `task rollout-load` и сохранить весь вывод, включая `run_id`, `start_time`, `end_time` и `load_summary`.
3. Пока клиент работает, выполнить `task image-build` и записать новую ссылку из `.local-image-ref`. Непосредственно перед обновлением запустить `task rollout-observe` в отдельном окне и сохранить его вывод. Он раздельно записывает время получения снимков Pod (`deletionTimestamp`, `Ready`) и `EndpointSlice` (`ready`, `serving`, `terminating`), но не измеряет момент изменения сетевого пути.
4. Запустить `task rollout-probes-start`: два клиентских Pod должны увидеть `/readyz: 200` непосредственно у двух старых API Pod до обновления. Заранее открыть журналы каждого старого API Pod с отметками времени, чтобы не потерять `signal_received`, `shutdown_*`, `readiness_rejected` и `work_rejected_during_shutdown` после его удаления. Затем выполнить `task deploy-rollout` и `task rollout-status`.
5. Дождаться завершения клиента и проверить его итоговый статус через `task rollout-load-status`; сохранить вывод `task rollout-probes-status`, `task rollout-events`, журналы API и снимки Kubernetes. Наблюдающие Pod оставляются для доказательства до сохранения журналов; затем удалить их через `task rollout-probes-cleanup`, а нагрузочный Pod — через `task rollout-load-cleanup`.
6. При отдельном повторе допустимо изменить только `maxUnavailable` на 1 через явное значение Helm и сравнить доступное число реплик. Второй опыт имеет свой `run_id`; нулевое число ошибок в нём не означает одинаковую гарантию контроллера.

## Ожидаемые признаки

Новый образ отличается от старого; Helm history получает новую ревизию. Новые Pod используют новый образ и достигают Ready, старые завершаются. При заданном профиле контроллер стремится сохранять две доступные реплики и может временно создать третью. Наблюдатели фиксируют переход `/readyz` каждого старого Pod от `200` к `503` и результат новой `/work`; срок ожидания ограничен 120 секундами. Клиент выдаёт ограниченную статистику: `total_requests`, `successful_requests`, `http_5xx`, `other_non_2xx`, `connection_errors`, `timeouts`, `duration_ms`. Каждое событие HTTP-ошибки содержит `run_id`, время, статус и значение `X-Lab-Pod`; отсутствие заголовка тоже сохраняется как пустое значение. Цель штатного опыта — ноль ошибок, но это результат измерения, а не гарантия.

## Диагностика

Чистый повтор связал каждый клиентский `request_error` с `work_rejected_during_shutdown` на конкретном старом Pod по времени, имени Pod и `run_id`. В клиенте принудительно отключено повторное использование HTTP-соединений, поэтому каждый запрос проверял новый TCP-путь через `Service`. Снимки Pod и `EndpointSlice` снимались последовательно примерно раз в секунду и могут пропустить краткий переход; даже условие `ready=false` в `EndpointSlice` не доказывает, что узел уже перестал выбирать Pod. `Taskfile.yml` остаётся источником команд для повторения опыта.

## Причина

Для трёх `503` чистого повтора установлена непосредственная причина: после `SIGTERM` приложение сразу включило middleware отказа в новой работе, пока запросы через `Service` ещё достигали старых Pod. Серверный журнал и клиентский `X-Lab-Pod` совпадают. Какая доля окна относится к обновлению `EndpointSlice`, а какая — к применению правил маршрутизации на узле, этим опытом не установлена. Прежние два `503` без корреляции остаются отдельным неуспешным наблюдением, совместимым с этой причиной, но не доказанным задним числом.

## Восстановление

В обоих чистых прогонах новая версия достигла двух Ready-реплик, а `task smoke` прошёл, поэтому откат для восстановления не потребовался. Нагрузочный и наблюдающие Pod сохранялись до чтения журналов. При будущем отказе сначала сохранить данные, затем выбрать исправление или откат по сценарию [`failed-rollout-rollback.md`](failed-rollout-rollback.md).

## Поведение Kubernetes

Helm revision 7 и `Deployment` завершили обновление до `2/2` Ready. Во время завершения старые Pod сохранялись в `EndpointSlice` как `terminating=true`, `ready=false`, первоначально с `serving=true`; более поздние снимки показывают `serving=false` и удаление старых конечных точек. Состояние контроллера не предотвратило три ошибки HTTP-клиента.

В успешном повторе Helm revision 9 также достигла `2/2` Ready. Для обоих старых Pod `EndpointSlice` показал `terminating=true`, `ready=false` до `SIGTERM`, пока приложение ещё сохраняло допуск новой работы в течение HTTP `preStop`. После завершения остались только две конечные точки новой версии.

## Поведение приложения

В неуспешном чистом прогоне после `SIGTERM` каждый старый процесс сразу выставил readiness false и отклонил новую работу с `503`, сохранив заголовок `X-Lab-Pod`. В успешном повторе сначала выполнен трёхсекундный HTTP `preStop` без отказа в новой работе, затем приложение получило `SIGTERM`, выставило readiness false и отклонило прямые диагностические запросы наблюдателей. Оба старых процесса завершили HTTP-сервер штатно; два новых процесса прошли проверку готовности.

## Что результат подтверждает

Два прежних прогона показывают успешное завершение обновления контроллером, но не непрерывную доступность HTTP-маршрута: сначала 2, затем 3 ответа `503` из 1799 запросов в каждом опыте. Чистый неуспешный прогон связывает три ошибки с отказом приложения принимать работу во время завершения. Следующий чистый прогон подтверждает, что при указанной нагрузке HTTP `preStop` предшествовал `SIGTERM` и все 1799 запросов через `Service` завершились успешно без HTTP- и сетевых ошибок.

## Что результат не подтверждает

Гарантию отсутствия ошибок при иной частоте или длительности запросов, другом числе узлов, потере узла, внешней сети, завершении принятой длительной работы или равномерной балансировке запросов между Pod. Прогон не устанавливает точное время прекращения маршрутизации на узле и не доказывает, что три секунды задержки достаточны в любой среде.

## Остаточный риск

Клиент выполняет один запрос примерно каждые 100 мс и открывает новое соединение; другой профиль нагрузки может выявить иное поведение. Состояние Pod меняется быстрее частоты ручных наблюдений.
