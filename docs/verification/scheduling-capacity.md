# Лабораторный сценарий: ограничение размещения Pod по CPU request

- Статус: `Passed` — повторный прогон после фиксации сценария в Git подтвердил `FailedScheduling: Insufficient cpu`, доступность API и удаление временного Pod
- Ревизия сценария при повторном прогоне: `2eeadba645bc3c4a29565e7aae46cf89b2d4c8a4` (commit создан после предварительного опыта). Базовый HEAD до подготовки сценария — `0155c1968c9f2701cc4262124b41fe40bafb38e7`
- Среда: выделенный одноузловой `kind`, контекст `kind-kubernetes-application-lab`, namespace `kubernetes-application-lab`
- Проверяемый контракт: [`../design/deployment-model.md`](../design/deployment-model.md)

## Цель

Показать, что планировщик не размещает временный Pod, чей CPU request превышает CPU `allocatable` единственного узла. Отделить решение планировщика по request от фактического использования CPU, CPU limit и работы HPA.

## Исходные условия

Проверить чистую Git-ревизию, текущий контекст, единственный Ready-узел и работоспособность основного Helm release через `task smoke`. Опыты с HPA и другие источники нагрузки завершить либо явно сохранить их состояние; новый Pod не принадлежит Helm release. Сохранить версию Kubernetes, `allocatable` узла, уже выделенные requests из описания узла и текущий статус API. Не удалять одноимённый Pod от прежнего опыта, пока его состояние и события не записаны.

Сценарий вычисляет request как CPU `allocatable` узла плюс `1000m`, а не использует случайное фиксированное число. Перед созданием Pod выполняются проверка точного контекста, числа и готовности узлов, отсутствия одноимённого Pod и серверная проверка объекта. Образ лабораторного клиента указывается как ограниченный резервный процесс, если среда неожиданно изменится и Pod всё же получит узел. Для проверки `FailedScheduling` образ не требуется загружать: контейнер не должен запускаться.

## Способ создать нагрузку или отказ

Сначала выполнить `task scheduling-validate`, затем `task scheduling-start` и `task scheduling-wait`. Команды находятся в `Taskfile.yml`; сценарий формирует объект Pod в памяти на основании текущего CPU `allocatable`. Pod имеет CPU request и limit на `1000m` выше `allocatable`, memory request `16Mi`, limit `32Mi`, `restartPolicy: Never`, `activeDeadlineSeconds: 90` и ограничения безопасности уровня `restricted`. При ожидаемом результате он не потребляет запрошенный CPU, потому что контейнер вообще не запускается.

До очистки сохранить полный вывод `task scheduling-status`: состояние узла и Pod, заданные ресурсы, условия, описание и события. Затем проверить основной API через `task smoke`. Только после сохранения доказательств выполнить `task scheduling-cleanup`; повторная проверка `task smoke` допустима после удаления Pod.

## Ожидаемые признаки

- Серверная проверка принимает объект. Созданный Pod остаётся `Pending`, `spec.nodeName` пусто, условие `PodScheduled=False` имеет причину `Unschedulable`.
- Событие `FailedScheduling` прямо указывает на нехватку CPU. CPU request Pod больше CPU `allocatable` единственного узла; CPU limit равен request, но не является основанием решения планировщика.
- Основной API остаётся доступен через `Service`. После сохранения данных удаляется только временный Pod.

## Диагностика

Если серверная проверка не принимает объект, сохранить её ошибку: отказ `ResourceQuota`, `LimitRange` или политики допуска отличается от решения планировщика. Если Pod остаётся `Pending` по другой причине, исследовать `PodScheduled` и события, не приписывая исход нехватке CPU. Если Pod получил `spec.nodeName`, опыт не доказал ожидаемое свойство: зафиксировать состояние, не увеличивать нагрузку и проверить фактический request и `allocatable`. Недоступность образа после успешного размещения тоже не является `FailedScheduling`.

## Причина

Планировщик сопоставляет requests Pod с доступной планируемой ёмкостью узла, основанной на `allocatable` и уже размещённых requests. В обоих прогонах CPU request `33` превысил весь CPU `allocatable: 32`, и событие для каждого Pod прямо указало `Insufficient cpu`. CPU limit тоже равен `33`, но результат объясняет именно request. Это не опыт CPU throttling и не нехватка фактически потребляемого процессорного времени.

## Восстановление

После записи событий владелец удалил `lab-api-unschedulable` через `task scheduling-cleanup`; удаление завершилось, последующая проверка не нашла Pod. Helm release, HPA и параметры узла сценарий не изменяет. Если резервный контейнер вопреки ожиданию запустился, он ограничен выделением `1Mi` на одну секунду и общим сроком Pod; это не ожидаемый успешный исход опыта.

## Поведение Kubernetes

В обоих прогонах API server принял объект, но scheduler не назначил ему узел. Pod сохранил `Pending` и `PodScheduled=False`; отдельное событие `FailedScheduling` установило причину. Контейнер не запускался, поэтому установленный CPU limit не применялся как квота процесса.

## Поведение приложения

API не участвовал в вычислении возможности размещения. Отдельная проверка `Service` после создания Pod успешно получила `/version`; это наблюдение основного стенда, а не доказательство отсутствия любых последующих ошибок.

## Что результат подтверждает

Повторный опыт после commit сценария подтверждает, что Pod с CPU request `33` не был размещён на единственном узле с CPU `allocatable: 32`, а планировщик назвал причину `Insufficient cpu`. После опыта основной API ответил через `Service`; временный Pod затем удалён.

## Что результат не подтверждает

Поведение нескольких узлов, работу Cluster Autoscaler, фактическое исчерпание CPU, память узла, HPA при `Pending` его собственных реплик или точность метрик использования ресурсов.

## Остаточный риск

Число `allocatable` и доступная ёмкость зависят от конфигурации узла и других Pod. Сценарий намеренно требует больше всего `allocatable`, поэтому на одноузловом кластере решение не зависит от их количества; на многоузловом кластере он останавливается до создания Pod. Документация содержит незакоммиченные изменения, поэтому весь прогон нельзя называть выполненным из полностью чистого рабочего дерева; код сценария и команды `Taskfile.yml` уже находятся в commit `2eeadba645bc3c4a29565e7aae46cf89b2d4c8a4`.
