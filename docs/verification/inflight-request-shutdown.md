# Лабораторный сценарий: завершение принятого запроса

- Статус: `Passed` — один принятый восьмисекундный запрос завершён после удаления Pod; новая работа отвергнута
- Ревизия предварительного прогона: `b01c0ad77c85-dirty` по ответу `/version`
- Ревизия повтора через Go CLI: чистый commit `630e5e1f53fde62394411e164d93aab1bc27bd7b`, подтверждённый предшествующей сборкой и ответом `/version`
- Ревизия полного повтора с серверным журналом: чистый commit `5d233c29e7ec345d24bc27113f897a6929226a41`; `/version.revision=5d233c29e7ec`
- Среда предварительного прогона: выделенный `kind`, контекст `kind-kubernetes-application-lab`, namespace `kubernetes-application-lab`; версии инструментов в предоставленном выводе не зафиксированы
- Проверяемый контракт: [`../design/application-runtime.md`](../design/application-runtime.md)

## Цель

Проверить, что принятый до `SIGTERM` запрос `/work` возвращает `200`, а новая работа во время завершения не принимается.

## Исходные условия

Выполнить `task rollout-client-build`, `task deploy-rollout`, `task rollout-status`. Оба Pod должны быть Ready; маршрут `/work` включён только в этом профиле. Клиентский образ загружен в узел `kind`.

## Способ создать нагрузку или отказ

Выполнить `task inflight-work` в Windows PowerShell. Сценарий выбирает Ready Pod, сначала запускает отдельный наблюдающий Pod и дожидается ответа `/readyz: 200`, затем создаёт клиентский Pod с запросом непосредственно к IP выбранного процесса на `/work?duration_ms=8000`. Он ждёт в серверном журнале **совпадающих** `work_started` и `run_id`, проверяет отсутствие `work_completed` перед удалением и только затем удаляет Pod обычным способом без `--force`. Клиент записывает ответ старого запроса, наблюдатель — переход `/readyz` к `503` и ответ новой `/work`. При отсутствии подтверждения начала серверный Pod не удаляется.

Во втором окне заранее наблюдать журналы API Pod через `kubectl --context kind-kubernetes-application-lab logs -f pod/<имя> -n kubernetes-application-lab`, чтобы сохранить `shutdown_*` и `work_completed`. Наблюдающий Pod обращается непосредственно к старому Pod: запрос через `Service` мог бы попасть в другую Ready-реплику и не проверил бы локальный отказ новой работе. После опыта выполнить `task rollout-status` и `task smoke`; оба клиентских Pod оставлены для доказательства и удаляются явной командой `kubectl --context kind-kubernetes-application-lab delete pod <имя> -n kubernetes-application-lab` только после сохранения журналов.

## Ожидаемые признаки

`work_started` с `run_id` предшествует удалению Pod. После добавления HTTP hook при удалении ожидаются `prestop_started`, `prestop_completed`, `signal_received` со значением `terminated`, `shutdown_started`, `http_server_shutdown_started`, `work_completed` и `shutdown_completed`. Во время `preStop` приложение ещё принимает запросы; после `SIGTERM` `/readyz` меняется на `503` и новая `/work` получает `503`, а ранее принятый запрос возвращает `200`. Клиенты сохраняют значение `X-Lab-Pod`, позволяющее сопоставить ответы с удаляемым Pod. Контроллер восстанавливает требуемое число Ready-реплик. Повтор на чистой ревизии подтвердил клиентские ответы, но не предоставил полный серверный журнал этого порядка.

## Диагностика

Если клиент не получил `200`, сохранить его Pod и журнал, события исходного Pod, последовательность `work_*` и `shutdown_*`, состояние `EndpointSlice` и причину завершения контейнера. Не считать сообщение `work_request_sent` доказательством принятия сервером; таким доказательством служит `work_started` с тем же `run_id`.

## Причина

При удалении Pod HTTP `preStop` сначала оставляет приложению три секунды для обслуживания запросов, пока Kubernetes обновляет сетевой путь. Затем `BeginShutdown` закрывает приём новой прикладной работы, но не отменяет контекст принятого HTTP-запроса. `http.Server.Shutdown` получает отдельный ограниченный контекст и ждёт активный обработчик. Этот расчёт требует повторной проверки длительного запроса после изменения.

## Восстановление

`Deployment` создаёт замену; дождаться её готовности и повторить `task smoke`. При сбое сохранить журналы клиентского Pod до удаления.

## Поведение Kubernetes

После удаления Pod Kubernetes передаёт `SIGTERM`, убирает завершающуюся конечную точку из маршрутизации и восполняет число реплик.

## Поведение приложения

Readiness становится false, новая работа получает `503`, принятый запрос завершает ограниченное ожидание и процесс штатно закрывается в пределах `terminationGracePeriodSeconds`.

## Что результат подтверждает

Повтор 24 октября подтвердил возврат `200` для одного принятого длительного запроса, прямые `503` для готовности и новой работы на удаляемом Pod, порядок серверных событий `preStop` → `SIGTERM` → завершение принятой работы → завершение сервера, а также восстановление двух Ready-реплик и ответа через `Service`.

## Что результат не подтверждает

Завершение произвольной внешней работы, отсутствие потерь при длительной нагрузке, устойчивость к потере узла или мгновенное исключение Pod из всех сетевых путей.

## Остаточный риск

Окно для непосредственного обращения к завершающемуся Pod короткое. Если наблюдающий Pod не успеет увидеть `503`, нужен повтор опыта; результат `Service` с двумя репликами не заменяет прямую проверку старого Pod. Между последней проверкой `work_completed` и удалением остаётся малая гонка; сопоставить времена событий после опыта.
