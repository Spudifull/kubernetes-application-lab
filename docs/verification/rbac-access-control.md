# Лабораторный сценарий: ServiceAccount и RBAC

- Статус: `Passed` — повторная проверка после commit и удаление временного Pod подтверждены для одного локального опыта
- Ревизия ресурсов при создании Pod: `724a2b556c295f20ffddf97ef36e721963d421ed`; ревизия зафиксированного сценария при повторной проверке: `539146476f4afae8784402d5810b0a2176ce59ac`. Манифесты RBAC между этими ревизиями не менялись.
- Среда: выделенный `kind-kubernetes-application-lab-net`, Kubernetes v1.34.0, namespace `kubernetes-application-lab-policy` с Pod Security Standards уровня `restricted`
- Проверяемый контракт: [модель поставки](../design/deployment-model.md) и [стратегия проверки](../engineering/verification-strategy.md)

## Цель

Проверить, что отдельный `ServiceAccount` может прочитать только объект собственного диагностического `Pod` в одном namespace, но не может читать `Secret`, менять `Deployment` или получать список Pod в другом namespace. Основной Go API не должен получать токен ради этого опыта.

## Исходные условия

Выделенный сетевой кластер и namespace `kubernetes-application-lab-policy` существуют. В нём присутствует `Deployment/lab-api` из того же Helm chart; основной `Deployment` сохраняет `automountServiceAccountToken: false`. После прежнего эксперимента `NetworkPolicy` не должны блокировать клиенту путь к Kubernetes API. Перед прогоном зафиксировать Git SHA, состояние namespace, API и правил `NetworkPolicy`.

## Способ создать нагрузку или отказ

`task rbac-validate` выполняет серверную проверку `ServiceAccount`, `Role` и `RoleBinding`. `task rbac-start` применяет их и создаёт временный `Pod/lab-rbac-client` в ограниченном namespace. `Role` разрешает только `get` для `pods/lab-rbac-client`; wildcard-прав, `ClusterRole` и `ClusterRoleBinding` нет. У `ServiceAccount` и Pod выключен автоматический токен. Только диагностический Pod получает короткоживущий проецируемый токен с аудиторией API server по умолчанию и CA из `kube-root-ca.crt`.

`task rbac-test` сопоставляет ответы `kubectl auth can-i` от имени ServiceAccount с четырьмя фактическими HTTPS-ответами Kubernetes API из Pod. Токен считывается только внутри контейнера и не печатается. Клиент выводит метку запроса, метод, HTTP-код и ожидаемый код, не тело ответа.

## Ожидаемые признаки

Чтение собственного Pod возвращает `yes` и HTTP `200`. Чтение списка `Secret`, попытка `PATCH` объекта `Deployment/lab-api` и получение списка Pod в основном namespace возвращают `no` и HTTP `403`. Любой отказ соединения, DNS/TLS, отсутствие токена, `401` или `404` не считается доказательством RBAC-запрета. Диагностический Pod завершается `Succeeded` только после всех четырёх точных проверок.

## Наблюдавшиеся признаки

`task rbac-validate` прошёл серверную проверку. `task rbac-start` применил `ServiceAccount`, `Role`, `RoleBinding` и создал временный клиентский Pod; экспериментальный `Deployment/lab-api` был доступен `1/1`. `task rbac-status` показал минимальное правило `get` для `pods/lab-rbac-client`, привязку к отдельному ServiceAccount и состояние клиента `Completed` без перезапусков. Журнал клиента от 18 октября 2026 года, 18:29:55 UTC, зафиксировал фактические ответы API: чтение собственного Pod — `200`, чтение списка `Secret` — `403`, `PATCH` объекта `Deployment/lab-api` — `403`, чтение списка Pod другого namespace — `403`.

Первый запуск `task rbac-test` не завершился: `kubectl auth can-i` отверг несуществующий флаг `--resource-name` до проверки первого разрешения. После исправления аргумента следующий запуск подтвердил `own_pod_read=yes`, но остановился на `secret_read_denied`: сценарий считал ожидаемый код завершения `1` при ответе `no` неисправностью команды. Обе остановки относятся к сценарию проверки, а не к отказу RBAC в клиентском Pod.

После исправления обработки кода завершения `task rbac-test` прошёл полностью: `own_pod_read=yes` с кодом `0`, а `secret_read_denied`, `deployment_change_denied` и `other_namespace_read_denied` дали `no` с кодом `1`. Ожидание Pod завершилось успешно, после чего сценарий прочитал те же четыре ответа API из журнала клиента: `200/403/403/403`. Повторный `task rbac-status` показал `Completed`, `0` перезапусков и неизменный узкий `Role`. Первый успешный вывод был предоставлен до commit исправленного сценария. После фиксации изменений пользователь повторил `task rbac-test` с теми же четырьмя результатами авторизации и клиентскими ответами, затем `task rbac-cleanup` удалил `Pod/lab-rbac-client`. Повторное создание Pod не выполнялось: второй запуск прочитал журнал клиента, созданного на более ранней зафиксированной ревизии тех же манифестов.

## Диагностика

При ошибке сохранить `task rbac-status` до очистки. Сопоставить `ServiceAccount`, `Role`, `RoleBinding`, имя и namespace Pod, условия Pod, события, доступность API server и его CA. Ответ `401` означает проблему идентификации, `403` — отказ авторизации, `404` может означать отсутствующий объект, а ошибка `curl` до HTTP — сетевой или TLS-сбой. Не выводить токен или заголовок `Authorization`.

## Причина

Ожидаемые `403` и ответы `no` согласуются с единственным разрешением `get pods/lab-rbac-client` в `Role`; ответ `200` и `yes` подтверждают разрешённый путь. Две прежние остановки независимой проверки были вызваны ошибками сценария: неподдерживаемым флагом `--resource-name` и неверной трактовкой кода завершения `1` для `no`. Исправленный сценарий затем выполнился полностью до фиксации в Git.

## Восстановление

После сохранения доказательств выполнен `task rbac-cleanup`: временный `Pod/lab-rbac-client` удалён с ожиданием завершения операции. `ServiceAccount`, `Role` и `RoleBinding` остаются для повторного опыта; основной и экспериментальный API release не меняются. Отдельный запрос на отсутствие Pod после удаления и проверка доступности основного API не предоставлены.

## Поведение Kubernetes

API server принял запрос клиента с проецируемым токеном для разрешённого чтения и ответил `403` на три действия вне выданного разрешения. Отдельная проверка `kubectl auth can-i` от имени того же ServiceAccount дала согласующиеся ответы. `RoleBinding` действует только в заданном namespace; этот опыт не проверяет все возможные права ServiceAccount.

## Поведение приложения

Go API в опыте не участвует и не получает токен Kubernetes API. Существование `Deployment/lab-api` служит лишь целью запрещённого запроса `PATCH`.

## Что результат подтверждает

В одном локальном опыте фактический клиент с отдельным токеном получил `200` для собственного Pod и три `403` для лишних действий; независимая проверка `kubectl auth can-i` дала `yes/0` и три `no/1`. Ответы согласуются с узким `Role` и `RoleBinding`.

## Что результат не подтверждает

Повторная проверка использовала существовавший Pod и его прежний журнал, а не создала нового клиента после commit `5391464`. Вывод удаления Pod не равнозначен отдельному запросу на его отсутствие. Опыт не доказывает безопасность других ServiceAccount, отсутствие дополнительных cluster-wide bindings вне этого опыта или доступность основного API после очистки.

## Остаточный риск

Namespace может иметь другие политики сети или авторизации, влияющие на опыт. Проецируемый токен был доступен внутри диагностического Pod до его удаления. Результат относится к проверенным действиям и состоянию локального кластера, а не ко всем возможным правам или средам.
